> 상위 문서: [01 백엔드 구성안](01-backend-architecture-v1.md)(기술 · 모듈 · 데이터 · 흐름 — §13 검토 반영 포함). 개발 환경은 [02](02-dev-setup.md).
> 상태: **1차 설계 v1.1 — Codex 검토 반영(§17, 앞 절보다 우선)** · 결정 필요 항목은 §15. 구현은 이 문서 · 01 · 목업(docs/ux/mockups)을 기준으로 한다.

## 0. 한눈에

| 항목 | 설계 |
|---|---|
| 운영 형태 | 기관 **내부망 온프레미스**, 인터넷 차단 전제. 사용자 6~20명 동시, 업무 시간 상시 |
| 서버 | 운영 **1대(앱 + DB)** 기본, 백업은 **별도 저장소(NAS · 백업 서버)**. 확장 시 앱/DB 2대 → DB 이중화(§13) |
| 서비스 | nginx(TLS · 정적 · 프록시) · api(NestJS) · collab(Hocuspocus) · worker(작업 · 렌더) · PostgreSQL 16 |
| 컨테이너 | Docker Engine + Compose, 이미지 버전 · 다이제스트 고정, 비루트 실행 |
| 저장 | PostgreSQL(업무 · Yjs · 큐 · 세션 · 감사) + 파일 볼륨(업로드 · 산출물, 불변 키 · 체크섬) |
| 백업 | DB 전체 백업 + WAL 연속 보관(시점 복구) + 파일 스냅샷 → 별도 장애 영역, 암호화. **RPO 15분 · RTO 4시간(제안)** |
| 보안 | 443만 개방 · 기관 인증서 TLS · DB 역할 분리(감사는 INSERT만) · 비밀값 파일 마운트 · 업로드 검사 · 보안 헤더 |
| 인증 | 자체 ID/PW(argon2id) + 사내 SSO(SAML 2.0 · OIDC) 선택, Admin 비상 로그인 |
| 관측 | JSON 로그(파일 회전 · 선택 SIEM 전달) · `/metrics` · 상태 확인 · 경보(디스크 · 백업 나이 · WAL · 인증서 · 큐) |
| 배포 | 개발망 CI → **오프라인 반입 묶음**(이미지 tar · 해시 · SBOM · 마이그레이션) → 운영 설치 스크립트(백업 → 마이그레이션 → 재시작 → 점검) |

**서비스별 책임**
| 서비스 | 하는 일 | 상태 | 수평 확장 |
|---|---|---|---|
| nginx | TLS · HTTP/2 · 정적 파일 · 프록시 · 보안 헤더 · 요청 크기/속도 제한 | 무상태 | 앞단 L4로 다중화 가능 |
| api | REST · SSE · 인증 · 권한 · 업무 트랜잭션 · collab 고정 RPC 호출 | 무상태(세션은 DB) | 프로세스 N개(기본 2) |
| collab | Yjs 동기화 · 갱신 순번 저장 · ACK · 고정/해제 · 조회 전용 · 열람 제한 | **문서별 상태(메모리)** | 문서 이름으로 고정 라우팅해야만 확장(§13.2) |
| worker | 엑셀 스트리밍 · 행 검사 · 산출물 · 공식 ERD 렌더 · 만료 · 메일 · 투영 재계산 · outbox | 무상태(큐는 DB) | 작업 종류별 동시성 설정 |
| PostgreSQL | 모든 영속 데이터 | 상태 | 스트리밍 복제(§13.3) |

## 3. 서버 사양 (운영 1대 기본)

| 자원 | 권장 | 근거 · 배분 |
|---|---|---|
| CPU | **8 vCPU** | api 2 · collab 1 · worker 2(엑셀 · Chromium) · PostgreSQL 2~3 · 여유 |
| 메모리 | **32 GB** | PostgreSQL `shared_buffers` 8GB · 작업 메모리 · api 2×1GB · collab 2GB(동시 영역 20개 × Y.Doc) · worker 4GB(10만 행 · Chromium) · OS 캐시 |
| 디스크(데이터) | **SSD 500 GB** (DB 200 · 파일 200 · 로그 · 여유) | 5년 증가 추정 §12 |
| 디스크(백업) | 서버 밖 **NAS · 백업 서버 2 TB** 이상 | 전체 백업 4주 + WAL 4주 + 파일 스냅샷 |
| OS | RHEL 9 계열(Rocky · Alma) 또는 Ubuntu 22.04/24.04 LTS — 기관 표준 따름 | Docker Engine 지원 |
| 시간 | 기관 NTP 동기화 필수(세션 만료 · 감사 · 사용 기한) | |

- 검증(스테이징) 서버는 같은 구성 · 절반 사양(4 vCPU · 16 GB)으로 운영과 같은 설치 묶음을 먼저 설치한다.
- 가상 머신이면 스냅샷은 백업을 대신하지 않는다(DB 일관성 · 별도 장애 영역이 아님).

## 4. 네트워크 · 포트

| 방향 | 출발 → 도착 | 포트 | 용도 |
|---|---|---|---|
| 인바운드 | 사용자망 → nginx | **443/TCP** (80은 443으로 이동만) | 화면 · API · SSE · WebSocket |
| 인바운드 | 운영자 단말 → 서버 | 22/TCP(관리망만) | 설치 · 점검 |
| 내부(호스트 안) | nginx → api / collab | 4310 · 4320 | 컨테이너 네트워크(외부 비공개) |
| 내부 | api · collab · worker → PostgreSQL | 5432 | 컨테이너 네트워크(외부 비공개) |
| 내부 | api → collab | 4321(내부 RPC) | 확정 신청 고정 · 해제 — **공유 비밀 + 컨테이너 네트워크 한정** |
| 아웃바운드 | worker → SMTP 릴레이 | 25/587 | 알림 메일 |
| 아웃바운드 | api → SSO IdP | 443 | SAML 메타데이터 · OIDC 토큰 |
| 아웃바운드 | 서버 → NTP · (선택) syslog/SIEM · 백신 API | 123 · 514/6514 · 기관 지정 | |
| 아웃바운드 | 서버 → 백업 저장소 | NFS/SMB/SSH(rsync) | 백업 전송 |
| 차단 | 서버 → 인터넷 | 전부 | 패키지 · 이미지는 반입 묶음으로 |

**nginx 설정 요점**
- WebSocket(`/collab`): `proxy_http_version 1.1` · `Upgrade`/`Connection` 헤더 · `proxy_read_timeout 1h` · 버퍼링 끔.
- SSE(`/api/v1/events`): `proxy_buffering off` · `X-Accel-Buffering: no` · `proxy_read_timeout 1h`.
- 업로드: `client_max_body_size 25m`(엑셀 20MB + 여유), 업로드 경로만 크게.
- 속도 제한: 로그인 경로 출처 IP당 분당 10회 · API 전체 초당 50회(버스트 100).
- 보안 헤더: HSTS · `Content-Security-Policy`(자기 출처만, 인라인 스크립트 금지 — web 빌드에서 해시) · `X-Content-Type-Options` · `Referrer-Policy` · `frame-ancestors 'none'`.
- 요청 ID: `X-Request-Id` 생성 → 모든 서비스 로그에 같은 값.

## 5. 컨테이너 구성 (운영 compose)

### 5.0 이름 규칙 — 이름만 봐도 무엇인지 안다
- 규칙: **`neodb-<하는 일>`**. 하는 일은 사용자가 아는 말로(`collab`이 아니라 `erd-collab`, `worker`가 아니라 `job-worker`).
- 이미지는 `neodb/<같은 이름>:<버전>`, 컨테이너는 `neodb-<같은 이름>`(여러 개면 `-1`, `-2`). compose 프로젝트 이름은 `neodb`.
- 버전 태그: `<주.부.수정>-b<빌드일>` (예: `1.0.0-b20261125`, 도커 태그는 `+`를 못 쓴다). `latest`는 쓰지 않는다.
- 모든 이미지에 OCI 라벨: `org.opencontainers.image.title`(이름) · `description`(한 줄 설명) · `version` · `revision`(커밋) · `vendor`(NeoDB) — `docker image inspect`만으로 역할이 보인다.

| # | 컨테이너 이름 | 이미지 | 하는 일 (한 줄) | 늘 떠 있음 |
|---|---|---|---|---|
| 1 | `neodb-web` | `neodb/web` | **사용자 입구** — HTTPS(기관 인증서) · 화면 파일 · api/공동 편집으로 연결 · 보안 헤더 · 업로드 크기 · 속도 제한 (nginx + 화면 빌드) | ● |
| 2 | `neodb-api-1` | `neodb/api` | **업무 API** — 로그인 · 권한 · 사전 · 결재 · 모델 · 설정 · 감사 · 실시간 알림(SSE) | ● |
| 3 | `neodb-api-2` | `neodb/api` | 업무 API 두 번째(한쪽 재시작 · 장애에도 이어짐) | ● |
| 4 | `neodb-erd-collab` | `neodb/erd-collab` | **ERD 실시간 공동 편집** — 동시 편집 · 변경 즉시 저장 · 조회 전용 연결 · 확정 신청 때 쓰기 고정 | ● |
| 5 | `neodb-job-worker` | `neodb/job-worker` | **뒤에서 도는 작업** — 엑셀 10만 행 검사 · DDL · 산출물 · 공식 ERD 렌더(Chromium · 한글 글꼴) · 메일 · 만료 처리 | ● |
| 6 | `neodb-postgres` | `neodb/postgres` | **데이터베이스** — PostgreSQL 16 + pg_trgm + 역할 · 초기 설정(공식 이미지에 NeoDB 초기화만 더함) | ● |
| 7 | `neodb-db-migrate` | `neodb/api` | **DB 구조 올리기** — 배포 때 한 번 실행하고 끝(구조 변경 계정은 이것만) | 일시 |
| 8 | `neodb-backup` | `neodb/backup` | **백업** — 예약 시간에 DB(전체 · 차등 · WAL) · 파일 스냅샷을 백업 저장소로 보내고 끝(pgBackRest · rsync) | 일시 |
| 9 | `neodb-monitor-prometheus` | `neodb/monitor-prometheus` | (선택) 지표 수집 · 경보 규칙 — 기관 모니터링이 없을 때만 | ● |
| 10 | `neodb-monitor-grafana` | `neodb/monitor-grafana` | (선택) 지표 화면 | ● |

- 합계: 기본 **늘 6개 + 일시 2개**, 모니터링을 쓰면 늘 8개. 이미지는 기본 6종(`web` · `api` · `erd-collab` · `job-worker` · `postgres` · `backup`) + 선택 2종.
- `neodb/api` 이미지 하나로 `neodb-api-1` · `neodb-api-2` · `neodb-db-migrate`를 돌린다(실행 명령만 다름).

### 5.2 컨테이너별 설정

| 컨테이너 | 이미지(고정 버전 · 다이제스트) | 자원 제한 | 볼륨 | 상태 확인 | 재시작 |
|---|---|---|---|---|---|
| `neodb-web` | `neodb/web` (nginx:1.27-alpine + 화면 빌드) | 0.5 CPU · 256MB | 인증서(ro) | `/healthz` 프록시 | always |
| `neodb-api-1` · `-2` | `neodb/api` (node:26-slim 기반, 비루트) | 1 CPU · 1GB 각 | 파일(rw: 업로드 저장), 비밀(ro) | `/readyz` | always |
| `neodb-erd-collab` | `neodb/erd-collab` | 1 CPU · 2GB | 비밀(ro) | `/healthz` | always |
| `neodb-job-worker` | `neodb/job-worker` (Chromium · 한글 글꼴 포함) | 2 CPU · 4GB | 파일(rw), 비밀(ro), `/tmp` tmpfs | 하트비트 | always |
| `neodb-postgres` | `neodb/postgres` (postgres:16 + pg_trgm · 초기화) | 3 CPU · 12GB | `/data/pg`, WAL 보관 경로 | `pg_isready` | always |
| `neodb-db-migrate` (일회성) | `neodb/api` `node dist/migrate` | — | 비밀(ro) | 종료 코드 | no |
| `neodb-backup` (예약) | `neodb/backup` (pgBackRest · rsync) | 1 CPU · 1GB | `/data/pg`(ro) · 파일(ro) · 백업 대상 | 마지막 성공 시각 | 예약 실행 |

- 모든 앱 컨테이너: 비루트 사용자 · 읽기 전용 루트 파일시스템(쓰기는 지정 볼륨 · tmpfs만) · `no-new-privileges` · 불필요한 권한(capabilities) 제거.
- 네트워크는 §5.1 — DB는 호스트 포트를 열지 않는다.
- 로그: stdout JSON → Docker `local` 드라이버(파일 회전 100MB × 10) → 선택 syslog 전달.

## 6. 저장 설계

### 6.1 PostgreSQL
- 버전 16, 확장 `pg_trgm`(사전 검색 3열 색인 — 23 §6-1). 인코딩 UTF-8, 정렬 `C`(+ 한글 정렬은 질의에서 `ko-KR` ICU 콜레이션).
- 시작 설정(32GB 서버): `shared_buffers=8GB` · `effective_cache_size=20GB` · `work_mem=32MB` · `maintenance_work_mem=1GB` · `max_connections=100`(api 2×20 · collab 10 · worker 10 · 여유) · `wal_level=replica` · `archive_mode=on` · `max_wal_size=4GB` · `checkpoint_timeout=15min` · `log_min_duration_statement=500ms`.
- **역할 분리**
  | DB 역할 | 권한 | 쓰는 곳 |
  |---|---|---|
  | `neodb_owner` | 스키마 소유 · DDL | 마이그레이션만(배포 때) |
  | `neodb_app` | 업무 스키마 SELECT/INSERT/UPDATE/DELETE, `audit` 스키마 **INSERT · SELECT만** | api · collab · worker |
  | `neodb_ro` | 읽기 전용 | 운영 점검 · 보고(선택) |
  | `neodb_backup` | 복제 · 백업 권한 | 백업 컨테이너 |
- 감사 테이블은 월 파티션, 5년이 지난 파티션은 보관 매체로 내보낸 뒤 분리(삭제는 기관 승인 절차).
- Yjs 갱신(`model.ydoc_updates`)은 체크포인트 뒤 정리 — 영역 · 버전마다 체크포인트 + 이후 갱신만 남긴다(01 §13.1).

### 6.2 파일
```
/data/files/
  uploads/<yyyy>/<mm>/<sha256>.xlsx      업로드 원본 (불변, 같은 해시는 한 번만)
  outputs/<yyyy>/<mm>/<export-id>.<ext>  산출물 (DDL · 엑셀 · PDF · PNG)
  quarantine/                             검사 대기 · 거부 파일
  manifest/<yyyy-mm-dd>.jsonl             하루 단위 파일 목록(키 · 크기 · 체크섬 · DB 행 ID) — 복구 대조용
```
- 파일은 **덮어쓰지 않는다**(불변 키). DB 행이 파일 키 · 체크섬을 가진다. 내려받기는 인증된 api 핸들러만(nginx가 직접 노출하지 않음, `X-Accel-Redirect`로 전달).
- 보존: 업로드 원본 1년(결재 문서에 연결된 원본은 문서와 같이 영구) · 산출물 90일(공식 산출물은 영구) — §15 D-4.
- 대안: 기관 S3 호환 저장소(MinIO 등)가 있으면 같은 키 구조로 바꾼다(01 B-3).

## 7. 백업 · 복구

| 대상 | 방식 | 주기 | 보관 | 위치 |
|---|---|---|---|---|
| DB 전체 | pgBackRest 전체 백업 | 주 1회(일요일 새벽) | 4주 | 백업 저장소(암호화) |
| DB 차등 | pgBackRest 차등 | 매일 새벽 | 2주 | 〃 |
| WAL | 연속 보관(archive_command) | 상시(최대 15분 지연 — `archive_timeout=900`) | 4주 | 〃 |
| 파일 | 하루 스냅샷(rsync --link-dest 또는 rclone) + manifest | 매일 새벽 | 30일 + 월말 12개월 | 〃 |
| 설정 · 인증서 | 설치 디렉터리 압축 | 변경 때 | 12개월 | 〃(비밀값은 별도 암호화) |

- **목표**: RPO 15분(WAL) · RTO 4시간(새 장비 복구 포함) — 기관 확인 필요(§15 D-1).
- **DB ↔ 파일 일관성**: 복구 시점 T의 DB를 올린 뒤 manifest로 DB가 가리키는 파일 키를 대조 — 없는 파일은 ‘복구 확인 필요’ 목록(공식 산출물은 확정 스냅샷에서 다시 만들 수 있음).
- **복구 리허설**(분기 1회, 인수 시험 필수):
  1. 새 서버에 설치 묶음 설치 → 2. 시점 T로 DB 복구 → 3. 파일 대조 → 4. **모든 세션 무효화**(sess_rev 일괄 증가) → 5. 큐 재개 · 중복 억제 확인 → 6. 판정 투영 재구축 → 7. 역할별 점검 시나리오(목업 회귀 목록) 통과 → 걸린 시간 기록.
- 감시: 마지막 성공 백업 나이(> 26시간 경보) · WAL 보관 지연(> 30분 경보) · 백업 저장소 여유 공간.

|---|---|---|
| SAML 2.0 | IdP 메타데이터 URL/파일 · 서명 인증서 · 엔티티 ID · 속성(불변 사번 · 이름 · 이메일) | SP 메타데이터 제공(`/api/v1/auth/saml/metadata`), 서명 · 발급자 · 대상 · 시각 검증 |

- IdP 장애 시: ID/PW 병행 모드면 그대로, SSO만 모드면 비상 로그인 절차.

### 11.1 흐름
```

        1) 사전 점검(디스크 · 백업 최신 · 버전 호환)  2) 즉시 백업(차등)
        3) 이미지 로드(docker load) · 해시 확인          4) 정지 공지 → api/collab/worker 정지
        5) migrate 일회 실행(종료 코드 확인)             6) 서비스 기동 · /readyz 대기

```

| DB | 마이그레이션 SQL(정방향) · 되돌릴 수 없는 변경 표시 · 시드(공통표준 판 · 기본 타입 매핑 · DBMS 예약어) |

## 13. 확장 · 이중화 경로

### 13.1 단계
| 단계 | 구성 | 언제 |
|---|---|---|
| S1(기본) | 운영 1대 + 백업 저장소 | 사용자 20명 이하 |
| S2 | 앱 서버 1대(nginx · api · collab · worker) + DB 서버 1대 | 엑셀 · 렌더 부하가 DB 응답에 영향, 또는 기관 정책(DB 분리) |
| S3 | S2 + DB 스트리밍 복제(대기 서버, 수동 전환) | RTO를 1시간 이하로 줄여야 할 때 |
| S4 | 앱 서버 2대(L4 앞단) + DB 주/대기 | 무정지 요구 · 사용자 수십 명 이상 |

### 13.2 collab 확장 원칙
- 업무 영역 · 버전마다 **쓰기 주인은 프로세스 하나**(01 §13.1). 여러 collab을 두면 nginx/L4에서 **문서 이름(영역 · 버전) 해시로 고정 라우팅**하고, 고정 RPC도 같은 규칙으로 해당 프로세스에 보낸다.
- 프로세스가 내려가면 다른 프로세스가 체크포인트 + 갱신 재생으로 이어받는다(고정 상태는 DB가 원본).

### 13.3 DB 이중화
- 스트리밍 복제(동기 또는 비동기 — 기관 RPO에 따라), 전환은 수동 절차 + 점검표(자동 전환은 S4에서 Patroni 검토).

## 17. 검토 반영 (v1.1, Codex [codex-infra-v1](review/codex-infra-v1.md) IN-01 ~ 23)
> 아래가 §1 ~ §16의 해당 부분보다 우선한다. 01 백엔드 구성안 §13과 충돌하면 **01 §13(업무 규칙) → 이 절(운영 정책) → 앞 절** 순으로 적용한다.

### 17.1 복구점 — DB와 파일을 한 묶음으로 (IN-01 · 02 · 03)
- **RPO는 대상별로**: 업무 DB 15분 · 업로드 원본 15분 · 공식 산출물 15분(또는 확정 스냅샷에서 다시 만듦) — 파일 일일 스냅샷만으로는 15분을 못 지키므로, 파일은 **쓰는 즉시 백업 저장소로 복제**(worker의 outbox 작업 `file.replicate`, 실패 재시도 · 경보)하고 일일 스냅샷은 보조로 둔다.
- **검증된 복구점**: 매일 1회 “DB 시점 T + 그때까지 복제 완료된 파일 목록(manifest)”을 묶어 복구점 ID를 발행한다. 복구 인수(I-06)는 이 복구점에서 **확정 문서와 첨부가 모두 열리고 체크섬이 맞아야** 통과.
- **WAL 보관 주체**: `neodb-postgres` 컨테이너 안 pgBackRest `archive-push`가 `archive_command`(실행 파일 · 저장소 설정을 이미지에 포함). `neodb-backup`은 예약(전체 · 차등 · 만료)과 검증(`check` · `info`)만 맡는다. 경보 기준은 “**백업 저장소에서 복구 가능한 마지막 시각**”이 20분 넘게 뒤처지면. 저장소 단절 · 연속 WAL 누락 · 재연결 · 로컬 WAL 적체를 인수 시험에 넣는다.
- **장비 없이 복구**: 기관에 따로 보관할 것 — 설치 묶음 사본 · 구성 · 비밀값(봉인) · **백업 복호화 키** · 복구 권한자 목록. 백업 저장소에는 서버 계정과 분리된 **삭제 제한 사본**(보관 잠금 · 별도 자격). 예비 장비 · DNS 전환 담당을 운영 문서에 지정. 복원 환경은 **메일 · worker 외부 전송을 끈 채** 검증하고, 복구점 이후 보낸 메일 · 처리한 작업을 대조한 뒤 재개한다.

### 17.2 업그레이드 순서 · 롤백 기준 (IN-04)
`neodb.sh upgrade`는 다음 순서로 고정한다.
1. 점검 모드(화면에 ‘점검 중’, 새 로그인 · 쓰기 차단) → 2. 열린 WS의 갱신 내구 저장 확인(collab ACK 대기) · worker 진행 작업 종료 대기 → 3. **복구점 고정**(차등 백업 + 파일 manifest) → 4. 마이그레이션 → 5. 서비스 기동 · `/readyz` → 6. 스모크 점검 → 7. 점검 모드 해제.
- 릴리스 노트에 **롤백 범위**를 적는다: 이전 이미지로 돌아갈 수 있는가(확장 단계만 적용됐으면 가능), 복구점 복원이 필요한가, 재개 뒤 되돌리면 잃는 범위와 승인자.

### 17.3 단절망 설치 묶음 · 서명 (IN-05 · 06 · 16)
- 묶음 명세(`release-manifest.json`): 이미지별 이름 · 다이제스트 · 플랫폼(linux/amd64), Docker Engine · Compose 오프라인 패키지(또는 ‘기관 제공’ 전제 명시), 내부 CA, 글꼴, 시드 버전, 잠금 파일 해시.
- 설치 스크립트는 **원격 pull을 하지 않는다** — 로드된 이미지 다이제스트를 명세와 대조한 뒤에만 기동. 인수: 이미지 캐시가 빈 승인 OS에서 DNS · 인터넷 없이 설치 성공.
- 서명: **서명 검증을 기본 인수 조건**으로(기관이 해시만 쓰면 해시 전달 경로 · 승인자 명기). 순서 = 서명 확인 → 전체 해시 확인 → 그 다음에만 로드 · 실행. 변조 · 미서명 · 다른 플랫폼은 거부. 긴급 취약점 패치의 반입 책임자 · 기한을 운영 문서에.
- **설치 입력서**(`install-inputs.yaml`): 사용자 · 관리 · 서비스 망의 출발/도착 · 포트 · 필수 여부, 내부 DNS · NTP · CA · SMTP · IdP 주소, FQDN/SAN. 설치 전 점검 스크립트가 이 값을 실제로 접속해 확인한다.
- 비밀값: 소비 컨테이너 UID 기준 권한(0400). 교체 순서 — DB 비밀번호(새 역할 비밀번호 → 앱 재시작 → 이전 폐기) · 세션 키(교체 시 전 세션 종료 공지) · collab RPC 비밀(두 개 병행 유예) · TLS(무중단 reload).

### 17.4 세션 · 권한 회수 · 인증 운영 (IN-07 · 08 · 09)
- **판정 기준은 DB 상태**, LISTEN/NOTIFY는 “다시 확인하라” 신호일 뿐. 통지 연결이 끊겼다 이어지면 전부 재검증. 확인 시점: API 모든 요청 · WS 갱신 수신과 구독 · SSE 전달 · worker 실행 · 결과 공개 · 내려받기. `review` 전환 시 비대상 구독을 끊고 확정본으로 돌린다(01 §13.2).
- 로그인 시도 제한은 **DB 공유**(api 2개 사이에서도 같은 카운트), 출처 IP는 `neodb-web`(nginx)가 넣은 `X-Forwarded-For`만 신뢰(신뢰 프록시 = edge 네트워크 주소).
- 최초 관리자: 신규 설치 · 복원 때 `neodb.sh admin-bootstrap`이 일회용 임시 비밀번호를 발급(24시간 · 변경 전용 세션 — 14 §7~8). 운영 시드에 목업 계정이 없음을 인수 점검. 임시 비밀번호 소비 경쟁 · 마지막 Admin 동시 변경을 트랜잭션으로 막는다.
- SSO(도입 시): 발급자 + 불변 ID 매핑 · 사전 등록 계정만 연결 · 중지 계정 거부 · 콜백 검증 · IdP 키 갱신 · 시간 오차 허용(±2분). **SSO만 모드로 바꾸는 저장 트랜잭션 안에서** 비상 로그인 가능한 Admin(사용 중 · ID/PW · 지정)을 확인. 1차 출시가 ID/PW면 SSO 인수는 도입 단계로 미룬다.

### 17.5 감사 · 내려받기 · 업로드 · 공식 산출물 (IN-10 · 11 · 12 · 13)
- 감사 기록 범위표: 업무 성공(같은 트랜잭션) · 실패 · 거부 · 인증 · 내려받기 · 관리자 접근 · 백업/복원 작업. 앱 역할은 `audit`에 INSERT · SELECT만이고 **TRUNCATE · DDL · 소유권 변경도 금지**(인수 시험). 파티션 반출 시 해시 목록으로 무결성 검증, 복원(PITR) 뒤 감사 공백 구간을 대조 기록.
- **내려받기는 api 스트리밍으로 확정**(nginx `X-Accel-Redirect`는 쓰지 않는다 — 파일 볼륨을 nginx에 붙이지 않음). 직전에 현재 권한 · 문서 · 시스템 범위 · 사유를 검사하고 감사, `Cache-Control: no-store`. `quarantine`은 어떤 경로로도 노출하지 않는다.
- 업로드 상태: 받음 → 격리 → 검사 → 사용 가능 / 거부. 한도: 20MB · 10만 행 · 셀 200만 · 압축 해제 200MB · 처리 10분 · 동시 2건. 검사 서비스 단절 시 ‘검사 대기’로 두고 신청을 막는다(공개 금지). 검증 결과의 신청은 검사 완료 + 원본 해시 · 검수 기준 · 사전 세대 고정 뒤에만. 같은 파일 키를 참조하는 보존 대상이 하나라도 있으면 삭제하지 않는다(고아 파일은 주간 정리).
- 공식 산출물: 원본 바이트 + 생성 근거(스냅샷 해시 · 타입 규칙 · 명명 템플릿 · 렌더러 이미지 다이제스트 · 글꼴 버전)를 함께 보존. 같은지 판정은 **내용 기준**(같은 입력 → 같은 해시의 정규화 결과, PDF 메타 시각 제외). 렌더러는 DB · SMTP · 백업 비밀을 받지 않고 네트워크가 막힌 별도 프로세스(같은 컨테이너 안 저권한 사용자 · seccomp · 임시 공간 · 시간 제한)에서 돈다.

### 17.6 공동 편집 고정 · 작업 재시도 (IN-14 · 15)
- 고정은 **영역 · 버전별 고정 토큰**(DB에 내구 상태 · 만료 10분)으로. 확정 신청 재시도는 같은 멱등 키 → 같은 결과. 커밋 여부를 모르면 토큰으로 조회해 판정. 고정이 만료되면 자동 해제 · 감사. DB에 내구 저장된 순번만 ACK. 소유권을 잃었거나 `review`가 된 문서의 쓰기는 거부.
- I-11 시험 항목 추가: 커밋 전후 프로세스 종료 · RPC 응답 유실 · 늦은 해제 · 재접속 · 체크포인트 경계.
- worker 작업 종류별 표(구현 산출물): 동시성 · 우선순위 · 기한 · 멱등 키 · 시도 제한(지수 대기) · 재처리 권한. 기한 만료(사용 기한 · 확인 요청)는 정기 작업에 더해 **요청 때도 검사**. 투영은 원본 순번 · 세대 비교 후 적용, 전체 재구축 명령 제공. worker 재시작 뒤 메일 · 공개 같은 부수 효과는 멱등 키로 한 번만.

### 17.7 관측 · 사양 · 용량 · 성능 기준 (IN-17 · 18 · 19 · 20)
- 관측이 같은 서버에만 있으면 서버가 죽을 때 같이 죽는다 → **서버 밖 감시 2개를 기본**: 443 접속 확인 · 백업 성공 신호(기관 모니터링 또는 백업 서버에서). SMTP 장애 때 쓸 두 번째 통보 경로(기관 지정). 경보 9종은 조건 · 지속 시간 · 담당 · 해제 기준을 표로(I-07). `/metrics` · Grafana는 관리망에서만.
- **8 vCPU · 32GB는 시작 사양**이다. 산정 표(사용자 20 · 활성 문서 · 업로드 · 렌더 동시성 · 연결 풀 · OS · 캐시 · 백업 I/O)를 구현 B0에서 실측으로 채우고, cgroup 제한 상태에서 CPU 제한 · 메모리(RSS/OOM) · 디스크 지연과 응답을 함께 본다.
- 용량은 **저 · 기준 · 고 3안 산식**으로(시스템 × 영역 × 연간 확정 버전 × 평균/상위 크기, 감사 이벤트/일 × 행 크기, 업로드/일 × 평균 크기 × 보존일) + 색인 · 여유 · WAL 적체 · 이미지 · 설치 묶음 · 복원 작업 공간. §12 표는 기준안의 대략값이다.
- **운영 SLO와 CI 회귀 기준을 따로**: CI는 고정 픽스처로 상대 비교(20% 악화 실패), 운영 인수는 기관 PC · 망 · 운영 사양에서 20명 · 문서당 2~5명 · 엑셀 10만 행 · 공식 렌더 · 백업이 동시에 돌 때 §1의 목표.

### 17.8 확장 · 이중화 조건 (IN-21 · 22)
- S1은 **erd-collab 1개 고정**. 확장(S4) 전에: 문서 이름을 아는 계층(nginx `hash $collab_doc consistent` 또는 배정표)에서 WS와 고정 RPC가 **같은 배정**을 쓰고, 소유권 세대가 바뀌면 이전 주인의 쓰기를 막고 새 주인은 체크포인트 재생 뒤에 연결을 받는다. S4에는 공용 파일 저장소 · SSE 재연결 재전달 · 공유 인증 키가 함께 필요.
- S3(DB 대기): 전환 승인자 · 구 주 노드 격리 · 승격 · 접속 주소 전환 · WAL 보관 · 재합류 절차와 노드별 장애 훈련. 비동기 복제면 손실 허용(RPO)을, 동기 복제면 단절 시 쓰기 정책을 명기.
