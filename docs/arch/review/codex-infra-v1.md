# NeoDB 인프라 설계 v1 검토

검토 대상은 [인프라 설계 03](../03-infrastructure-design-v1.md)이다. [백엔드 구성안 01](../01-backend-architecture-v1.md)의 §13 우선 규칙과 [UX 입력 00](../../ux/00-inputs.md), [계정·인증 14](../../ux/14-user-account-auth.md), [RBAC 29](../../ux/29-rbac-r2.md), [성능 스파이크 23](../../spec/da-feature-spec/23-performance-spike.md)을 대조했다. 아래에서 번호로 지칭하는 문서는 이 다섯 문서를 뜻한다.

일괄 구현 전에 복구 목표·복구점, 오프라인 설치 목록, 세션 회수, 공동 편집 고정의 계약을 확정해야 한다. **치명**은 데이터 손실 또는 무권한 접근을 허용할 수 있어 구현 기준 확정이 필요한 항목, **상**은 설치·운영·인수에 실패하거나 구현이 갈릴 수 있는 항목, **중**은 운영 기준을 구체화할 항목이다.

## IN-01 · DB와 파일의 복구점 불일치

- **심각도** 치명
- **근거** 03 §0·§7은 RPO 15분을 제시하지만 파일은 하루 한 번 복제한다. DB를 T로 복구하면 최근 파일을 가리키는 행은 살아 있어도 원본 바이트는 약 하루치까지 없을 수 있다. manifest 대조는 누락을 알려줄 뿐이고, 재렌더링은 반입 원본을 되살리지 못한다.
- **고칠 방법** RPO를 DB·원본·공식 산출물에 각각 명기한다. 업무 전체가 15분이면 파일 복제를 그 예산 안에 포함하고, DB 시점과 복제 완료된 파일 목록을 묶어 검증된 복구점을 발행한다. RPO 범위 내에서 복원한 확정 문서와 그 첨부가 모두 열리고 체크섬이 맞아야 I-06을 통과하도록 한다.

## IN-02 · WAL 보관 실행 주체와 경보가 복구 목표를 보장하지 못함

- **심각도** 상
- **근거** 03 §5·§7은 pgBackRest를 예약 백업 컨테이너에만 명시하고, PostgreSQL이 상시 실행할 archive_command와 저장소까지의 경로는 정하지 않았다. archive_timeout 900초는 보관 완료 시간의 상한으로 쓸 수 없고, 30분 경보는 15분 RPO 위반 뒤에도 울리지 않을 수 있다. 01 §8의 일일 전체 백업과 03의 주간 전체 백업도 다르다.
- **고칠 방법** DB 컨테이너에서 동작하는 보관 명령과 실행 파일, 저장소 연결 방식, 예약 실행 주체, 백업별 보존·만료와 복구 가능 시작점을 명시하고 01과 일치시킨다. 마지막 외부 복구 가능 시각으로 경보를 잡고, 저장소 단절·연속 WAL 누락·재연결과 로컬 WAL 증가를 인수 시험에 넣는다.

## IN-03 · 장애 장비 없이 복구할 수 있는 경로가 불완전함

- **심각도** 상
- **근거** 03 §7의 설정 백업은 변경 시 수행하지만, 원본 장비가 사라졌을 때 설치 묶음·백업 암호화 키·인증서·저장소 자격증명을 어디서 어떤 권한으로 확보하는지 없다. 서버에서 삭제 가능한 NAS 사본은 장애 영역 분리만으로 보존을 보장하기 어렵다.
- **고칠 방법** 기관에 보관할 구성·비밀·복호화 키·릴리스 목록과 복구 권한자, 서버 자격증명과 분리된 삭제 제한 사본, 예비 장비와 DNS 복구 담당을 정한다. 복원 환경에서 SMTP와 워커를 차단한 상태로 파일·세션·DB를 검증하고, 외부 전송을 재개하기 전에 복구점 이후 처리된 메일·작업을 대조해 재실행 여부를 확정한다. 장비 인수부터 사용자 재개까지 RTO에 포함한다.

## IN-04 · 업그레이드 중 쓰기와 롤백 기준 시점

- **심각도** 치명
- **근거** 03 §11.1에서 즉시 백업 뒤에 서비스 중지가 온다. 백업 후 접수된 승인·편집·파일을 되돌릴 때 어느 시점까지 보존할지 없다. §11.2의 확장→이전→축소와 01 §8의 되돌림 스크립트도 버전별 롤백 범위를 정하지 않는다.
- **고칠 방법** 점검 모드 → 신규 쓰기·연결 차단 → WS 갱신 내구 저장·워커 종료 확인 → DB 복구점과 파일 목록 고정 → 마이그레이션 → 점검 → 트래픽 재개 순서를 명시한다. 릴리스마다 이전 이미지로 복귀 가능한 범위, 복원이 필요한 단계, 공개 재개 뒤 데이터 되돌림 승인과 손실 범위를 기록한다. 마이그레이션 단일 실행과 실패 재시도 조건도 정한다.

## IN-05 · 단절망 설치 묶음에 필수 의존성이 빠짐

- **심각도** 상
- **근거** 03 §5에는 PostgreSQL 이미지가 있으나 §11.2·I-04 목록에는 빠져 있다. §10의 관측 프로필을 선택하면 그 이미지도 필요하다. Docker·Compose 자체를 어디서 설치하는지와 01 §13.7의 잠금 파일·기관 CA를 어떻게 전달하는지도 불명확하다.
- **고칠 방법** 필수·선택 프로필별 이미지와 플랫폼, 오프라인 엔진·Compose 설치 패키지 또는 기관 제공 전제, 신뢰 CA·폰트·시드 버전·잠금 파일을 배포 명세로 만든다. 설치 스크립트가 사전 로드된 이미지의 식별자를 검증하고 원격 pull 없이 기동하도록 한다. 빈 이미지 캐시의 승인된 OS에서 DNS·인터넷 접근 없이 설치와 재설치를 시험한다.

## IN-06 · 반입 서명 정책과 검증 순서가 충돌함

- **심각도** 상
- **근거** 03 §11.1과 I-08에는 서명이 포함되나 §11.2·D-8은 기관 요구에 맡긴다. 설치 흐름은 이미지 로드와 해시 확인을 한 단계로 놓아 검증 전에 설치 도구나 이미지를 신뢰해도 되는지 불명확하다.
- **고칠 방법** 서명 의무 여부, 기관이 별도 경로로 배포하는 검증 키, 검증 도구·순서를 고정한다. 묶음 서명과 전체 내용의 해시를 확인한 뒤에만 실행·로드하게 한다. 변조·미서명·오류 플랫폼 거부를 인수 기준으로 둔다. 분기 패치 사이에 긴급 취약점이 발견됐을 때 반입 책임자와 기한, I-04 고위험 항목의 판정 기준도 정한다.

## IN-07 · 세션 회수와 열린 연결의 권한 재검사

- **심각도** 치명
- **근거** 03 §8은 sess_rev 통지만 적는다. 01 §13.2·§13.6과 14 §8은 열린 WS·SSE·백그라운드 작업까지 회수 이후의 권한을 적용한다. 29 R-09~12는 사업 종료·기한 만료·범위 축소로도 접근을 제한한다. 통지 단절 중 권한 캐시를 유지하면 정보가 계속 나갈 수 있다.
- **고칠 방법** DB 상태를 판정 기준으로 두고 통지는 갱신 신호로 사용한다. 통지 재연결 시 재검증하며, API 읽기·쓰기, WS 수신 및 구독, SSE 전달, 워커 실행·공개·다운로드 시점의 확인을 명기한다. review 전환 시 비대상 구독을 끊고 확정본으로 돌린다. API 두 인스턴스에서 권한 회수, 통지 단절, 대기 중 작업, 열린 연결을 조합해 시험한다.

## IN-08 · 인증 운영과 최초 관리자 계약

- **심각도** 상
- **근거** 03 §4·§8은 IP 제한·잠금·세션만 요약한다. 14 §7~8 및 01 §13.6의 최초 관리자, 변경 전용 세션, 원자적 임시 비밀번호 소비, 실패 응답 균질화와 마지막 관리자 보호의 운영 인수 기준이 없다. 03 §8의 개인정보 항목도 14 §2의 회사·부서·이름·ID를 누락한다.
- **고칠 방법** 14 §7~8을 적용 조항으로 연결하고 신규 설치와 복원 시 일회용 관리자 발급·복구 경로를 사양화한다. 계정 시도 제한을 인스턴스 간 공유하고 프록시 뒤 출처 IP의 신뢰 범위를 지정한다. 운영 시드에 목업 계정이 없는지, 임시 비밀번호 소비 경쟁과 마지막 관리자 동시 변경에 안전한지 검증한다. 프로필·감사에 저장하는 개인정보와 열람 주체도 명시한다.

## IN-09 · SSO 선택 시 계정 연결과 비상 로그인 부족

- **심각도** 상
- **근거** 03 §9의 OIDC는 발급자와 sub를 쓰지만 SAML의 계정 연결 키, 인증 모드 전환 조건, 비상 로그인 추가 인증·사유·다른 관리자 통지는 비어 있다. 14 §7~8은 이를 요구한다. 03 §4의 자기 출처 CSP·SameSite 정책이 실제 IdP 콜백과 맞는지도 확인해야 한다.
- **고칠 방법** 두 프로토콜의 기관별 발급자와 불변 ID 매핑, 사전 등록·중지 계정 처리, 콜백 검증, 키 갱신과 내부망 시간 오차를 설정 계약으로 둔다. SSO만 모드 전환 시 정상 비상 경로를 트랜잭션에서 확인한다. 지정 개인 관리자, 허용 경로, 추가 인증·사유·경보를 시험한다. 출시에서 SSO를 미루면 해당 인수 단계도 명기한다.

## IN-10 · 감사의 기록 범위와 보존 책임

- **심각도** 상
- **근거** 03 §0은 INSERT만, §6.1은 INSERT·SELECT를 명시한다. I-03은 UPDATE·DELETE 거부만 확인한다. 01 §13.5~6, 14 §8, 29 R-12·14·15는 불변 실행자·대리·사유·결과·관리/업무 구분, 감리 범위, 내보내기 감사를 요구한다. §8의 같은 트랜잭션 문구만 따르면 실패 로그인과 롤백된 변경 시도의 기록이 사라질 수 있다.
- **고칠 방법** 업무 성공 감사와 실패·인증·다운로드 이벤트의 기록 시점, 허용 읽기 경로와 범위, 관리자·백업 접근의 감시를 표로 정한다. 앱 역할의 TRUNCATE·DDL·소유권 변경 금지까지 검증한다. 감사 5년과 접속·권한 이력의 보존·점검 책임, 파티션 반출 후 무결성 검증과 열람 절차, PITR 뒤 감사 공백 대조를 명기한다.

## IN-11 · 다운로드 권한과 프록시의 파일 볼륨 모순

- **심각도** 상
- **근거** 03 §6.2는 X-Accel-Redirect를 쓰지만 §5의 nginx에는 파일 볼륨이 없다. 다운로드를 인증만으로 구현하면 29 R-14의 시스템 범위·out.export·개인정보 사유와 조회만 계정의 내려받기 금지를 놓칠 수 있다.
- **고칠 방법** API 스트리밍 또는 nginx 내부 경로와 읽기 전용 공개용 볼륨 중 하나를 확정한다. 다운로드 직전에 현재 문서·시스템 범위와 권한·사유를 검사하고 감사한다. 격리 경로의 외부 노출 금지, 캐시 정책, 직접 주소·권한 회수·범위 밖·조회만 계정의 거부를 I-10에 추가한다.

## IN-12 · 업로드 검사와 파일 수명주기의 경계

- **심각도** 상
- **근거** 03 §6.2·§8은 불변 키와 격리·검사를 제시하지만 파일 이동과 DB 참조 사이의 장애, 공유 해시의 삭제, 검사 장애 시 처리, 격리 용량을 정하지 않는다. 23 §6의 20MB·10만 행은 둘 다 상한이며 01 §13.7은 재검증 근거를 입력에 묶는다.
- **고칠 방법** 업로드 상태, 검사 주체, 바이트·행·셀·압축 해제·시간·동시성 한도, 실패·타임아웃·검사 서비스 단절의 결과를 확정한다. 검사 완료와 원본 해시·검수 기준·사전 세대 등의 고정 이후에만 검증 결과의 신청을 허용한다. 보존 대상 참조가 하나라도 남으면 같은 파일을 삭제하지 않고, 고아 파일과 격리 파일은 별도 규칙으로 정리한다.

## IN-13 · 공식 산출물의 재생성 및 렌더러 격리

- **심각도** 상
- **근거** 03 §7은 공식 산출물을 다시 만들 수 있다고 하지만 01 §13.7이 요구하는 스냅샷 해시·타입 규칙·명명 템플릿·렌더러 버전과 그 보존은 지정하지 않았다. §5·§8은 큐·DB와 연결된 worker 안에서 Chromium의 네트워크를 어떻게 차단하는지도 결정하지 않았다.
- **고칠 방법** 공식본의 원본 바이트와 생성 근거, 재생성에 필요한 이미지·글꼴·입력 버전을 보존한다. 일치 판정이 바이트 단위인지 내용 단위인지 정의한다. 렌더러에 DB·SMTP·백업 비밀이나 임의 네트워크 접근을 주지 않는 실행 경계와 샌드박스·임시 공간·시간 제한을 지정하고 그 구성에서 한글 렌더를 검증한다.

## IN-14 · 공동 편집 고정의 중간 실패와 소유권

- **심각도** 치명
- **근거** 03 §2·§13.2·I-11은 단일 쓰기 주인·고정·실패 해제를 말한다. 01 §13.1의 내구 ACK·고정·스냅샷/결재/상태/감사 원자 커밋 사이에서 RPC 응답 유실, API 중단, 늦은 해제가 발생할 때 어느 상태가 우선인지 빠져 있다.
- **고칠 방법** 영역·버전별 고정 토큰과 내구 상태, 재시도·중복 제출 키, 커밋 여부 확인과 고정 만료·해제 조건을 정한다. DB에 내구 저장된 순번만 ACK하고, 소유권을 잃거나 review로 전환된 문서의 쓰기는 막는다. I-11의 반복 횟수에 더해 커밋 전후 프로세스 종료, 응답 유실, 늦은 해제, 재접속, 체크포인트 경계에서 데이터·권한 불변식을 확인한다.

## IN-15 · 워커 재시도와 업무 처리 진행 보장

- **심각도** 상
- **근거** 03 §2·§7·§10의 한 worker는 엑셀·렌더·메일·만료·투영을 맡는다. 01 §13.3·§13.5는 stale 투영 덮어쓰기 금지와 outbox 중복 억제·실패 목록을 요구한다. 공용 동시성만 두면 장시간 작업에 계정 만료 처리와 알림이 밀릴 수 있다.
- **고칠 방법** 작업 종류별 동시성·우선순위·기한·멱등 키·시도 제한·재처리 권한을 정한다. 기한 만료는 요청 시에도 검사한다. 투영 적용 전 원본 순번·세대를 비교하고 전체 재구축 명령을 등록한다. 엑셀·렌더 중 만료 및 결재 알림 진행, worker 재시작 후 부수 효과의 중복 억제를 검증한다.

## IN-16 · 망 연결과 비밀값의 설치 계약

- **심각도** 상
- **근거** 03 §4는 443 전용과 선택 80, 관리망 SSH, 서비스 연결을 혼용한다. DNS·모니터링 수집·백업 상세 방향과 컨테이너별 송신 통제가 없다. §8의 0400과 비루트 실행을 함께 만족할 UID·GID 및 교체 순서도 빠져 있다.
- **고칠 방법** 사용자·관리·서비스 망의 출발/도착·프로토콜·포트·필수 여부·장애 영향을 설치 입력으로 정한다. 내부 DNS·NTP·CA·SMTP 신뢰, Docker 포트 게시와 호스트 방화벽을 검증한다. 비밀값은 소비자 UID 기준으로 권한을 설정하고 DB·세션·내부 RPC·인증서 각각의 교체 순서와 재시작·유예 정책을 명시한다. 비루트·읽기 전용 상태에서 PID·캐시·임시 파일을 쓸 경로도 고정한다.

## IN-17 · 관측이 장애 대상과 같은 서버에 의존함

- **심각도** 상
- **근거** 03 §5·§10의 기본 관측은 같은 호스트와 기관 SMTP에 의존한다. 호스트나 메일 릴레이가 죽으면 가장 중요한 경보가 전달되지 않을 수 있다. worker·backup 등의 상태 확인이 서로 다른데 I-01은 모든 서비스의 /readyz를 요구한다.
- **고칠 방법** 서비스별 생존·준비·최근 작업 성공의 판정과 운영 재시작 책임을 정한다. 외부에서 443 접근과 백업 성공 신호를 감시하고, SMTP 장애 시 사용할 기관 수신 경로를 지정한다. I-07은 아홉 경보의 조건·지속 시간·담당·해제 기준과 호스트 정지 시험까지 연결한다. metrics·Grafana는 관리 경로로 제한하고 로그의 보존·회전·SIEM 전달 방식을 하나로 정한다.

## IN-18 · CPU·메모리·I/O 산정 근거 부족

- **심각도** 상
- **근거** 03 §3·§5의 명시 CPU 상한 합은 일반 서비스 8.5, 백업 실행 시 9.5 vCPU다. 초과 할당은 가능하지만 8 vCPU의 여유 근거가 없다. DB 12GB 제한 안에서 8GB shared_buffers와 연산별 work_mem·연결·유지보수 메모리가 경합한다. 4 vCPU·16GB 스테이징에 운영과 같은 메모리 제한을 둘 경우 명시 항목의 한도 합만 20.25GB(백업 제외)다. 23의 단일 PC 시험은 운영 혼합 부하 근거가 아니다.
- **고칠 방법** 8 vCPU·32GB는 검증 전 시작 사양으로 표시한다. 동시 사용자·활성 문서/유지 시간·업로드/렌더 동시성·커넥션 풀·OS 및 캐시·백업 I/O를 표로 산정한다. 스테이징의 실행 자원과 운영 사양 인수 환경을 명기하고, B0에서 cgroup 제한 상태의 CPU throttling·RSS/OOM·디스크 지연과 응답 시간을 함께 확인한다.

## IN-19 · 5년 용량과 백업 저장소의 산식 누락

- **심각도** 상
- **근거** 03 §12의 DB 항목 합계는 1년 11GB, 5년 38GB다. 색인 포함 15/60GB로 늘어나는 산식이 없다. 23 §2의 20만 건·색인 76MB는 검색 시험 데이터의 크기다. 영구 스냅샷·산출물 증가율, batch_rows 정리 기한, WRITE/WAL·DB 임시공간·업그레이드 두 세대 용량이 빠져 있다. 1~1.5TB 추정은 복제 방식과 파일 변경량에 따라 크게 달라진다.
- **고칠 방법** 시스템×영역×연간 확정 버전×평균/상위 크기, 감사 이벤트/일×행 크기, 업로드/일×평균 크기×보존일로 저·기준·고 부하를 계산한다. 색인·여유 공간·WAL 적체·이미지와 설치 묶음·복원 작업 공간을 별도 항목으로 둔다. 백업은 전체·차등·WAL·파일의 실제 보관 방법과 삭제율로 합산하고 모니터링 측정치로 갱신한다.

## IN-20 · 실측 수치와 운영 성능·회귀 기준 혼용

- **심각도** 상
- **근거** 03 §1·I-12의 300/500/200ms와 3초는 23 §6의 확정 수치가 아니다. 23 §2는 검색 질의, §3은 첫 렌더, §4는 간이 엑셀 검사, §5는 동일 PC 동기화를 쟀다. §4의 10만 행은 표 4.1MB와 해석 2.4MB가 다르다. I-12의 20% 악화 판단은 비교 통계·환경·샘플과 합격 기준이 없다.
- **고칠 방법** 운영 SLO와 CI 회귀 기준을 각각 정의한다. 23 §6의 2자 이하 접두 검색·총건수 상한·깊은 페이지 및 300개 권장값을 반영한다. 고정 픽스처·규격으로 반복 측정하고 운영 인수 때는 기관 PC·망과 운영 사양에서 20명, 문서당 2~5명, 엑셀 10만 행 실검증·공식 렌더·백업 동시 상황을 재현한다. WS 상대 전달과 내구 ACK, 화면 열기 시작·종료, 엑셀 처리 시간과 다른 사용자 p95를 각각 정의한다.

## IN-21 · 앱 확장 시 파일·라우팅·공동 편집 소유권

- **심각도** 상
- **근거** 03 §13.2의 문서 이름 해시는 WS 연결을 맺을 때 이름이 경로에 있는지, 연결 하나가 여러 문서를 담당하는지에 따라 적용 가능성이 달라진다. L4에서 문서 이름을 본다는 설명과 §2의 로컬 파일 볼륨으로는 S4의 라우팅·공용 파일 접근을 재현할 수 없다. 노드 재배치 시 양쪽 쓰기 주인이 함께 살아날 수 있다.
- **고칠 방법** S1의 collab 한 인스턴스 운영 조건을 고정하고, 확장 전에 이름을 아는 계층에서 WS와 RPC가 같은 배정표를 쓰게 한다. 소유권 세대 변경 뒤 이전 소유자의 내구 쓰기를 막고 새 소유자가 체크포인트를 재생한 뒤 연결을 받는 시험을 둔다. S4는 공용 파일 저장소 및 복구점, SSE 재연결·재전달, 공유 인증 키와 세션, L4 헬스체크가 마련된 뒤 적용한다.

## IN-22 · DB 대기 서버와 가용성 약속

- **심각도** 상
- **근거** 03 §13.3은 동기/비동기 복제와 수동 전환만 정한다. 기본 주 노드 차단과 재합류, 앱·워커의 DB 주소 전환, 재접속 후 세션과 큐, 복제 지연의 허용 손실이 빠져 있다. §13.1의 S3 RTO 1시간과 S4 무정지는 앱·파일·마이그레이션까지 확인할 기준이 없다.
- **고칠 방법** S2의 DB 연결 신뢰·방화벽부터 정한다. S3는 전환 승인·구 주 노드 격리·승격·엔드포인트 전환·WAL 보관 및 재합류를 절차화하고 노드별 장애를 훈련한다. 비동기 복제 지연에 따른 손실 목표 또는 동기 복제 단절 시 쓰기 정책을 명기한다. S4의 무정지 적용 범위와 계획 정지 허용 범위는 별도로 검증한다.

## IN-23 · 설계 우선순위와 단계별 인수 기준

- **심각도** 상
- **근거** 03 §14는 01 §13.9를 따르지만 I-01~12는 대부분 인수 시점이 없다. 01 §13.9는 B1에서 신청·결재부터 DDL까지 이어가고 B3에서 메일을 다룬다. 00 §4-8은 메일을 결재 알림 범위로 정한다. 29의 최종 승인·확인·외주 범위 규칙은 00의 초기 제품 결정을 보완한다.
- **고칠 방법** 01 §13 우선 규칙, 29의 개정 요구, 03에서 확정한 운영 정책을 서로 링크하고 충돌 시 적용 조항을 적는다. I-01~12에 B0 위험 제거, B1 W1 수직 완주, B3 연동, B5 운영 승인 중 해당 시점을 지정한다. B1의 결재 메일 포함 여부와 B3 기관 SMTP 인수 범위를 명시하고, 수신자 범위·TLS·실패 재시도·메일에 넣을 데이터·앱 알림 유지 조건을 확정한다.
