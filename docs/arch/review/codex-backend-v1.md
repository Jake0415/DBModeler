# NeoDB 백엔드 1차 구성안 검토

검토 대상은 [백엔드 구성안 v1](../01-backend-architecture-v1.md)이다. 업무 규칙은 목업 공용 상태 계층과 UX 합의를 기준으로 대조했다. 상은 구현 또는 출시 전에 닫아야 할 정합성·보안·출시 범위 문제, 중은 기술 결정이나 운영 절차에 보완할 문제다. 성능 수치는 기존 스파이크의 측정 범위에서 판단했다.

## BA-01. 공동 편집 저장과 제출본 고정을 한 순서로 처리해야 한다

- **심각도** 상
- **근거** 구성안 §5.3은 collab가 2초 디바운스로 저장하는 동안 별도 API 프로세스가 최신 Y.Doc을 읽고, 제출 뒤 연결을 조회 전용으로 바꾼다. DB에서 읽으면 아직 저장되지 않은 변경이 빠지고, 메모리에서 읽어도 조회 전용 전환 전에 수락한 변경이 제출본과 갈라질 수 있다. UX 03 §13.1은 서버가 쓰기를 고정한 시점과 내용 해시를 요구한다. [ERD 편집기](../../ux/03-erd-editor.md#131-재확인-2026-11-18--sws-비교-후에도-w1-실시간-유지)
- **고칠 방법** 버전별 갱신을 collab가 직렬화하고 쓰기 수락 경계를 먼저 고정한다. 수락분을 내구 저장한 뒤 서버 리비전·고정 시각·정규화한 제출본 해시를 확정한다. 제출 검증, 불변 스냅샷, 결재 문서, review 전이는 일관된 트랜잭션으로 커밋한다. 실패·재시작 때 DB 상태로 고정 여부를 복구하고, 저장 ACK 이전 변경은 UI에서 미저장으로 표시한다. 동시 편집·중복 제출·커밋 직전 장애·늦은 재접속을 통합 검증한다.

## BA-02. 읽기 전용 연결에도 결재 중 열람 제한을 적용해야 한다

- **심각도** 상
- **근거** §5.3의 readOnly 전환은 쓰기 제한이다. 그대로 두면 연결된 조회자가 검토본 동기화를 계속 받을 수 있다. 목업의 `canUserSeeDoc`과 `areaView`는 결재 중 신청자·결재선만 허용하고 그 밖의 영역 조회는 마지막 확정본으로 돌린다. 제출본 직접 주소는 열람을 제한한다. §6의 일괄 403 정책도 숨겨진 문서의 존재를 추론할 여지를 남긴다. [app.js](../../ux/mockups/assets/app.js#L1231) · [RBAC §7](../../ux/15-rbac.md#7-결재-중-열람-범위-확정-2026-11-19)
- **고칠 방법** 승인 문서와 모델 버전 접근 결정에 세션 유효성, 대상 범위, 검토 상태를 함께 입력한다. 조회 전용 권한과 검토본 열람 권한을 독립적으로 평가한다. 전환 때 비인가 WS 구독을 종료하고 영역 화면에는 허용된 확정본을 제공한다. 직접 주소·검색·집계·참조 미리보기·SSE·산출물에도 같은 필터를 적용한다. 존재를 숨기는 대상은 직접 조회의 상태 코드와 응답을 일관되게 정한다.

## BA-03. Yjs 저장 계약과 업무 불변식을 명시해야 한다

- **심각도** 상
- **근거** §4.2의 update 병합과 §5.3의 저장 훅에는 순번, 복구 기준점, 문서 스키마 버전, 쓰기 검증이 없다. 수렴하더라도 삭제된 엔터티를 가리키는 관계나 수정 가능한 참조 사본이 남을 수 있다. `model-doc`과 관계형 테이블에 보기·메모의 소유권이 겹친다. [ERD 편집기 §4·§13](../../ux/03-erd-editor.md) · [성능 스파이크 §5·§7](../../spec/da-feature-spec/23-performance-spike.md)
- **고칠 방법** 버전 키별 유일한 쓰기 소유자, 증가하는 갱신 순번, 체크포인트 이후 재생, 검증된 체크포인트 이전분 정리 기준을 문서화한다. 구조·참조 무결성은 갱신 적용 전에 검증하고 표준 미준수는 편집 중 표시하되 제출에서 차단한다. 크기·갱신량을 제한하고 버전 전환 후 오래된 오프라인 업데이트는 재동기화나 사용자 복구 절차로 보낸다. 공유 보기·메모와 개인 설정의 저장 주체를 각각 지정한다. 가져오기·일괄 변경·되돌리기도 같은 쓰기 경로로 통과시킨다.

## BA-04. 투영이 어떤 모델과 규칙을 반영하는지 추적해야 한다

- **심각도** 상
- **근거** §4.2·§5.3·§12는 저장 훅 기반 비동기 투영을 정의한다. 모델 편집이 없어도 사전·타입·정책 변경으로 판정이 달라진다. 용어 ID만으로는 단어·도메인·코드 변경 영향이나 삭제 제한을 일관되게 판정하기 어렵다. [메타데이터 설계 MD-11·MD-24·MD-50~54](../../spec/da-feature-spec/30-metadata-design.md) · [SWS 비교 §6](../../spec/da-feature-spec/22-sws-comparison.md#6-반영-제안--결정-2026-11-18-10개-모두-채택-7은-인라인은-추가이름만)
- **고칠 방법** 투영에 영역·버전·원본 리비전과 사전·타입·정책 세대를 기록한다. 변경 이벤트를 원본 저장과 함께 기록하고, 오래된 작업이 새 결과를 덮지 못하도록 한다. 참조 서명과 역참조 색인으로 영향 범위만 재판정하고 삭제분도 반영한다. 지연 상태와 재구축 절차를 마련한다. 승인·공식 산출·사전 삭제 같은 업무 결정은 신선도가 보장된 데이터나 원본 검증을 사용한다.

## BA-05. 결재 상태 전이와 결재선의 고정 범위를 확정해야 한다

- **심각도** 상
- **근거** §5.2 그림은 DA 단계 회수만 명시한다. MD-21은 진행 중 본인 회수를 요구한다. 반려·회수 후 모델 편집 재개, 재신청 시 새 제출본, 실패 재검사 이력, 담당자 공백의 복구 규칙도 빠져 있다. 또한 목업 `lineFor`는 영역 키로 최종 승인 설정을 읽지만 UX 00의 정책 단위는 시스템이다. 과거 15 §6의 자기 승인 예시보다 29의 독립 최종 승인 규칙이 최신이다. [app.js](../../ux/mockups/assets/app.js#L1119) · [입력 정리 §4](../../ux/00-inputs.md#4-결재) · [RBAC 2차](../../ux/29-rbac-r2.md) · [메타데이터 설계 MD-20~27](../../spec/da-feature-spec/30-metadata-design.md)
- **고칠 방법** 유형별로 단계·행위자·필수 사유·실패 결과·모델/묶음 부수 효과를 전이표로 정의한다. 승인과 회수의 경쟁은 같은 문서 리비전 검사로 처리한다. 실패 재검사는 승인 반영 없이 이력을 보존한다. 결재선에는 신청 당시 적용한 단계·시스템·정책과 배정 정보를 보존하고, 실제 자격은 실행 때 재평가한다. 자기 승인에는 사유와 독립 최종 승인을 강제한다. 최종 단계에서 신청자와 DA 실행자·위임 원담당자를 제외하고 유효한 결재 쌍을 확인한다. 위임의 내부 계정·동일 역할·유효 기간·범위와 결재 공백의 재배정 절차를 명시한다. 영역 키와 시스템 정책 불일치는 시나리오로 확인해 기준을 확정한다.

## BA-06. 사전 승인에서 항목별 충돌과 반영을 함께 보장해야 한다

- **심각도** 상
- **근거** §4.2·§5.1의 문서 key와 단계 비교는 서로 다른 바구니나 파일에 들어간 같은 사전 항목의 경합까지 막지 못한다. 목업 `openItems`는 부분 반려된 항목을 진행 중 충돌에서 제외한다. MD-10은 승인 전 기존본 유지와 대상 버전 변경 시 재조회를 요구한다. [app.js](../../ux/mockups/assets/app.js#L948) · [메타데이터 설계 MD-10·MD-20·MD-23~24](../../spec/da-feature-spec/30-metadata-design.md)
- **고칠 방법** 수정은 불변 항목 ID와 기대 버전, 신규는 종류·사전 세트·정규화 식별 키를 기준으로 진행 중 예약과 도메인 고유 제약을 둔다. 대상 및 참조 변경을 확인하며 재검사·반영·이력·예약 해제·결재 완료를 같은 트랜잭션에서 커밋한다. 부분 반려 시 해당 항목만 해제하고 의존 항목을 다시 검사한다. §6의 멱등 키는 실행자·명령·요청 해시·결과에 연결한다. 공표 차수와 항목 버전은 별도로 관리한다.

## BA-07. 모듈 간 트랜잭션과 백그라운드 작업의 책임을 정해야 한다

- **심각도** 중
- **근거** §3은 감사·알림을 outbox 소비로 설명하고 §7은 감사를 쓰기 트랜잭션에 직접 넣는다. 모델 제출, 승인 반영, 사업 종료는 여러 모듈의 쓰기를 묶는다. §4.2의 모델 스냅샷과 결재 스냅샷도 같은 내용을 두 번 소유할 수 있다.
- **고칠 방법** 유스케이스별 트랜잭션 소유자와 모듈의 공개 명령을 정하고 공통 트랜잭션을 넘긴다. 감사 이벤트는 업무 변경과 같이 커밋하고 알림·투영·파일 처리는 outbox로 전달한다. 소비자는 업무 키로 재시도와 중복을 처리하고 실패 상태를 운영자가 확인할 수 있게 한다. 모델 모듈이 불변 스냅샷을 소유하고 결재 문서는 ID·해시로 참조한다. 규칙 입력은 명시적인 서버 시각·대상·계정·정책으로 구성하고 범위가 필요한 서버 호출은 컨텍스트 없이는 거절한다. 목업 `canUser`의 컨텍스트 생략 허용은 화면 표시 용도로 한정한다. ## BA-08. 세션 종료와 관리 변경 승인을 실제 실행 경계에서 강제해야 한다

- **심각도** 상
- **근거** §7의 `sess_rev`와 §5.3의 접속 시 인증만으로 열린 WS·SSE가 즉시 종료된다는 보장이 없다. 임시 비밀번호는 §7에서 결재 권한 잠금으로 설명하지만 UX 14 §8은 일회용·24시간·변경 전용 세션을 요구한다. 관리자 확인은 만료 외에 현재 값 재검사가 필요하다. [계정·인증 §8](../../ux/14-user-account-auth.md#8-서버-구현-요건-목업이-흉내만-내는-것) · [RBAC 2차 R-01·R-03·R-05](../../ux/29-rbac-r2.md) · [app.js](../../ux/mockups/assets/app.js#L1127)
- **고칠 방법** 세션의 유휴·절대 만료와 갱신 기준을 정의하고 회수·초기화·삭제·기한 만료를 모든 프로세스에 전파한다. WS는 변경 수신마다, SSE는 재접속과 전달 시점에 현재 자격을 확인한다. 작업은 실행·공개·다운로드 시점에 필요한 권한을 재확인한다. 임시 비밀번호의 발급 버전·소비·세션 교체를 원자화한다. 관리 변경 확인은 현재 값과 요청의 기대 리비전, 확인자 자격·독립성, 만료 시각을 적용 트랜잭션에서 비교한다. 마지막 관리자·첫 기관 담당자·인증 전환의 예외도 동시 변경 아래 검증한다. 사업 종료는 신청·영역 담당·엑셀 묶음 인계와 중지 순서를 정한다.

## BA-09. 인증과 감사의 운영 통제를 구체화해야 한다

- **심각도** 상
- **근거** §7의 쿠키 속성·Argon2id·INSERT 제한은 출발점이다. UX 14는 출처와 계정의 시도 제한, IdP 검증, 비상 로그인 통제, 불변 사용자 식별, 접속 이력 점검까지 요구한다. 29 R-12·R-14는 감리 감사 범위와 개인정보 산출물의 역할·사유 제약을 별도로 둔다. [계정·인증 §8](../../ux/14-user-account-auth.md) · [RBAC 2차](../../ux/29-rbac-r2.md) · [app.js 권한표](../../ux/mockups/assets/app.js#L70)
- **고칠 방법** 운영 설치에서 목업 계정을 제외하고 최초 관리자 발급, 세션 ID 교체, CSRF와 WS Origin 검사, 출처·계정별 시도 제한을 정의한다. SSO는 실제 기관 IdP에서 검증하고 발급자와 불변 식별자를 함께 묶는다. 비상 로그인에는 개인 관리자·접속 경로 제한·추가 인증·경보를 적용한다. 감사에는 불변 실행자 키와 당시 이름, 대리 대상, 결과·사유·대상 범위를 기록하고 비밀번호·토큰·불필요한 개인정보는 가린다. 앱 쓰기, 조회, 파티션 보존 관리 권한을 분리하고 기관이 위변조 점검과 5년 보관·파기 책임을 정한다. 실제 다운로드에 권한과 사유를 다시 적용하며 개인정보 컬럼 목록의 역할 제한을 명시한다.

- **근거** §5.4의 스트리밍 읽기와 COPY는 처리 방식이다. 기준본·현재 사전·편집 파일의 3방향 비교와 미리보기 이후 변경 검출 계약이 빠져 있다. §5.5에서는 확정본 외에 명명 템플릿·타입 매핑의 시점이 지정되지 않아 같은 확정 버전의 DDL이 달라질 수 있다. [app.js 기준본 기록](../../ux/mockups/assets/app.js#L1336) · [SWS 비교 §2·§6](../../spec/da-feature-spec/22-sws-comparison.md) · [메타데이터 설계 MD-08·MD-09·MD-38](../../spec/da-feature-spec/30-metadata-design.md)
- **고칠 방법** 기준본 ID·항목 버전, 파일 해시, 검증 기준 버전, 비교한 사전 상태, 행별 선택을 검증 결과에 연결한다. 신청 때 바뀐 입력은 재검증하고 취소·재시도 시 검증이 끝난 결과만 공개한다. 업로드에서 바이트를, 파싱에서 행·셀·압축 해제 크기와 처리 시간을 제한한다. 공식 산출물에는 스냅샷 해시·타입/명명 규칙 버전·렌더러 버전을 연결한다. 확정 재현과 최신 규칙 재검증을 별도 동작으로 정의한다. DDL 방언별 게이트와 기준 산출물을 통과 조건에 둔다.

## BA-11. DB와 파일을 같은 시점으로 복구할 수 있어야 한다

- **심각도** 상
- **근거** §8은 DB 전체 백업과 WAL 보관을 제시한다. DB만 시점 복구하면 같은 리비전의 업로드·공식 산출물·작업 상태가 없을 수 있다. 단일 서버 장애나 디스크 소진은 DB와 파일을 함께 중단시킨다. 마이그레이션 되돌림 스크립트만으로 데이터 변경의 복구 가능 여부도 판단하기 어렵다.
- **고칠 방법** 기관과 RPO·RTO를 정하고 별도 장애 영역에 암호화한 DB·WAL·파일·복구 설정을 보관한다. 파일을 불변 키·체크섬으로 저장해 DB 복구 지점과 매칭하는 목록을 남긴다. 새 장비 복구에서 세션 무효화, 파일 대조, 큐 재개·중복 억제, 투영 재구축을 확인한다. 백업 나이·WAL 적체·볼륨 여유·복구 연습 결과를 감시한다. 배포는 마이그레이션을 한 번만 실행하고 롤백 가능 범위와 복구 경로를 검증한다.

## BA-12. 내부망 반입과 렌더 작업 격리를 초기에 검증해야 한다

- **심각도** 중
- **근거** §8·§12의 이미지와 의존성 캐시 외에 사내 CA, 네이티브 모듈, Chromium·한글 글꼴, 오프라인 패치 경로, 컨테이너 간 권한 경계가 빠져 있다. API 2개와 SSE·WS가 함께 동작할 때 DB 연결 한도나 연결 종료 전파도 운영 변수다. UX 03은 공식 ERD에 동일 출처와 크기 상한을 요구한다. [ERD 편집기 §11](../../ux/03-erd-editor.md#11-열린-질문)
- **고칠 방법** B0에서 고정 버전 이미지·잠금 파일·해시 목록과 내부 CA 포함 설치 묶음을 망 분리 환경에 실제 설치한다. 배포 계정과 DB·파일 접근을 최소화하고, 파일은 인증된 핸들러로 제공한다. 렌더러는 전용 저권한 프로세스로 자원·시간·접근 가능한 경로를 제한하고 크기·한글 글꼴·표제란 결과를 확인한다. DB 연결 풀과 업로드·렌더 작업 동시성을 제한하고 WS/SSE 지연·재연결, 큐 적체, 투영 지연을 운영 지표로 둔다.

## BA-13. TypeScript 선택은 타당하나 비교 근거를 보강해야 한다

- **심각도** 중
- **근거** §2의 Yjs 원본 처리와 브라우저 미리보기 규칙 공유는 TypeScript의 실제 이점이다. 같은 소스여도 사전 버전·정규화·시각·권한 입력이 다르면 결과가 달라진다. Python 비교에서 Hocuspocus 채택을 전제로 두었으며, SWS는 공통 사례로 TS·Python의 규칙 결과를 맞춘 사례다. SWS 경험은 인력·운영 경험에 반영할 수 있고 메타데이터 코드·DB·API 공유는 30의 범위 밖이다. 23은 Node 26에서 측정했고 엑셀 실제 업무 검사, DB 기반 Yjs 저장, 사내망 20명은 측정하지 않았다. [SWS 비교 §2](../../spec/da-feature-spec/22-sws-comparison.md) · [메타데이터 설계 §1](../../spec/da-feature-spec/30-metadata-design.md) · [성능 스파이크 §1·§4~7](../../spec/da-feature-spec/23-performance-spike.md)
- **고칠 방법** TypeScript를 기본안으로 두고 FastAPI 업무 API + Node collab의 분리안도 비교한다. 서버 전용 규칙과 공통 순수 계산을 분리하고, 고정 입력·판정 사례로 양쪽의 테스트·운영 비용을 비교한다. 팀의 NestJS·Node 운영 경험, 장애 대응, 망 반입과 지원 수명, DB 트랜잭션 숙련도, CPU 집약 검사가 이벤트 루프에 미치는 영향을 평가한다. 배포 후보 버전에서 저장·복구와 실제 엑셀 검증을 다시 측정한다.

## BA-14. 단계별 기능 완료보다 W1의 업무 완주를 종료 기준으로 삼아야 한다

- **심각도** 상
- **근거** §10은 총 16~17주를 배정했으나 인력·병렬화·기관 환경 접근을 가정으로 제시하지 않는다. B1 결재와 B2 모델은 B4의 두 사람 확인·조회 범위·위임·타입/검수 정책에 의존한다. B3에 W1 필수인 엑셀 등록·정의서 가져오기·DDL 산출과 W2의 DDL 가져오기가 함께 있다. 20의 W1 종료는 S0~S6 완주이며 이후 22와 UX 03은 W1 실시간을 확정했다. [통합 우선순위 §1·§2](../../spec/da-feature-spec/20-priority.md) · [SWS 비교 §6](../../spec/da-feature-spec/22-sws-comparison.md) · [ERD 편집기 §13.1](../../ux/03-erd-editor.md)
- **고칠 방법** B0에서 내부망 설치·백업 복원·제출 고정·세션 회수의 최소 흐름을 확인한다. 결재와 모델의 최초 구현에 최소 정책·타입 규칙·열람 범위·관리 통제를 함께 넣는다. W1 판정은 정의서 가져오기, 사전 신청과 반영, 두 사용자 편집, 표준 맞추기, 확정, 게이트를 거친 DDL·정의서·준수율까지 한 데이터로 검증한다. DDL 리버스와 선택 SSO는 업무 의존성과 기관별 일정에 따라 별도로 산정한다. 실제 투입 인원과 기관 준비 일정을 반영해 기간을 다시 추정하고 20명·장애·복구·대용량 업로드 판정을 출시 일정에 포함한다.
