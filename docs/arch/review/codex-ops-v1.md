# 운영 확인 최소 기능 v1 설계 리뷰

검토 대상은 [04 운영 확인 최소 기능](../04-ops-self-check-plan.md)이다. 정책은 [03 인프라 설계 §17](../03-infrastructure-design-v1.md)과 [01 백엔드 구성안 §13](../01-backend-architecture-v1.md)을 우선 대조했다. 심각도는 **치명**(데이터 유실 또는 복구 보장 오류), **높음**(운영 장애·권한 노출·인수 차단), **중간**(판정·운영 계약 미비)으로 표시했다. 문서와 공식 자료를 검토했으며, 실행 시험은 포함하지 않았다. 배포할 Docker Engine·Compose·pg-boss·pgBackRest 버전에서 아래 인수 조건을 확인해야 한다.

## OP-01 · 높음 · 같은 이벤트 루프에서 멈춤을 감지할 수 없음

- **근거** — 04 §3.2·T-01. 이벤트 루프가 멈추면 30초 타이머와 오류 로그, 종료 호출도 실행되지 않는다. 10초 멈춤은 위상에 따라 측정에서 빠질 수 있고, 지연이 관측되어도 3회 연속 실패 조건을 충족시키지 않는다. Compose는 `unhealthy`를 표시하고, 재시작 정책은 컨테이너 종료에 반응한다. [Docker 재시작 정책](https://docs.docker.com/engine/containers/start-containers-automatically/)
- **고칠 방법** — B0에서 앱 프로세스 밖의 동일 컨테이너 감독 프로세스가 로컬 하트비트를 확인하고 종료 신호와 강제 종료 기한을 관리하는 방식으로 검증한다. T-01을 10초 일시 정체에서는 유지, 영구 정체에서는 제한 시간 내 재기동으로 나눈다. 탐지 주기·probe 타임아웃·종료 유예·재기동 시간을 모두 합산해 한도를 정한다.

## OP-02 · 높음 · 부하와 의존성 장애가 공통 재시작 루프로 이어짐

- **근거** — 04 §3.2·T-02. collab 저장 대기는 DB 단절만으로 30초를 넘긴다. worker 하트비트가 업무 실행 완료나 DB 폴링 성공에 묶이면 장애나 긴 렌더에서도 멈춘 것으로 보인다. 메모리 90% 역시 합법적인 코드·캐시·Chromium 사용으로 지속될 수 있다. 고정된 재연결 주기는 API 두 인스턴스와 다른 서비스의 재시도를 동기화한다.
- **고칠 방법** — DB·저장 적체와 메모리 압박은 준비 상태·경고와 부하 제한에 사용한다. 자기 종료는 의존성과 독립된 진행 정체에 한정하고, 기동 유예·지터·재시작 예산 및 예산 소진 시 운영자 복구 절차를 정한다. `always`와 예산 정지의 관계를 배포 구성에서 검증한다. 2분 DB 중지, 정상 최대 부하, 반복 기동 실패에서 재시작과 동시 연결 피크를 측정한다. 이전 종료 코드·OOM·강제 종료는 호스트 상태에서 수집하고 인스턴스 식별자와 관측 구간을 기록한다. DB에 뒤늦게 기록되는 시작 행만으로 재시작 수를 계산하면 DB 장애와 컨테이너 재생성 구간이 비게 된다.

## OP-03 · 치명 · 공동 편집 갱신의 저장 경계가 빠짐

- **근거** — 04 §3.2·§3.9, 01 §13.1의 내구 저장·ACK 계약, 03 §17.2·§17.6. 10초 flush는 DB 장애·이벤트 루프 멈춤·OOM에서 실패할 수 있다. worker의 주기적 체크포인트·갱신 정리가 collab의 단일 쓰기 소유권과 경합하면 복구에 필요한 순번까지 지울 수 있다.
- **고칠 방법** — 종료 시 신규 쓰기 차단 → 이미 수락한 갱신 저장 시도 → 커밋된 순번만 ACK 순서를 고정한다. 미ACK 갱신은 저장 중으로 표시하고 재접속 시 클라이언트가 재전송할 수 있게 안정된 식별자와 중복 억제를 둔다. 체크포인트 생성·정리는 collab 소유권 아래에서 수행하고, 체크포인트 커밋이 확인된 순번까지만 정리한다. 커밋 전·후 종료, ACK 유실, DB 단절 중 편집, 체크포인트 경합에서 ACK된 갱신 전부가 복원되고 재전송이 중복 반영되지 않는지 시험한다.

## OP-04 · 높음 · Compose 기동 조건과 운영 중 트래픽 전환이 혼재

- **근거** — 04 §3.2·§3.7·O-04, 03 §11·§17.2. `depends_on: service_healthy`는 Compose의 기동 순서이고 운영 중 upstream 선별이나 연쇄 재시작을 제공하지 않는다. `pg_isready`는 연결 수락 상태를 보여 주며 앱 쿼리·스키마 버전 확인은 별도로 필요하다. SPA 문서가 이미 200으로 열린 상태에서는 nginx가 API 응답을 HTML로 바꿔도 브라우저가 점검 페이지로 이동하지 않는다. [Compose 기동 순서](https://docs.docker.com/compose/how-tos/startup-order/) · [PostgreSQL pg_isready](https://www.postgresql.org/docs/16/app-pg-isready.html) · [nginx 프록시 오류 처리](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_intercept_errors)
- **고칠 방법** — 기동 healthcheck, 서비스별 readiness, nginx upstream 동작, 업그레이드 게이트를 구분한다. 마이그레이션 종료와 대상 API 두 개·collab·worker의 준비 상태를 배포 스크립트가 유한 시간 안에 확인하게 한다. 문서 탐색에서는 정적 페이지, API에서는 구조화된 503, 기존 SPA·SSE·WS에서는 화면 상태·재연결 처리를 정의한다. 한 API만 단절, DB 단절, 계획 점검을 각각 시험한다.

## OP-05 · 치명 · pgBackRest info로 PITR 상한을 계산하는 전제 오류

- **근거** — 04 §3.4·O-07·T-04, 03 §7·§17.1. `info`는 백업 메타데이터와 아카이브 범위를 보여 주며 범위 안에 누락이 있을 수 있다. 백업 종료 시각·마지막 WAL 이름·`last_archived_time` 모두 연속 WAL로 실제 도달 가능한 업무 시각을 단독으로 증명할 수 없다. `check`는 primary에서 WAL 전환을 유발하며, `archive_timeout=900`은 세그먼트 전환 설정이라 저장소 전송 시간과 누락을 보장하지 않는다. 20분 경보를 5분마다 평가하면 15분 RPO 초과 뒤에 알릴 수 있다. [pgBackRest 명령 참조](https://pgbackrest.org/command.html) · [PostgreSQL 16 WAL 설정](https://www.postgresql.org/docs/16/runtime-config-wal.html#RUNTIME-CONFIG-WAL-ARCHIVING)
- **고칠 방법** — 최근 백업·아카이브 진행·검증된 복구점·현재 판정 불가를 각각 표시한다. 20분 정책과 RPO의 차이를 명시하고, 15분 목표에 맞춘 전환·전송·감지 시간 예산을 별도로 정한다. 시각 추정이 필요하면 유효한 백업 기준점, 동일 타임라인에서 연속 WAL, 시간과 대응되는 확인 지점을 함께 검증한다. 확증이 없으면 시각은 미확인으로 표시한다. `check`는 부하가 관리되는 별도 검증, `verify`는 고정 버전에서 지원 범위를 확인한 저장소 검증, 격리 복원은 PITR 인수에 사용한다. 누락 WAL, 무트래픽, 저장소 단절·재연결 및 복원 표식의 실제 도달을 시험한다.

## OP-06 · 높음 · 백업 결과를 양쪽에 기록하지 못하는 장애가 남음

- **근거** — 04 §3.4·T-04. 백업 저장소 단절 중에는 해당 저장소의 `status.json`을 갱신할 수 없다. DB까지 꺼지면 같은 실패를 양쪽에서 잃는다. 한 파일에 여러 종류가 결과를 쓰면 늦게 끝난 실행이 최신 상태를 덮을 수 있고, 강제 종료 시 실행 종료 기록이 없다.
- **고칠 방법** — 호스트 예약 실행기가 실행 ID, 종류, 시작·종료·종료 상태를 로컬 제한 디렉터리에 원자적으로 기록하고 DB·백업 저장소로 내보낼 때 같은 ID로 중복을 억제한다. 최근 시도·마지막 성공·진행 중·기한 초과·읽기 실패를 분리하고, 공간 고갈 등 로컬 기록 실패 시에도 CLI가 미확인과 부실 상태를 반환하게 한다. 저장소와 DB 동시 단절, 중간 강제 종료, 동시 실행 및 재동기화를 시험한다.

## OP-07 · 높음 · WAL 적체와 파일 복제의 측정·복구 경계가 빠짐

- **근거** — 04 §3.4~3.5·O-07, 03 §17.1. `statfs`로는 WAL 대기 파일 수와 최고 대기 시간을 얻을 수 없다. 대기 볼륨의 파일 개수는 실제 PostgreSQL 아카이브 대기를 대변한다는 근거가 없다. 04의 파일 복제 대기 표시는 outbox의 재시도·종료 실패·미등록 파일 및 DB와 파일이 함께 복원되는지 설명하지 않는다.
- **고칠 방법** — PostgreSQL 쪽에서 실제 아카이브 대기 상태·최고 대기 시간·`pg_wal` 파일시스템 여유와 아카이버 오류를 안전한 요약으로 노출한다. 파일 쪽은 참조 확정부터 복제 완료까지의 지연, 재시도·종료 실패, 저장소 여유를 분리한다. O-07을 I-06의 일일 DB 시점 T + 체크섬 manifest 발행에 연결한다. 격리 복원에서 확정 문서·첨부 열기, 체크섬, 큐 및 외부 전송 재개 통제와 RTO 실측을 인수 조건으로 둔다. [PostgreSQL 16 아카이버 통계](https://www.postgresql.org/docs/16/monitoring-stats.html#MONITORING-PG-STAT-ARCHIVER-VIEW)

## OP-08 · 높음 · pg-boss 처리 보장과 예약 누락 대응 미정

- **근거** — 04 §3.5·§3.9·O-05·T-09, 01 §13의 outbox, 03 §17.6. pg-boss의 실행 만료와 재시도로 이전 시도의 외부 부수 효과가 취소되지는 않는다. DB/스케줄러 정지 후 모든 cron 회차가 자동 보충된다는 전제도 없다. 공식 기본 스케줄 문서는 제한된 시간 창을 설명하며 설치 버전에 따라 제공 옵션이 다르다. 대기 시간은 지연 예약·retry backoff와 실행 가능한 적체를 구분해야 한다. [pg-boss 예약](https://pgboss.io/api/scheduling) · [큐·만료·재시도](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md)
- **고칠 방법** — 버전·스키마 마이그레이션 주체를 고정하고, 큐별 `tz`·동시성·실행 기한·재시도 수(최초 1회와 재시도 3회 구분)·멱등 키·중첩 및 보충 규칙을 표로 둔다. 작업 실행 ID와 시도 번호, 중단 상태를 기록하고 계정·승인 만료는 요청 때도 검증한다. 큐별 실행 가능한 대기, 예약/재시도 대기, 최종 실패를 분리한다. 다운타임 뒤 누락된 예약, 부수 효과 직후 강제 종료, 장기 작업과 재시도의 겹침을 인수에 넣는다.

## OP-09 · 높음 · 점검이 자기 실행 중단을 알 수 없음

- **근거** — 04 §3.3·§3.5·§3.7~3.9. 동일 worker·DB·큐가 점검과 알림에 필요하다. worker 정지·큐 포화·DB 단절로 `ops.checks`가 안 돌면 직전의 정상 결과가 계속 노출될 수 있다. 마지막 성공이 한 번도 없는 경우와 점검 일부만 타임아웃된 경우도 정의가 없다.
- **고칠 방법** — 상태 API와 호스트 CLI가 데이터 유효기간을 독립 판단하도록 한다. 측정 안 됨·오래됨·접근 불가를 노출하고 CLI가 정상 종료 코드로 숨기지 않게 한다. 점검 큐에 별도 처리 슬롯과 점검별 제한 시간을 둔다. 적용 전·첫 실행 지연·계획 정지·중단 이후 복구를 구분한다. worker만 정지·업무 큐 포화·DB 재개 시 UI와 CLI 표시 및 알림 재개를 검증한다.

## OP-10 · 높음 · 알림 전이와 전송 트랜잭션이 빠짐

- **근거** — 04 §3.3·§3.6·T-03, 01 §13 outbox. `fail → warn`은 해결되지 않고, 한 번의 `ok`는 경계에서 해결·재발을 반복시킨다. 재시도나 겹친 점검은 열린 행, 알림, 해결 알림을 중복 생성할 수 있고, 상태만 커밋한 뒤 프로세스가 종료되면 통지를 잃을 수 있다. 마지막 알린 시각만으로 대기·전송 실패·재시도 여부를 구별하기 어렵다.
- **고칠 방법** — 확인은 열린 알림의 감사 동작으로 두고, 전이표에 복구 임계·연속 횟수, `unknown/stale` 처리, 재발 시 새 발생 ID, 24시간 재통지 기산점을 명시한다. 키별 열린 행 유일 제약과 조건부 전이를 적용하고, 상태 변경 및 outbox를 같은 트랜잭션에 넣는다. 발생 ID·이벤트 종류·회차·수신자·채널별 키로 중복을 억제한다. 커밋 전후 종료, 동시 점검, fail/warn 경계, 확인 후 재알림·해결·재발을 시험한다.

## OP-11 · 높음 · 수신자가 없거나 바뀔 때의 인계와 노출 범위가 모호

- **근거** — 04 §3.6~3.7·T-05, 01 §5 notify·§13 회수 규칙. 기관 담당자의 자격과 운영 정보 열람 범위가 정의되지 않았다. 활성 Admin이 뒤늦게 생기거나 알림 전송 전에 기존 수신자 자격이 회수되면 처리 규칙이 없다. 운영 메일은 01의 결재 메일 계약에 추가되는 범위다.
- **고칠 방법** — 수신자 판정에 활성·만료·권한 검사를 적용하고 발송 및 열람 때 재확인한다. 기관 담당자에게 위임된 수신 범위와 제한된 문구를 정한다. 모두 부재일 때 보류 상태와 CLI 표시를 남기고 적격 수신자 복귀 시 열린 사건을 인계한다. 운영 메일은 B3 별도 정책으로 승인 범위, 실패 재시도, 앱 알림 성공과의 독립 여부를 정한다. 자격 변경, 양쪽 모두 부재, SMTP 단절을 시험한다.

## OP-12 · 높음 · /data 읽기 전용 마운트로 업무 파일과 비밀 노출 가능

- **근거** — 04 §3.5·O-04. `ro`는 읽기·열거를 허용한다. /data 안의 PGDATA·격리 파일·설정과 하위 마운트까지 worker의 접근 범위가 넓어질 수 있다. 하위 마운트의 재귀적 읽기 전용 동작은 커널과 설정에 의존하며, 상위 경로의 `statfs` 한 번으로 하위 파일시스템을 대표할 수도 없다. [Docker bind mount](https://docs.docker.com/engine/storage/bind-mounts/)
- **고칠 방법** — 기존 호스트 예약 실행기에서 지정 파일시스템별 용량·inode 상태만 요약 파일로 내보내거나 파일시스템별 비어 있는 전용 경로만 노출한다. worker에 /data 전체·PGDATA·Docker 소켓을 부여하지 않는다. TLS는 공개 인증서 교체와 nginx reload 뒤 실제 제공 체인·만료일을 확인한다. 인증서 파일 마운트라면 원자 교체 뒤 컨테이너가 새 파일을 보는지 검증한다. 데이터·WAL·Docker 로그가 서로 다른 파일시스템인 배치, 마운트 해제, 비인가 파일 접근 거부를 인수에 넣는다.

## OP-13 · 높음 · 키 이름 마스킹으로 자유 텍스트와 지원 번들의 민감 정보가 남음

- **근거** — 04 §3.1·§3.8·T-06~08, 03 §6의 느린 SQL 로그. 오류 스택·메시지, nginx 요청/쿼리 문자열, PostgreSQL 문장·바인드 값, pgBackRest/rsync stderr 및 브라우저 오류에는 금지 키 이름 없이 값이 들어갈 수 있다. `userId`·`doc`·경로를 보관하는 로그와 T-08의 개인정보 없음 약속도 별도 반출 규칙이 필요하다. Docker local 회전 한도는 컨테이너 단위 용량 설정이며 24시간 보존을 보장하지 않는다. [Docker local 드라이버](https://docs.docker.com/engine/logging/drivers/local/)
- **고칠 방법** — 출처별 허용 필드와 경로 템플릿을 정하고 원문 body/header/query·SQL 파라미터·자유 형식 stderr를 기본 배제한다. nginx가 요청 ID를 생성·덮어쓰고 서비스는 신뢰 경로에서만 받게 한다. 번들은 별도 허용 목록으로 ID를 제거·가명 처리하고 수집 가능한 기간과 잘림을 표시한다. 호스트 전용 권한과 보관·반출 규칙을 둔다. 고유 표식 비밀을 예외·DB·프록시·백업·클라이언트 경로에 넣어 원본 로그와 번들 양쪽에 0건인지, 로그 폭증 때 회전과 디스크 예산이 지켜지는지 확인한다.

## OP-14 · 높음 · 운영 DB 역할·API 권한·CLI 감사의 경계가 불일치

- **근거** — 04 §3.3·§3.7~3.8·§5와 03 §6·§17.5. 기존 `neodb_backup`은 백업 권한 역할이고 04는 이름을 결과 INSERT 전용으로 재정의한다. 공용 `neodb_app`이 ops 전체를 쓰면 결과·알림 이력을 위조·삭제할 수 있다. `settings` 문자열만으로 위임 사용자 포함 여부를 판단하기 어렵다. DB가 중지된 상태에서 CLI 실행을 DB 감사에 즉시 남기는 계약도 성립하지 않는다.
- **고칠 방법** — 백업 실행 자격과 결과 기록 계정을 분리하고 스키마 USAGE·테이블 INSERT 및 필요한 경우 시퀀스 권한만 허용한다. 운영 API 읽기와 ACK, worker 전이·보존, 마이그레이션 소유권을 구분한다. ACK와 감사는 같은 트랜잭션에 두고, 호스트 CLI는 운영자 계정·호스트 저널 기록 및 필요한 작업만 DB 복구 후 대조할 범위를 명시한다. 권한 우회, 백업 계정의 SELECT/UPDATE/DDL 거부, DB 없이 CLI 실행 및 기록을 시험한다.

## OP-15 · 중간 · 일부 지표가 운영 상태를 오판하게 함

- **근거** — 04 §3.5·§3.7~3.8. 같은 호스트 앱·DB 시각 비교는 공통 호스트 시계 오차를 잡지 못하고, PostgreSQL `now()`는 트랜잭션 시작 시각이다. 모든 서비스 버전 문자열이 같다는 조건은 서버별 빌드 버전·호환 스키마·확장 단계 업그레이드를 포괄하지 않는다. 상태 화면을 열 때마다 각 서비스에 동기 질의하면 장애 중 요청이 길어진다.
- **고칠 방법** — NTP는 호스트 동기화 확인으로 표시하고 DB 비교가 필요할 경우 짧은 독립 샘플·왕복 시간·`clock_timestamp()`를 사용한다. 릴리스 매니페스트의 서비스별 기대 버전과 스키마 호환 범위를 대조한다. 상태 API는 짧은 총 타임아웃과 관측 시각을 반환하고 일부 서비스가 응답하지 않아도 나머지 상태를 표시한다. [PostgreSQL 16 시각 함수](https://www.postgresql.org/docs/16/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

## OP-16 · 높음 · 구현 선후행과 규모가 기반 일정에 맞지 않음

- **근거** — 04 §6, 01 §13.9, 03 §17.9. O-02의 DB 기록은 O-03이 필요하고 O-06의 일부 점검은 O-04·O-07 및 업무 모듈에 기대지만 의존 열에 빠져 있다. O-07의 I-06 의존은 I-06 인수가 O-07 결과를 요구하므로 선행 백업 실행과 최종 인수를 분리해야 한다. O-09의 ‘목업 먼저’와 O-08 완료 의존, 03 §10의 MO-53 제품 정보 확장과 04의 새 화면 위치도 조율이 필요하다. O-01~04·O-07·O-10을 각 전체 범위로 합치면 B0 관련 작업만 10~18 개발자일이며 B0의 다른 기반 작업도 있다. O-06의 11종 점검과 알림 엔진·메일을 M 한 건으로 보면 통합 비용이 숨는다.
- **고칠 방법** — B0에는 로그·기동/준비 계약·스키마·호스트 CLI 최소본과 자기 감시/내구 ACK·백업 복원 위험 검증을 배치한다. B1에는 실제 B1 모듈 범위의 pg-boss·점검·앱 알림·상태 API/UI, B3에는 외부 계정·확인 요청 만료와 SMTP, B5에는 지원 번들·doctor·복구 인수를 배치한다. 목업은 정보 구조와 API 계약 합의에 붙이고 화면 구현은 API에 의존시킨다. O-06과 O-07을 실제 배포 가능한 단위로 쪼개 단계별 개발·통합·장애 시험 공수를 다시 산정한다.

## OP-17 · 높음 · 기존 인수표가 설정 문구만 통과시킬 수 있음

- **근거** — 04 §7의 T-04는 단절 직후 한 점검에서 경보를 요구하지만 §3.4는 26시간·20분 경과 조건을 둔다. T-03의 ‘24시간 안 재알림 없음’은 실제 재통지와 해결 후 재발을 검증하지 않는다. T-09의 ‘작업 하나 실패’는 최종 실패, 마지막 성공 지연, 재시도 성공을 구별하지 않는다. T-10은 파일만 바꿔도 통과할 수 있다.
- **고칠 방법** — 각 시험에 선행 상태·장애 주입·관측 시계·기한·기대 상태와 금지된 부수 효과를 적는다. 백업 최근 시도 실패는 다음 점검, WAL 목표 초과는 기준 시각 이후 첫 점검, 단절 중 기록은 호스트에서 각각 검증한다. 가상 시계 또는 기준시각 제어로 24시간 재통지·해결·재발을 시험하고, 재시도 성공/소진·작업 중단·첫 실행 누락을 나눈다. TLS는 무중단 reload 뒤 실제 접속과 워커 측정값을 함께 확인한다. OP-01·03·05의 장애 시험을 각각 B0 위험 검증과 B5 최종 인수에 연결한다.
