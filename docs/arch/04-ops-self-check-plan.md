# 운영 확인 최소 기능 — 검토 · 설계 · 구현 플랜 (v1.1, 2026-11-25)

> 범위: 관제 시스템 없이 **서비스가 스스로 돌기 위해 필요한 최소한**(인프라 설계 [03 §10](03-infrastructure-design-v1.md)). 로그 · 상태 확인 · 자동 회복 · 백업 결과 기록 · 시스템 상태 화면 · Admin 앱 알림 · 정기 작업 · 운영 명령(`neodb.sh status` 등).
> 원칙: 별도 관제 도구(Prometheus · Grafana · SIEM · 외부 감시)는 쓰지 않는다. **앱이 이미 가진 것**(DB · 작업 대기열 · 앱 알림 · Admin 화면)으로 만든다.
> 상태: **v1.1 — Codex 검토(OP-01~17, [review/codex-ops-v1.md](review/codex-ops-v1.md)) 반영. §8이 앞 절보다 우선한다.** 구현은 오르카로. 구현 플랜은 §8.9(§6 대체), 인수 기준은 §8.10(§7 대체).
> 목업: [시스템 상태](../ux/mockups/ops-status.html)(`?state=ok|warn|fail|stale`) · [점검 중 정적 페이지](../ux/mockups/maintenance.html).

## 1. 왜 필요한가 — 없으면 생기는 일

| 기능 | 없으면 |
|---|---|
| 서비스 로그 | 장애가 나도 원인을 알 수 없다. 내부망이라 외부에서 원격 조사도 못 한다 |
| 상태 확인 · 자동 회복 | 프로세스가 멈췄는데(살아는 있지만 응답 없음) 아무도 모른다. 업그레이드 스크립트가 다음 단계로 넘어갈지 판단할 수 없다 |
| 백업 결과 기록 | **백업이 몇 주째 실패해도 아무도 모른다** → 장애 때 복구할 데이터가 없다(RPO 15분 약속이 무의미) |
| 시스템 상태 화면 | Admin이 서버에 들어가지 않고는 상태를 볼 수 없다 |
| Admin 앱 알림 | 디스크가 차서 DB가 멈추거나, 인증서가 만료돼 접속이 끊긴 뒤에야 안다 |
| 정기 작업 | 사용 기한이 지난 외주 계정이 그대로 남고, 확인 요청 · 세션 · 오래된 파일이 쌓인다 |

## 2. 현재 설계(03 §10) 검토 — 빈틈

| # | 빈틈 | 왜 문제인가 | 이 문서의 해결 |
|---|---|---|---|
| G-01 | **“상태 확인이 실패하면 Docker가 자동 재시작”은 틀림** | Docker Compose 단독은 healthcheck 실패로 재시작하지 않는다. `restart: always`는 **프로세스가 종료됐을 때만** 동작 | ~~앱 안 자기 감시~~ → **컨테이너 안 감독 프로세스**가 앱 하트비트를 보고 종료시킴(§8.1) |
| G-02 | 살아 있음 · 준비됨의 기준이 서비스마다 없음 | 무엇이 실패해야 재시작인지 모호 — DB 잠깐 끊김에 전 서비스가 재시작되면 더 나빠진다 | 서비스별 판정표(§3.2): DB 단절은 ‘준비 안 됨’이지 ‘죽음’이 아님 |
| G-03 | 백업 결과가 DB에 어떻게 들어오는지 없음 | `neodb-backup`은 일시 컨테이너 · DB 쓰기 권한 미정 · **DB가 죽었을 때는 기록할 곳이 없음** | 전용 역할로 `ops.backup_runs`에 기록 + 백업 저장소의 상태 파일에도 기록(§3.4) |
| G-04 | 디스크를 누가 어떻게 재는지 없음 | 컨테이너는 호스트 디스크를 못 본다 | ~~worker에 /data 마운트~~ → **호스트 예약 실행기**가 파일시스템별 용량 요약만 내보냄(§8.5) |
| G-05 | 인증서 만료일을 어디서 읽는지 없음 | 인증서는 `neodb-web`에만 있다 | ~~인증서 파일 마운트~~ → 실제 제공되는 HTTPS 체인에 접속해 확인(§8.5) |
| G-06 | 알림이 매번 다시 오거나, 한 번 오고 끝남 | 5분마다 같은 알림이 쌓이면 무시되고, 한 번만 오면 잊힌다 | 알림 **열림 · 해결 · 다시 알림(24시간)** 수명주기(§3.6) |
| G-07 | 받는 사람이 없을 때 | Admin이 모두 중지 · 기한 만료면 아무도 못 받음 | Admin 없으면 기관 담당자에게, 둘 다 없으면 서버 로그 + `neodb.sh status`에 표시 |
| G-08 | **DB나 api가 죽으면 상태 화면도 못 연다** | 화면 자체가 api · DB에 기대므로 가장 필요할 때 안 보임 | `neodb-web`이 502/503에 **정적 점검 페이지**를 보여 주고, 서버에서는 `neodb.sh status`가 DB 없이도 동작(§3.7 · §3.8) |
| G-09 | 정기 작업이 돌았는지 확인할 수 없음 | 만료 처리가 몇 주째 안 돌아도 모름 | 실행마다 `ops.job_runs` 기록, 마지막 성공이 기준보다 오래되면 알림 |
| G-10 | 로그 형식 · 가리기 · 보관 기간이 구체적이지 않음 | 비밀번호 · 토큰이 로그에 남거나, 디스크를 채움 | 로그 계약(§3.1) — 필드 · 가릴 항목 · 회전 · 요청 ID 전파 |
| G-11 | 내부망 장애 조사 수단 | 업체가 원격으로 못 봄 | `neodb.sh support-bundle`: 가린 로그 · 상태 · 버전을 한 파일로(§3.8) |
| G-12 | 시간 어긋남 | 세션 만료 · 사용 기한 · 감사 시각이 틀어짐, 컨테이너 안에서는 NTP를 확인 못 함 | `neodb.sh status`가 호스트에서 NTP 동기화 상태 확인 + 앱은 DB 시각과의 차이만 점검 |

## 3. 설계

### 3.1 로그 계약
- **형식**: 서비스마다 stdout에 JSON 한 줄. 필드 — `ts`(ISO, 기관 시간대) · `level`(debug/info/warn/error) · `svc`(web/api/erd-collab/job-worker/backup) · `reqId` · `userId`(있을 때) · `msg` · `route` · `status` · `ms` · `err`(이름 · 메시지 · 스택은 error만) · `job`(작업 이름 · 시도) · `doc`(collab 문서 키).
- **요청 ID 전파**: `neodb-web`이 `X-Request-Id` 생성 → api가 받아 로그 · 작업(job payload) · collab RPC에 실어 보냄 → 한 요청을 서비스 넘어 따라갈 수 있다.
- **가리기(반드시)**: `password` · `pw*` · `token` · `cookie` · `authorization` · `secret` · 세션 ID · 임시 비밀번호 · 업로드 셀 값 → `***`. 사전 · 모델 내용은 로그에 싣지 않는다(ID만).
- **수준**: 운영 기본 `info`, 느린 요청(> 1초) · 재시도는 `warn`, 처리하지 못한 예외는 `error`.
- **보관**: Docker `local` 드라이버, 서비스당 100MB × 10개(약 1GB) 회전. 장기 보관이 필요한 기록은 감사 로그(DB)다.
- **브라우저 오류**(선택, 권장): `POST /api/v1/client-errors` — 화면에서 난 스크립트 오류를 api 로그로(로그인 사용자만, 분당 10건 제한, 메시지 · 화면 경로 · 버전만).

### 3.2 상태 확인 · 자동 회복
| 서비스 | 살아 있음 `/healthz` (실패 = 재시작 대상) | 준비됨 `/readyz` (실패 = 일을 못 받음, 재시작 아님) |
|---|---|---|
| neodb-web | nginx 프로세스 응답 | api 1개 이상 준비됨 |
| neodb-api | 이벤트 루프 지연 < 5초 · 메모리 한도 90% 미만 | DB 쿼리 1회 성공(1초 안) · 마이그레이션 버전 일치 |
| neodb-erd-collab | 이벤트 루프 지연 < 5초 · **갱신 저장 대기열이 30초 넘게 막히지 않음** | DB 연결 · 고정 RPC 응답 |
| neodb-job-worker | 작업 루프 하트비트 < 60초 | DB 연결 · 대기열 접근 |
| neodb-postgres | `pg_isready` | — |
- **자기 감시(G-01)**: api · erd-collab · job-worker는 30초마다 자기 ‘살아 있음’을 판정해 **3회 연속 실패하면 오류 로그를 남기고 스스로 종료**(종료 코드 70). `restart: always`가 다시 띄운다. erd-collab은 종료 전에 갱신 저장을 끝까지 시도한다(최대 10초).
- **DB 단절은 재시작하지 않는다**: ‘준비 안 됨’으로 두고 지수 대기로 다시 연결(1 · 2 · 4 · … 최대 30초). 모두 재시작하면 DB 복구 뒤 동시 접속 폭주가 난다.
- **재시작 횟수 기록**: 프로세스가 뜰 때 `ops.service_starts`에 (서비스 · 시각 · 이전 종료 코드) 기록 → 1시간에 3번 넘게 재시작하면 알림(§3.6).
- compose `healthcheck`는 `depends_on`(기동 순서) · `neodb.sh status` · 업그레이드 판단에 쓴다.

### 3.3 운영 데이터(`ops` 스키마)
| 테이블 | 내용 | 쓰는 곳 |
|---|---|---|
| `ops.checks` | 점검 결과 최신값: `key`(예 `disk.data`) · 상태(ok/warn/fail) · 값 · 측정 시각 · 메시지 | job-worker(5분마다) |
| `ops.backup_runs` | 백업 실행: 종류(full/diff/wal-check/file-replicate/file-snapshot) · 시작 · 끝 · 결과 · 크기 · 복구 가능한 마지막 시각 · 오류 | neodb-backup · job-worker |
| `ops.job_runs` | 정기 작업 실행: 이름 · 시작 · 끝 · 결과 · 처리 건수 · 오류 | job-worker |
| `ops.service_starts` | 프로세스 시작 기록 | 각 서비스 |
| `ops.alerts` | 알림: `key` · 상태(open/resolved) · 처음 · 마지막 · 횟수 · 알린 시각 · 확인한 사람 · 확인 시각 | job-worker |
- DB 역할: `neodb_app`은 `ops` 읽기 · 쓰기, **`neodb_backup`은 `ops.backup_runs` INSERT만**. 보존: checks 최신만 · backup_runs/job_runs/service_starts 1년 · alerts 1년.

### 3.4 백업 결과 기록 (G-03)
- `neodb-backup`은 실행이 끝날 때마다 ① `ops.backup_runs`에 한 줄 기록(전용 역할) ② **백업 저장소에 `status.json`**(마지막 성공 시각 · 결과 · 복구 가능한 마지막 시각)을 쓴다. ②는 DB가 죽어도 남아 `neodb.sh status`가 읽는다.
- job-worker 점검(5분마다): 마지막 전체/차등 성공 > 26시간 → 알림 · pgBackRest `info`의 복구 가능한 마지막 시각이 지금보다 20분 넘게 뒤 → 알림 · 파일 복제 대기 > 15분 → 알림.

### 3.5 점검 항목 (job-worker, 5분마다 — 가벼운 것만)
| key | 측정 방법 | warn | fail(알림) |
|---|---|---|---|
| `disk.data` | `/hostdata`(호스트 `/data` 읽기 전용 · 용량 확인만) statfs | 70% | **80%** |
| `disk.pgwal` | WAL 보관 대기 볼륨 statfs · 파일 수 | 대기 100개 | 500개 또는 30분 |
| `db.size` | `pg_database_size` · 상위 테이블 | — | (표시만) |
| `db.conn` | `pg_stat_activity` 수 / `max_connections` | 70% | 90% |
| `queue` | pg-boss 대기 · 실패 · 가장 오래된 대기 | 대기 > 100 | 실패 반복 · 대기 > 30분 |
| `backup.*` | §3.4 | | |
| `jobs.*` | 정기 작업별 마지막 성공(기준 주기 × 2 초과) | | 초과 |
| `cert.tls` | 공개 인증서 파일(읽기 전용 마운트) 만료일 | 60일 | **30일** |
| `restart` | `ops.service_starts` 1시간 안 횟수 | 2 | 3 초과 |
| `clock` | 앱 시각 − DB `now()` | 2초 | 30초 |
| `version` | 실행 중 서비스 버전 · 마이그레이션 번호 일치 | | 불일치 |

### 3.6 Admin 앱 알림 (G-06 · G-07)
- 점검이 `fail`이 되면 `ops.alerts`에 **같은 key로 하나만 연다**(이미 열려 있으면 횟수 · 마지막 시각만 갱신).
- 알림: 처음 열릴 때 1회 → 열린 채 **24시간마다 다시** → 점검이 `ok`로 돌아오면 자동 **해결** + ‘해결됨’ 알림 1회.
- 받는 사람: 사용 중인 Admin 전원 → 없으면 기관 담당자 → 둘 다 없으면 로그 `error` + `neodb.sh status` 표시. 메일은 기관 메일 설정이 있을 때만(앱 알림이 기본).
- Admin은 알림을 **확인**할 수 있다(누가 · 언제 — 감사 로그). 확인해도 원인이 남아 있으면 24시간 뒤 다시 온다.
- 알림 문구(디자인 가이드 §11.2): “디스크가 82% 찼습니다 — 오래된 업로드 정리 또는 디스크 증설이 필요합니다”, “백업이 26시간 넘게 성공하지 않았습니다 — 백업 저장소 연결을 확인하세요”.

### 3.7 시스템 상태 화면 (Admin 전용)
- 위치: 상단 메뉴 **관리 › 시스템 상태**(설정 · 감사 로그 옆). 권한 `settings`(Admin).
- 구성(위 → 아래): ① 요약 띠(정상 / 확인 필요 n건) ② 열린 알림 목록(확인 버튼) ③ 서비스(버전 · 준비 상태 · 최근 재시작) ④ 백업(마지막 성공 · 복구 가능한 마지막 시각 · 최근 7회) ⑤ 저장(디스크 · DB 크기 · WAL 대기) ⑥ 작업 대기열 · 정기 작업 마지막 성공 ⑦ 인증서 · 시각.
- 데이터: `GET /api/v1/ops/status`(점검 최신값 + 알림 + 서비스 준비 상태를 그 자리에서 확인), `GET /api/v1/ops/alerts`, `POST /api/v1/ops/alerts/{id}/ack`.
- **DB · api가 죽었을 때(G-08)**: `neodb-web`이 502/503/504에 정적 페이지 “서비스 점검 중입니다 — 잠시 뒤 다시 시도하세요(관리자는 서버에서 neodb.sh status)”를 보인다.
- 목업: **만들었다** — [`ops-status.html`](../ux/mockups/ops-status.html)(정상 · 주의 · 장애 · 확인 안 됨 4상태) · [`maintenance.html`](../ux/mockups/maintenance.html). 백업 칸은 §8.4, 유효기간 표시는 §8.6을 따른다.

### 3.8 운영 명령 (`neodb.sh`, 서버에서)
| 명령 | 하는 일 | DB 없이 |
|---|---|---|
| `status` | 컨테이너 상태 · 준비 상태 · 버전 · 디스크(호스트) · NTP 동기화 · 백업 `status.json` · 열린 알림(DB 되면) · 최근 재시작 — 한 화면 요약, 문제 있으면 종료 코드 1 | **됨** |
| `logs <서비스> [--since 1h] [--level warn]` | 해당 서비스 로그 | 됨 |
| `support-bundle` | 최근 24시간 로그(가림 처리) · status · 버전 · 설정(비밀값 제외)을 `neodb-support-<시각>.tar.gz`로 — 업체 전달용 | 됨 |
| `doctor` | 설치 입력값(DNS · NTP · CA · SMTP · 디스크 권한 · 포트) 재점검 | 됨 |

| `files.retention` | 매일 03:00 | 보존 기한 지난 업로드 · 산출물 정리(참조 남은 것 제외) · 고아 파일 |
| `model.projection-verify` | 매일 02:00 | 투영 신선도 점검 · 오래된 것 재계산 |
| `ops.retention` | 매주 | ops 기록 1년 지난 것 정리 |
- 모든 작업은 실행마다 `ops.job_runs` 기록, 실패하면 지수 대기 재시도(최대 3회), 반복 실패는 `jobs.*` 점검으로 알림.

## 4. 하지 않는 것

## 8. Codex 검토 반영 (v1.1 — 앞 절보다 우선)

> [review/codex-ops-v1.md](review/codex-ops-v1.md) OP-01~17을 모두 받아들였다. 앞 절과 다르면 이 절을 따른다.

### 8.1 자기 감시는 앱 밖 감독 프로세스로 (OP-01 · OP-02)
- **앱 이벤트 루프 안의 타이머로는 멈춤을 못 잡는다**(루프가 멈추면 타이머도 멈춤). 각 앱 컨테이너(api · erd-collab · job-worker)에 **감독 프로세스**(PID 1, 작은 바이너리 — tini 계열)를 두고 앱은 자식으로 실행한다.
- 앱은 **진행 하트비트**를 로컬 파일(`/run/neodb/heartbeat`, tmpfs)에 1초마다 갱신. 이 하트비트는 **DB · 업무 작업 성공과 무관한 순수 진행 신호**(루프가 돈다는 것만)다.
- 감독: 하트비트가 **20초** 갱신 없으면 SIGTERM → **10초** 유예 → SIGKILL → 감독도 종료(코드 70) → `restart: always`가 컨테이너를 다시 띄움. 한도 = 탐지 20 + 유예 10 + 재기동 약 20 = **약 50초 안 복귀**.
- **자기 종료 대상이 아닌 것**: DB 단절 · 저장 적체 · 메모리 압박 · 긴 렌더(Chromium) → 모두 ‘준비 안 됨’ 또는 경고 · 부하 제한(새 작업 받지 않음)으로만.
- **재시작 예산**: 기동 후 60초 유예(이 동안 하트비트 판정 안 함) · 재기동 지연에 0~5초 무작위(지터) · DB 재연결도 지수 대기 + 지터(최대 30초). 감독이 1시간에 5번 넘게 앱을 종료했으면 **더 재시작하지 않고** ‘정지 · 예산 소진’ 표식으로 둔다 → `neodb.sh status`가 빨간색으로 표시하고 운영자 절차(로그 확인 → `neodb.sh restart <서비스>`)를 안내.
- **재시작 횟수는 호스트에서 센다**: DB의 시작 기록만으로 세면 DB 장애 구간이 빈다. 호스트 예약 실행기(§8.4)가 `docker inspect`의 RestartCount · 이전 종료 코드 · OOMKilled를 5분마다 요약 파일로 내보내고, worker가 이를 `ops.service_starts`에 대조 기록.

### 8.2 공동 편집 저장 경계 (OP-03 · 치명)
- 종료 순서 고정: ① 새 편집 받기 중지(클라이언트에 ‘저장 중’) → ② 이미 받은 갱신을 DB에 저장 시도(최대 10초) → ③ **커밋된 순번까지만 ACK**. ACK 받지 못한 갱신은 클라이언트가 보관했다가 재접속 때 **같은 갱신 ID로 재전송**, 서버는 갱신 ID로 중복 반영을 막는다.
- **체크포인트 · 갱신 정리는 erd-collab이 문서 쓰기 소유권 아래에서만** 한다(§3.9의 `model.checkpoint`를 job-worker에서 erd-collab으로 이동). 정리는 체크포인트 커밋이 확인된 순번까지만.
- 01 §13.1 내구 저장 · ACK 계약과 같은 규칙. 인수: §8.10 T-03.

### 8.3 기동 · 준비 · 트래픽 전환 구분 (OP-04)
| 구분 | 무엇으로 | 쓰는 곳 |
|---|---|---|
| 기동 확인 | compose `healthcheck` + `depends_on: service_healthy` | 처음 띄울 때 순서만 |
| 준비 상태 | 서비스별 `/readyz`(DB 쿼리 1회 · 스키마 버전 일치 — `pg_isready`만으로는 부족) | nginx upstream · `neodb.sh status` |
| 트래픽 전환 | nginx upstream(api-1 · api-2) — 한쪽이 실패하면 다른 쪽으로 | 운영 중 |
| 업그레이드 게이트 | 배포 스크립트가 마이그레이션 종료 → api 2개 · collab · worker `/readyz`를 **최대 3분** 안에 확인, 넘으면 이전 버전으로 되돌림 | `neodb.sh upgrade` |
- 사용자 응답: **문서 요청(처음 화면 열기)** → 정적 점검 페이지(목업 `maintenance.html`) · **API 요청** → 구조화된 503 JSON(`{"code":"SERVICE_UNAVAILABLE","retryAfter":30}`) → 이미 열린 화면은 상단 띠 “서버에 연결할 수 없습니다 — 다시 연결 중” · **SSE · 공동 편집 WS** → 자동 재연결(지수 대기 + 지터), 편집은 로컬 보관.

### 8.4 백업 상태는 ‘검증된 것만’ 시각으로 (OP-05 · 치명, OP-06 · OP-07)
- **pgBackRest `info`로 ‘복구 가능한 마지막 시각’을 계산하지 않는다.** 화면 · CLI는 다음 넷을 따로 보여 준다:
  1. 최근 백업 — 마지막 시도 · 마지막 성공 · 진행 중 · 기한 초과
  2. WAL 보관 진행 — `pg_stat_archiver`의 마지막 보관 시각 · 실패 수 · 마지막 실패(PostgreSQL 쪽에서)
  3. **검증된 복구점** — 정기 복구 시험(분기, 격리 복원)으로 실제 도달이 확인된 시각
  4. 판정 불가 → **“확인 안 됨”**(시각을 추정해 보여 주지 않음)
- **RPO 15분 예산**: WAL 전환 `archive_timeout=300`(5분) + 전송 ≤ 5분 + 감지(점검 주기) ≤ 5분 = 15분. 알림은 “마지막 WAL 보관이 **10분** 넘게 없음”(무트래픽이어도 5분마다 전환되므로 성립). 03 §7 · §17.1의 20분 기준은 이것으로 바꾼다.
- **백업 결과 기록 주체는 호스트 예약 실행기**(systemd timer — `neodb-backup` 컨테이너를 띄우는 그것): 실행 ID · 종류 · 시작 · 끝 · 종료 코드를 **로컬 제한 디렉터리**(`/var/lib/neodb/runs/`, root 전용)에 원자적으로 쓰고(임시 파일 → rename) → DB(`ops.backup_runs`)와 백업 저장소(`status/<실행 ID>.json`)로 **같은 ID로** 내보냄(중복 무시). 둘 다 끊겨도 로컬 기록이 남아 `neodb.sh status`가 읽고, 연결되면 재동기화. 종류별로 파일을 나눠 늦게 끝난 실행이 다른 종류를 덮지 않게 한다. 로컬 기록마저 실패(공간 고갈)하면 CLI는 “확인 안 됨”과 종료 코드 1.
- **파일 복제**: 참조 확정 → 복제 완료까지 지연 · 재시도 · 최종 실패 · 저장소 여유를 따로 기록. 일일 DB 시점 T와 파일 체크섬 manifest를 짝으로 발행(03 I-06).

### 8.5 측정 위치 — worker에 호스트 경로를 붙이지 않는다 (OP-12 · OP-15)
- **worker에 /data · PGDATA · Docker 소켓을 마운트하지 않는다.** 호스트 예약 실행기(5분)가 `/var/lib/neodb/host-summary.json`을 쓴다: 파일시스템별(데이터 · WAL · 백업 대기 · Docker 로그) 용량 · inode, NTP 동기화 상태, 컨테이너 재시작 요약(§8.1). 이 파일 **하나만** worker에 읽기 전용으로 붙인다.
- **TLS**: worker가 `https://neodb-web`에 실제로 접속해 받은 인증서 체인의 만료일을 잰다(파일이 아니라 사용자가 받는 것 기준 — 교체 후 nginx reload를 안 했으면 잡힌다).
- **시각**: NTP는 호스트 요약으로. DB 비교가 필요하면 `clock_timestamp()`와 왕복 시간으로(`now()`는 트랜잭션 시작 시각이라 쓰지 않음).
- **버전**: 설치 묶음 매니페스트의 서비스별 기대 버전 · 스키마 호환 범위와 대조(“모두 같은 문자열”이 아님).
- 상태 API는 **총 2초 제한**, 응답하지 않는 서비스는 “확인 안 됨”으로 두고 나머지를 보여 준다.

### 8.6 데이터 유효기간 — 오래된 정상값을 보여 주지 않는다 (OP-09)
- 모든 점검 값에 측정 시각. 상태 API와 CLI가 **각자** 판단: 15분 넘으면 **오래됨**, 한 번도 없으면 **측정 안 됨**, 읽지 못하면 **읽기 실패**. 화면은 해당 칸에 표시(목업 `?state=stale`), CLI는 종료 코드 1.
- 점검 큐는 업무 큐와 **별도 처리 슬롯 1개**(업무 적체에 밀리지 않음), 점검별 제한 시간 10초.
- “점검이 30분 넘게 안 돌았다”는 api가 요청 때 판단해 알림을 연다(worker가 죽어도 열림). api까지 죽으면 CLI 몫.

### 8.7 알림 전이표 · 수신자 · 권한 (OP-10 · OP-11 · OP-14)
| 현재 | 점검 결과 | 다음 | 알림 |
|---|---|---|---|
| (없음) | fail 2회 연속 | open(새 발생 ID) | 처음 1회 |
| (없음) | warn | open(warn) | 처음 1회(앱만, 메일 없음) |
| open(warn) | fail | open(fail, 같은 발생 ID) | 수준 상승 1회 |
| open | ok **3회 연속**(15분) | resolved | 해결됨 1회 |
| open | stale · unknown | 그대로 | 없음(대신 ‘점검 멈춤’ 알림이 따로 열림) |
| open | 계속 | 그대로 | 마지막 통지 + 24시간마다(확인했으면 멈춤) |
| resolved | 다시 fail | **새 발생 ID**로 open | 처음 1회 |
- `ops.alerts`에 **key별 열린 행 유일 제약**, 조건부 갱신(`WHERE state='open' AND version=?`). 상태 변경과 알림 outbox를 **같은 트랜잭션**. 중복 억제 키 = 발생 ID · 이벤트 종류 · 회차 · 수신자 · 채널.
- **확인(ACK)**: 다시 알림만 멈춘다(원인 해결 전에는 닫히지 않음). ACK와 감사 기록은 같은 트랜잭션. 목업과 같다.
- **수신자**: 발송 때마다 사용 중 · 기한 내 · `settings` 권한을 다시 검사. Admin이 없으면 기관 담당자에게 **제한 문구**(무엇이 · 누구에게 연락 — 서버 경로 · 오류 원문 없음). 둘 다 없으면 ‘수신자 없음 보류’ + CLI 표시, 적격자가 생기면 열린 알림을 넘겨 줌. 운영 메일은 **B3 별도 정책**(앱 알림과 독립, 실패 재시도 3회).
- **DB 역할 분리**: `neodb_backup`(백업 실행 — 03 §6 그대로)과 **`neodb_ops_writer`**(호스트 실행기 결과 기록 — `ops` USAGE + `backup_runs` · `service_starts` INSERT만, SELECT · UPDATE · DDL 없음). `neodb_app`은 `ops` 읽기 + `alerts` ACK 열만 갱신, 전이 · 보존은 worker 전용 역할 `neodb_ops_worker`. 마이그레이션은 `neodb_migrate`. (§3.3의 “`neodb_backup`은 INSERT만”은 이것으로 바꾼다.)
- 호스트 CLI 실행은 **호스트 저널**(`journald`, 운영자 계정)에 남기고, DB가 살아나면 `ops`로 대조 기록(즉시 DB 감사를 약속하지 않음).

### 8.8 로그 — 키 가리기가 아니라 허용 목록 (OP-13)
- 출처별 **허용 필드만** 남긴다: 경로는 템플릿(`/api/v1/models/:id`), 요청 body · header · query 원문 · SQL 바인드 값 · 자유 형식 stderr는 **기본 배제**. 오류는 이름 · 코드 · 스택(앱 코드 줄만), 메시지는 정해진 오류 코드 문구로.
- 요청 ID는 **nginx가 생성 · 덮어씀**(밖에서 온 `X-Request-Id`는 버림), 서비스는 내부망에서만 받는다.
- pgBackRest · rsync 출력은 종료 코드 · 정해진 요약 줄만 로그로, 원문은 호스트 제한 디렉터리.
- **지원 번들**은 별도 허용 목록: 사용자 ID · 문서 키는 가명 처리, 수집 기간 · 잘림 여부를 표지에 표시, 호스트 운영자만 만들 수 있다.
- 로그 예산: Docker `local` 100MB × 10은 **용량 상한**이지 24시간 보존 약속이 아니다 → 번들은 “있는 만큼”으로 표시.
