## 2. ① 사전 검색

검색 1회 = 30건 한 쪽 + 전체 건수(목록 화면이 실제로 하는 질의). 검색어 150개씩, 같은 검색어로 비교했다. 단위는 ms.

| 검색 | 1.7만 건 색인 없음 p95 | 1.7만 trigram p95 | 5만 색인 없음 p95 | 5만 trigram p95 | 20만 색인 없음 p95 | 20만 trigram p95 |
|---|---|---|---|---|---|---|
| 이름 부분 일치 3자 | 10.1 | **2.2** | 31.0 | **2.1** | 57.2 | **2.2** |
| 이름 부분 일치 2자 | 10.8 | 9.8 | 40.0 | 26.6 | 54.7 | 69.5 |
| 초성 3자 | 8.4 | **3.4** | 13.3 | **4.3** | 57.4 | **9.3** |
| 초성 2자 | 7.1 | 4.4 | 13.9 | 17.2 | 396.4 | **432.5** |
| 약어 3자 | 12.5 | **2.3** | 27.6 | **3.0** | 53.7 | **8.7** |
| 통합(이름·약어·초성) 3자 | 16.3 | **2.2** | 60.2 | **2.3** | 106.7 | **3.9** |

**짧은 검색어(2자 이하) 처리 — 20만 건**

| 방식 | p50 | p95 |
|---|---|---|
| 초성 2자 · 부분 일치 + 정확한 총건수 | 110.6 | 412.2 |
| 초성 2자 · 부분 일치 + **총건수 1,000 상한** | 5.7 | **14.4** |
| 초성 2자 · **앞부분 일치**(btree) | 3.3 | **6.9** |
| 이름 2자 · 부분 일치 + 정확한 총건수 | 39.1 | 53.3 |
| 이름 2자 · 앞부분 일치(btree) | 1.0 | 2.5 |
| 이름 1자 · 앞부분 일치(btree) | 2.2 | 4.7 |

**페이지 이동**: 뒤쪽 페이지(OFFSET 16만)는 23.9ms, 키셋(마지막 값 기준)은 0.9ms. 보통 목록의 앞쪽 몇 쪽은 OFFSET으로 충분하다.
**크기**: 20만 건 + 색인 = 76MB.

해석:
- trigram은 **3글자 단위**로 색인하므로 2글자 이하 검색어에는 효과가 없다. 오래 걸리는 원인은 검색 자체가 아니라 **일치하는 수만 건의 총건수 계산**이다. 총건수에 상한을 두면 해결된다.
- 색인 생성 시간이 1.7만 건에서 19초로 20만 건(7.6초)보다 길게 나왔다. 첫 실행의 디스크 준비로 보이며 **재측정이 필요하다**.

## 3. ② ERD 캔버스

수치는 헤드리스 Chrome 기준이다(실제 화면은 더 빠름). 두 번 측정한 값의 범위를 적었다.

| 경우 | 처음 그리기 | 상세 이동(100%) | 축소 이동(30%) | 확대·축소 연속 | 전체 보기 이동 |
|---|---|---|---|---|---|
| 100개 · 화면 밖 생략 · 요약 | 0.3초 | 60fps | 59fps | 28fps | 60fps |
| 300개 · 최적화 없음 | 0.6초 | 47fps | 29fps | 25fps | **13fps** |
| 300개 · 화면 밖 생략만 | 0.4초 | 52fps | 29fps | 14fps | **13fps** |
| 300개 · 화면 밖 생략 + 요약(LOD 1) | 0.4~0.6초 | 40~56fps | 41~45fps | 16~18fps | 26~29fps |
| 300개 · + **영역 묶음(LOD 2)** | 0.4~0.5초 | 45~56fps | 38~45fps | 16~19fps | **60fps** |
| 1,000개 · 화면 밖 생략 + 묶음 | 1.3~1.7초 | **21fps** | 15fps | 6~7fps | 60fps |

| 자동 배치 (elkjs layered, 직각 연결선, Worker) | 300개 | 1,000개 |
|---|---|---|
| 배치 계산 | 0.6~1.2초 | 2.9~4.0초 |
| 그동안 화면 멈춤 | 0~3% | 0~1% |
| 결과 적용 | 10~120ms | 22~30ms |

해석:
- **화면 밖 생략**(`onlyRenderVisibleElements`)만으로는 전체 보기가 빨라지지 않는다. 전체 보기에서는 모든 노드가 화면 안에 있기 때문이다.
- **요약(LOD 1)** 은 노드 크기와 연결점을 그대로 두어 선이 흔들리지 않는다(22 §6-5 채택안). 그래도 300개를 모두 그려 26~29fps에 그친다.
- **영역 묶음(LOD 2)** 에서는 노드 수 자체가 줄어 300개든 1,000개든 60fps다. 이것이 설계 §3.1의 답이다.
- 1,000개를 **한 캔버스에서 편집**하면 상세 화면에서도 약 21fps다. React Flow가 매 프레임 1,000개 노드와 1,667개 관계를 훑기 때문이다. 업무 영역은 수백 개 이하로 두고, 1,000개는 시스템 전체 조회(묶음 보기)로만 보는 지금 설계가 맞다.
- **확대·축소를 연속으로 할 때**가 가장 약하다(300개 16~19fps). 상세도 단계가 바뀌는 순간 모든 노드를 다시 그리기 때문이다. 구현할 때는 **확대가 멈춘 뒤 단계를 바꾸고**(약 150ms 지연), 요약 전환은 CSS로만 처리하는 방식을 검토한다.
- 미니맵을 꺼도 차이가 거의 없었다(1,000개 21.4 → 21.4fps).

## 4. ③ 표 가상화와 엑셀

**표** (행 높이 32px, 6열)

| 경우 | 처음 그리기 | 화면에 있는 행 | 스크롤 |
|---|---|---|---|
| 5만 행 · 가상화 | 71ms | 41 | 55fps |
| 20만 행 · 가상화 | 79ms | 41 | 59fps |
| 2,000행 · 가상화 안 함 | 856ms | 2,000 | **1.8fps** |
| 5,000행·5만 행 · 가상화 안 함 | 3분 안에 측정 끝나지 않음 | — | — |

**엑셀** (용어 양식 8열, 서버 측 Node)

| 행 | 파일 | 쓰기 | 스트리밍 읽기+검사 | 전체 읽기+검사 | 전체 읽기 추가 메모리 |
|---|---|---|---|---|---|
| 2만 | 0.8MB | 0.3초 | 0.5초 | 0.5초 | 91MB |
| 5만 | 2.0MB | 0.5초 | 0.8초 | 1.2초 | 102MB |
| 10만 | 4.1MB | 0.9초 | 1.4초 | 2.1초 | 243MB |
| 20만 | 8.1MB | 2.0초 | 3.3초 | 5.5초 | **778MB** |

해석:
- 스트리밍 읽기는 행 수에 비례해 시간이 늘지만 메모리는 거의 늘지 않는다. 전체 읽기는 메모리가 급격히 늘어나 동시 업로드에 위험하다.
- 이 양식은 약 2.4MB에 10만 행이 들어간다. 그래서 **20MB 제한만으로는 행 수가 사실상 제한되지 않는다**(약 50만 행).
- 실제 검증은 읽기보다 무겁다(사전 대조·분해·3방향 비교). 검증 시간은 구현 설계에서 다시 잰다.

## 5. ④ Yjs 공동 편집 (같은 PC, 네트워크 지연 제외)

| 항목 | 결과 |
|---|---|
| 문서 크기 (300 엔터티·속성 3,600·관계 500) | 449KB (편집 약 600건 뒤 저장본 456KB) |
| 처음 만들기 | 25ms |
| 새 사용자가 처음 받기 | **64ms** |
| 편집 전달 (200회) | p50 0.4ms · **p95 0.8ms** · 최대 6.6ms |
| 같은 칸을 둘이 동시에 100번 수정 | 한 값으로 **수렴** |
| 사용자별 되돌리기 | A가 되돌리면 A의 변경만 되돌아가고 B의 변경은 남음 — **통과** |
| 표준 맞추기 일괄 변경(속성 50개)을 한 묶음으로 | 되돌리기 한 번에 50개 모두 원래대로 — **통과** (§13.1-5) |
| 서버가 정한 읽기 전용 접속 | 조회자의 편집이 다른 사람에게 **전달되지 않음** — 통과 (§13.1-1) |
| 오프라인 병합 (양쪽 200건씩) | 다시 연결 후 **99ms**에 수렴 |
| 서버 재시작 | 저장본에서 복구, 다시 받기 174ms, 내용 그대로 — 통과 |

해석:
- §13.1-6의 착수 조건(두 브라우저 동기화, 300 엔터티 로딩·병합, 재시작 복구, 오래 끊긴 클라이언트 병합)은 **같은 PC 기준으로 모두 통과**했다. W1 실시간 결정은 유지한다.
- 읽기 전용 접속은 서버가 막지만 조회자의 **화면에는 자기 편집이 남는다**. 화면도 읽기 전용으로 막아야 한다.
- 남은 측정: 사내망 지연 조건, 동시 접속 20명, 오래 쓴 문서의 크기 증가(삭제 흔적 정리), 저장소를 파일 대신 DB에 두었을 때.

## 7. 측정 한계

- ERD·표 수치는 **헤드리스 Chrome**에서 쟀다. GPU를 쓰는 실제 브라우저에서는 더 빠를 것이다. 실제 사용자 PC(사내 표준 사양)에서 다시 재야 한다.
- 실행할 때마다 ERD 수치가 ±15% 정도 흔들렸다. 그래서 두 번 측정한 범위로 적었다.
- 사전 검색의 짧은 검색어 '총건수 상한' 방식은 상한 안에서만 정렬하므로 결과 순서가 완전하지 않다. 화면 문구로 보완한다.
- 공동 편집은 같은 PC의 웹소켓이다. 사내망 지연과 동시 20명은 재지 않았다.
- 엑셀은 읽기와 간단한 검사까지만 쟀다. 사전 대조·분해·3방향 비교를 넣은 실제 검증 시간은 구현 설계에서 잰다.
