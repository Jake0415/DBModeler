## 0. 한눈에 보기

| 영역 | SWS (구현) | DBModeler (설계) | 핵심 차이 | 판단 |
|---|---|---|---|---|
| 사전 관리 | 전역 사전 1개, 단일 DA 결재, 이력 스냅샷, V0 삭제, 엑셀 일괄 신청(50,000행) | 공통+기관 2세트, **설정형 결재선**(DA→기관 담당자), 후보 큐, 엔터티 용어, **엑셀 왕복 편집**(기준본·3방향 비교·반영본) | 구조는 거의 같고 우리가 확장한 형태. SWS는 **영구 삭제·연결 진단·사용처 색인**이 더 구체적 | 구조 유지, ☆ 3개 채택 검토 |
| 오류 검사 | 검증 엔진 1개를 입력·엑셀·신청·승인이 공유, **TS·Python 엔진을 공통 테스트 케이스로 일치**, 설정형/고정형 규칙 분리, 정책 버전 스냅샷, 검증 토큰 | 같은 흐름(① 권한 → ② 입력 형식 → ③ 업무 규칙, ③은 신청·승인 때 다시 실행), ⛔/📝/⚠ 3단계, 분해 의심·복합어 경고 추가 | 원칙은 같고 **구현 장치**(공통 테스트 케이스·검증 토큰·정책 버전)를 SWS가 이미 갖춤 | 구현 설계에 장치 4개 채택 |

| 공동 편집 | **문서 단독 편집 lease(90초) + 저장 버전 검사**. 실시간 엔진(op log·필드 버전)은 만들었으나 **비활성(423)** — 2026-11-02 사용자 확정으로 단독 편집 채택 | **Yjs CRDT 실시간 공동 편집**(Hocuspocus), 잠금 없음 | 가장 큰 차이 | **결정: W1 실시간 유지**(§6-1, ux/03 §13.1) |
| 대용량 | 화면 밖 노드 생략, 50개 이상·35% 미만 축소 요약, 표 가상화 없음, OFFSET 페이징, ILIKE(초성·trigram 없음), NDJSON 스트리밍 검증, 모델 = JSON 1건 | LOD(묶음 보기)·미니맵, 목표 300 엔터티/500 관계 60fps, 서버 페이징, **초성 검색**, 비동기 검증, 엑셀 20MB(행 상한은 측정 후) | 둘 다 **성능 목표 미측정**. SWS 실측 사례 174 테이블·2,590 컬럼 | 측정 스파이크로 확정(§6-6) |

## 1. 표준사전 관리 기능

### 1.1 데이터 모델·수명주기

| 항목 | SWS 구현 | DBModeler 설계 | 차이 |
|---|---|---|---|
| 사전 범위 | 전역 사전 1개(프로젝트·기관 ID 없음) | 공통(행안부 시드, 읽기 전용) + 기관 1개 고정, 공통 우선·충돌 거부 (30 §2) | ★ 세트 구분 |
| 단어·도메인·용어·코드 구조 | 단어·용어·도메인(`managed_domains`, standard/business)·그룹·분류·데이터타입·공통코드 별도 테이블 | 같은 구조 + 용어 유형(속성/엔터티), 엔터티 분류어·접미, 도메인 보안 속성 | ＝ 기본, ★ 확장 3개 |
| 용어 ↔ 단어·도메인 연결 | 용어에 `word_ids`(JSON)·`standard_domain_id`(FK) | 구성 단어 ID 목록(순서)·도메인 ID, 엔터티 용어는 도메인 없음 | ◐ 엔터티 용어만 다름 |
| 버전 | **두 가지**: 제정차수(원본 개념, 식별자 일부) + 내부 `version`(낙관적 잠금 정수) | 항목 버전 V1·V+1(승인 시) + 제정차수(공표 시 +1, 07 §4) | ◐ 우리 V는 사용자에게 보이는 개정 번호, SWS version은 잠금용 |
| 이력 | 단어·용어·도메인별 이력 테이블에 before/after JSON, 반영 구분(초기 적재/데이터 보완/사용자 승인) | 같은 방식 + **칸별 전후 표시**(SC-16·07 E5) | ＝ |
| 사용 상태 | 사용/미사용, 삭제 = `is_deleted` + 화면 "V0" | 사용/미사용, 삭제 보관 V0 (MD-24) | ＝ |
| **영구 삭제** | V0 → DA/Admin이 **대상 명칭을 정확히 입력**하고 사유를 남겨야 함. 원본·이력은 물리 삭제, `dictionary_purge_logs`에 기록. 참조가 남아 있으면 차단 | "영구 삭제는 사유 기록, 결재 기록 보존, 복원 없음"까지만 정의 (MD-24) | ☆ 확인 절차·수행 로그 구체화 |
| 결재 | 단일 결재(DA·Admin 중 먼저 처리), 자기 승인 허용·본인 반려 불가, 직접 등록·수정 API는 409 | **설정형 결재선**: DA(필수) → 기관 담당자(선택), 참조자, 자기 승인 사유 필수, 모델 확정도 결재 (MD-20·25·26) | ★ 다단계·모델 확정 |
| 신청 묶음 크기 | 신청 1건에 1~50,000행 스냅샷 + 행별 경고 | 엑셀 1회 업로드 = 신청 1건(W1), 행 상한은 부하 측정 후 (07 §4) | ⚠ 우리 상한 미정 |
| 승인 시 반영 | advisory lock + `LOCK TABLE` 아래에서 **현재 규칙으로 다시 검사**한 뒤 반영·이력 기록. 새 분류는 이때 함께 생성 | 매 단계 승인 시 재검사, 실패하면 승인 취소 + 이력 (MD-20). 목업은 `checkDictDoc`로 재현 | ＝ 원칙, SWS는 잠금 방식까지 구현 |
| 변경 영향 | 단어·도메인 변경 시 연결 용어·분류·코드 건수 경고, 코드값이 새 규격에 안 맞으면 차단, 자동 연쇄 없음 | 같은 규칙 + **모델 사용처** 건수 (MD-11) | ★ 모델 사용처 |
| **연결 진단** | 읽기 전용 그래프(용어→단어, 용어→도메인→분류→그룹)로 **15종 이슈 코드**, 용어 기준 서명(sha256)으로 "설계 적용 뒤 사전이 바뀜" 감지 | 참조 서명(용어·단어·도메인·분류·그룹 ID+버전 해시)으로 재검토 필요 판정 (MD-50·51) | ◐ 서명은 같은 발상. **15종 진단 목록**은 SWS만 있음 ☆ |
| 사용처 색인 | 최신 설계 문서 컬럼 단위로 용어·단어·도메인·코드 참조 색인 | 상세 패널 "사용처" 탭, 재검토 알림 대상(목업) — 색인 구조는 미설계 | ☆ 색인 설계 참고 |

### 1.2 관리 화면·기능

| 항목 | SWS 구현 | DBModeler 설계 | 차이 |
|---|---|---|---|
| 검색 방식 | `ILIKE '%x%'` 부분 일치(명칭·약어·설명·제정차수), 필드 선택 | 통합 검색: 현재명·약어·영문·설명·**초성**·동의어·금칙어·**과거명**(기관 이력), 일치 종류 표시, 빈 검색 = 최근 변경 (07 E6) | ★ 초성·과거명·일치 종류 |
| 초성 검색 | **없음**(코드 전체에서 0건) | 공통·기관 현재명에 적용 (07 §6 합의) | ★ |
| 동의어 | 목록은 `synonyms_text` 필터로만, 분석기에서는 표준 단어로 치환 | 검색 결과에 "동의어: x" 표시 + 분석기 치환 (MD-04) | ◐ |
| 과거 이름 | 별도 변경이력 화면에서 before/after JSON을 ILIKE로 검색 | 통합 검색에서 기관 과거명 일치 (07 E6) | ◐ |
| 목록 | 서버 정렬 + OFFSET/LIMIT(최대 200, 기본 30), 정렬 키 화이트리스트, 전체 탭은 UNION ALL | 서버 정렬·페이징·종류별 탭 + 전체 탭 (ST-R03), 행 높이 32px 고밀도 | ＝ |
| 필터 | 그룹·분류·동의어·타입·길이 범위·금칙어 유무·원본 폐기·결재 대기·도메인 연결 여부 | 종류·출처(공통/기관)·도메인그룹·변경 기간·진행 중 신청 | ◐ SWS 필터가 더 세밀(길이 범위·원본 폐기·도메인 연결) ☆ |
| 신청 폼 | 신청 목록에 쌓은 뒤 일괄 신청, 용어명 입력 후 600ms 자동 분석, 입력 중 중복 미리 조회 | 같은 흐름(대기 목록 → 신청, 입력 멈추면 분석, 후보 선택) (MD-01~04) | ＝ |
| 용어 추천 | 승인 용어 ILIKE 최대 300건 + 점수(약어 일치 70·용어명 70·동의어 50·토큰 비율 40·설명 10, 상한 100), **매칭 근거 반환** | 표준 맞추기 4상태 일괄 화면 + 추천(21: "추천 엔진은 재사용" 방침) | ◐ 점수 체계는 SWS 참고 |
| 용어별 도메인 자동 검색 | 계획만 있음(미완료). 현재는 마지막 형식단어 분류의 도메인만 | 형식단어 기준 도메인 추천 + 형식단어 아님 ⚠ (MD-04) | ＝ (둘 다 형식단어 기준) |
| 중복 탐지 | 단어: 이름+약어 모두 같으면 차단, 한쪽만이면 사유, 영문명은 설정. 도메인·용어: 명칭 casefold 중복. **코드: 코드값 집합 Jaccard 유사도** | 단어 규칙 같음 + **복합어 중복 경고**(MD-07)·**분해 의심**(MD-06) | ★ 복합어·의심, ☆ 코드 유사도 |
| 엑셀 일괄 | XLSX/CSV 20MB·50,000행, 헤더명 매핑, 원본 미리보기 → 스트리밍 검증 → 정상 행만 부분 신청, 행 분류(신규/변경/동일/대기 동일/대기 다름/오류) | 같은 5색 분류 + **왕복 편집**: 편집용 내려받기(기준본 기록) → 3방향 충돌 비교 → 화면 안 보정(F8·자동 수정) → 보정본 → 반영본 재업로드로 왕복 완료 확인 (07 E1~E5) | ★ 기준본·3방향·보정·반영본 |
| 오류 보고서 | 2시트 XLSX: "검증 결과"(오류 셀 붉게) + **"오류 및 수정 가이드"(규칙별 고치는 법·예시)** | 오류 행 내려받기 — 칸 메모에 규칙·고치는 법 (07 E3) | ◐ SWS는 가이드를 **별도 시트**로 ☆ |
| 업로드 이력 | 브라우저 로컬 "관리 대상 파일" 추적 | 서버 업로드 이력 SC-15(묶음·연결 신청·보정본·반영본·30일 보관) | ★ |

## 2. 오류 체크 루틴·방식

### 2.1 규칙 체계

| 규칙군 | SWS: 검사 내용 / 시점 / 심각도 / 설정 | DBModeler 설계 | 차이 |
|---|---|---|---|
| 입력 형식 | 필드별 최대 길이·공백 금지·허용 문자 9종·특수문자 선택·숫자 시작 금지·`__` 금지·**Oracle/PostgreSQL 예약어**·DBMS 길이 상한 / 입력 즉시(TS) + 서버(신청·엑셀·승인) / 기본 차단(코드값만 경고) / **DB의 JSON 정책 + 검수기준 화면 + 정책 버전·이력** | 검수 기준(필수·길이·허용 문자·차단/경고), 프런트·서버·엑셀 동일 적용, DBMS 길이는 시스템 DBMS 기준 (30 §4) | ◐ 예약어 검사·정책 버전 관리 ☆ / DBMS 4종 기준 ★ |
| 업무 규칙(고정) | 금칙어, 동의어·금칙어 충돌, 중복, 형식단어↔분류, 도메인명 = 분류+타입+길이, 용어 = 단어로만 분해·후보 1개·약어 = 단어 약어 `_` 결합, 형식단어 분류 도메인만 / 신청 준비·엑셀 미리보기·승인 재검사 / 차단(중복 한쪽은 사유, 형식단어 아님은 경고) / **해제 불가** | 같은 규칙 (MD-01~04) + 분해 후보 여러 개면 **엑셀에서 선택**(MD-09, SWS는 오류) + 1음절 의심 + 복합어 경고 | ◐ 우리가 완화·확장 |
| 데이터타입 | 등록된 타입·활성 여부·길이 필수/불가·scale ≤ length·시간 정밀도 0~9·FLOAT 1~53 / 모든 쓰기 경로 | DataType(타입 코드·길이 방식·소수점 + DBMS별 물리 타입) (30 §2.1) | ＝ (세부 범위는 SWS 참고) |
| 상위 변경 영향 | 사용 중 하위가 있으면 미사용 전환 차단, 코드값이 새 규격에 안 맞으면 차단, 연결 건수 경고 | 같음 + 모델 사용처 (MD-11) | ★ |

## 7. 근거·한계

- SWS 근거는 `backend/app/services/*`, `backend/app/models/*`, `frontend/src/features/{modeling,erd,standard-dictionary,…}`, `frontend/package.json`, `docs/architecture/{validation-rules,modeling-redesign}.md`, `docs/superpowers/plans/2026-11-*`를 코드로 읽어 확인했다. 핵심 사실 6개(React Flow 12·dagre, lease 90초, 공동 편집 423, 사전 엑셀 50,000행·20MB, 초성 검색 0건, 화면 밖 노드 생략)는 직접 다시 확인했다.
- SWS를 실행하거나 성능을 측정하지는 않았다. "성능 목표 미확정"은 SWS 문서의 서술이다.
- SWS의 공동 편집 비활성 **이유**는 코드 메시지("기존 공동 문서는 읽기 전용입니다. 단독 편집 사본을 만드세요")와 `modeling-redesign.md` 기록까지만 확인했다. 운영 판단의 배경은 §6-1에서 따로 확인해야 한다.
