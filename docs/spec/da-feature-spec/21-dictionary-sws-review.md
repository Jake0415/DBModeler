## 1. 결론 (제안)

**적용한다 — sws 사전 구조를 기반으로 쓰고, 부족한 5가지를 확장한다.** docuCBD 안(20-priority Q-1)을 이 안으로 대체한다.

| 판단 근거 | 내용 |
|---|---|
| 같은 도메인 | sws는 행안부 공공데이터 공통표준(단어·도메인·용어·코드)을 그대로 관리항목으로 쓰고, 공통표준 2025.11 시드(단어 3,284·도메인 129·용어 13,176)를 갖고 있다 (`backend/seed/public-standard-2025-11.json.gz`) |
| DA# 핵심 개념이 이미 있음 | 도메인그룹 → **도메인분류** → 도메인 3단계, **형식단어**(분류어) → 도메인분류 연결, 이음동의어·금칙어, 제정차수, 단일 DA 결재, 헤더 기반 엑셀 업로드 |
| DA# 문제를 이미 피함 | 엑셀은 **헤더명 매핑**(F-06·F-25 해소), **미리보기 → 검증 → 유효 행만 제출**(F-19·F-27 해소), 결재 시 재검증·버전 충돌 거부, 분해 후보 30개까지 제시(F-04의 단일 오분해 확정 방지) |
| 모델링까지 같은 방향 | 컬럼이 용어 ID·참조 서명(SHA-256)을 저장해 사전 변경을 감지, M:N 연결 엔터티 미리보기, "검사 실패를 오류 0건으로 표시하지 않음", 같은 DB일 때만 FK 생성 규칙 — DA# 분석 결과(F-31, U-02, U-09)와 같은 결론 |
| 기술 스택 | FastAPI·async SQLAlchemy 2·PostgreSQL / React 18·Vite·TypeScript·TanStack Query·Zustand·**@xyflow/react**(React Flow) — 웹 모델러 후보 스택과 같다 |

단, sws는 **기관 하나의 전역 사전**을 전제로 만들어져 있다. DBModeler의 "프로젝트별 분류체계"·"엔터티 용어"·"후보 큐"·"테이블명 준수율"은 sws에 없다(§3).

## 2. sws 사전 구조 요약

```
표준단어 (words)                     표준도메인 (managed_domains, kind=standard)
 ├ 단어명 / 단어 영문약어명            ├ 도메인그룹명 (domain_group, 8개 시드)
 ├ 형식단어 여부 (is_format_word) ─┐   ├ 도메인분류 (classification_id → 50개 시드)
 ├ 도메인분류명 (domain_label)     └──▶├ 도메인명 = 분류명+타입+길이 (예: 연월C6, 번호V20)
 ├ 이음동의어 / 금칙어 (구분자 텍스트)  └ 데이터타입·길이·소수점·허용값·저장/표현형식
 └ 제정차수·use_status·version
                    │ word_ids(JSON)               ▲ standard_domain_id (FK)
                    ▼                              │
               표준용어 (standard_dictionary_terms) ┘
                ├ 용어명 / 용어 영문약어명 (= 단어 약어를 _로 결합)
                └ 허용값·저장/표현형식·제정차수·approval_status·version

표준코드 그룹·코드값 (common_code_*)  — 그룹은 표준도메인에 연결, 값은 계층·유효기간
결재 (approval_requests/events)      — 대상: 단어·도메인·용어·코드, 생성/수정/삭제, before/after
이력 (*_history)                      — 변경 전후 JSON 스냅샷 (append-only)
검수 기준 (dictionary_validation_rules) — 길이·필드 규칙·엔터티 규칙(단일 행)
데이터타입 (data_types)               — 기본 타입·길이 방식·최대 길이·소수점 허용
```

분해 엔진(`services/dictionary_rules.py` `WordAnalyzer`):
- 단어명과 이음동의어로 사전을 만든다.
- 최장 일치를 재귀적으로 적용해 **후보를 최대 30개** 만든다.
- 금칙어가 들어간 경로는 차단한다.
- 약어는 단어 약어를 `_`로 결합한다.
- 마지막 단어가 형식단어이면 그 도메인분류에 속한 도메인만 허용한다.
- **미등록 단어가 있는 용어는 등록을 차단한다.** 분류·도메인은 예외 사유를 적으면 허용한다.

## 4. 열린 질문 재답변 (20-priority §3 대체안)

| ID | 기존 결정안 (docuCBD 기준) | sws 기준 수정안 |
|---|---|---|
| Q-1 | docuCBD 사전 재사용, 분류체계 = 세트 | **sws 사전 구조를 기반으로 쓴다.** 세트(프로젝트 범위) 개념만 docuCBD 설계를 참고해 sws에 추가한다. DA#의 "표준분류체계"는 새 세트에 대응한다. sws의 "도메인분류"는 이와 다른 개념(도메인 세부 구분)이므로 이름을 섞지 않는다 |
| Q-2 | 기본 admin 승인, 자가 승인 옵션은 W2 | **sws 정책을 그대로 쓴다: DA 또는 Admin 단일 결재, 자기 승인 허용**(`approval_rules.py`). 후보 큐 승인도 같은 결재 경로를 탄다 |
| Q-3 | 게이트 A는 경고, 게이트 B는 문법 오류만 차단 | 유지. sws modeling-redesign §14의 "오류 차단 / 경고 확인 기록" 구분과 일치 |
| Q-4 | 전 구간이 등록 단어로 커버될 때만 성공 + 1음절 단어가 끼면 의심 | sws `WordAnalyzer`가 이미 "전 구간 커버, 후보 여러 개면 사용자 선택"이다. **1음절 의심 표시만 추가**한다. 엑셀 업로드에서 후보가 여러 개면 지금은 오류인데, 미리보기에서 고르게 바꾼다 |
| Q-5 | `.damx` 가져오기는 W3, 후보 큐로만 | 유지 |
| Q-6 | 분류어 접미는 사전에, 조합은 명명 템플릿에 | sws의 **형식단어(`is_format_word`)는 도메인 쪽 분류어**다. 엔터티 분류어(기본→`_M`, 내역→`_D`)는 별도 플래그 `is_entity_class_word`와 `entity_suffix`를 단어에 추가한다. 조합은 명명 템플릿에서 한다 |
| Q-7 | 개정은 docuCBD 불변 개정, 금칙어는 그대로, 보안 속성은 추가 | **개정: sws의 "행 수정 + version++ + 전후 JSON 이력 + 제정차수"를 유지한다.** 산출물이 참조한 정의는 sws 방식대로 컬럼의 참조 서명과 스냅샷으로 보존한다. 불변 개정 묶음으로 바꾸지 않는다(sws 데이터·결재와 호환). **금칙어**: 구분자 텍스트를 유지한다. **보안 속성**: 도메인에 추가한다 |

## 5. 통합 방식 (인벤토리 OQ-2와 연결)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. sws에 모델러를 모듈로 추가** | DBModeler 웹 편집기를 sws의 모델링 메뉴 확장으로 개발 | 사전·결재·권한·DDL·엑셀이 이미 있음. 스택이 같음(@xyflow 포함). 데이터 연결이 끊기지 않음 | sws 납품 범위·릴리스 일정과 묶임. sws 모델링(테이블 설계 중심)과 DA#식 다이어그램 편집기의 UX 통합 설계 필요 |
| **B. sws 사전을 서비스로 분리해 API로 사용** | DBModeler는 별도 앱, 사전은 sws API 호출 | 제품 독립성 | 토큰 인증·프로젝트 범위 API 신설 필요. 결재·후보 큐가 두 앱에 걸침 |
| **C. 스키마·규칙 코드를 복사해 DBModeler에 내장** | sws 모델·서비스를 가져와 독자 운영 | 초기 속도 | 두 사전이 갈라짐(이중 유지보수), 시드·규칙 갱신 중복 |

**제안: A를 우선 검토한다.**
- sws는 이미 "표준사전 기반 모델링·ERD·DDL·표준화 검수"를 갖고 있다.
- DA# 분석 결과 W1에 필요한 사전·결재·업로드·DDL 기반의 상당 부분이 sws에 있다.
- DBModeler가 새로 만들 것은 **대화형 다이어그램 편집기**, **"표준 맞추기" 일괄 흐름**, **엔터티 용어·명명 템플릿**, **게이트 A·B**, **프로젝트 세트**로 좁혀진다.
- A가 sws 납품 범위상 어렵다면 B로 간다. C는 권하지 않는다.

이 선택은 DBModeler 저장소의 위치(독립 프로젝트 vs sws 모듈)를 바꾸므로 **사용자 결정이 필요하다.**

## 7. 확인 한계

- sws DDL 생성(`deliverable_ddl.py`, `ddl_type_conversion.py`)은 파일명으로만 확인했다. FK 생성 실제 동작은 코드를 읽어 확인해야 한다.
- sws를 실제로 실행해 보지 않았다(코드·문서 기준).
- 엔터티 준수 판정(`_entity_reasons`)과 용어의 도메인 필수 규칙(`dictionary_rules.py:397-399`)은 코드에서 직접 확인했다. 나머지 항목은 하위 조사 결과를 정리한 것이다.
