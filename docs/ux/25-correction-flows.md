# 25. 잘못 입력한 값 바로잡기 — 시스템 · 업무 영역 · 모델 (v1, 2026-11-24)

> 질문: 시스템을 설정하고 모델링을 시작한 뒤에 업무 영역이나 DB 정보가 잘못 들어간 것을 알게 되면 어떻게 고치나?
> 범위: 목업(`system.html` · `settings.html` · `model.html` · `assets/app.js`)을 점검한 결과와 수정 방안.
> 결정(2026-11-24): ① 업무 영역 이름 변경은 **결재 없이 · 감사 로그만** ② 엔터티 영역 이동은 **모델러가 직접**, 다음 확정 결재에서 DA가 확인 ③ **DBMS는 바꿀 수 없다** — 시스템 등록 때 정하고, 잘못 넣었으면 올바른 시스템을 새로 등록해 업무 영역을 옮긴다.

## 1. 지금 목업에서 고칠 수 있는 것 / 없는 것
| 잘못 들어간 것 | 지금 고칠 수 있나 | 근거 |
|---|---|---|
| 엔터티 · 속성 · 관계 내용 | **됨** — 작업 중이면 바로 고침(Ctrl+Z · 버전 비교). 검토 중이면 회수 뒤 고침. 확정본이면 새 작업 버전 → 다시 확정 결재 | 모델 트리 메뉴 이름 바꾸기 · 삭제, 결재 회수 |
| 명명 템플릿 · 타입 매핑 · 시스템 컬럼 | **됨** — 설정 › 시스템에서 저장. 다음 DDL · 물리 반영부터 적용. [영향 미리보기] | settings.html 시스템 탭 |
| 업무 영역 **이름 · 설명** | **안 됨** — 만들 때 이름만 받고 이후 바꾸는 곳 없음 | system.html 새 업무 영역 창만 있음, 트리 영역 메뉴에 이름 바꾸기 없음 |
| 업무 영역 **잘못 만듦(중복 · 오타 · 필요 없음)** | **안 됨** — 삭제 · 보관 없음 | 같음 |
| 업무 영역을 **다른 시스템에 만듦** | **안 됨** — 시스템 간 이동 없음(영역 복제도 같은 시스템 안, 시연만) | app.js 트리 영역 메뉴 '영역 복제'(목업 시연) |
| 엔터티를 **다른 업무 영역에 만듦** | **안 됨** — 다른 영역에서 ‘참조’만 됨, 옮기기 없음 | app.js 엔터티 메뉴 '지금 영역에 참조 추가' |
| 업무 영역 **담당자** | **안 됨** — 화면에 고정 값 | system.html `OWN` 고정 |
| 시스템의 **DBMS · 버전 · 스키마** | **안 됨** — 설정에서 조회 전용(“시스템을 등록할 때 정합니다”)인데 **시스템 등록 · 수정 화면이 없음** | settings.html `#sys-dbms` disabled, `SYSLIST` 고정 |
| **시스템 자체** 추가 · 이름 · 삭제 | **안 됨** | `SYSLIST` 고정 2개 |

→ **모델 안의 내용은 고칠 수 있지만, 그 틀(시스템 · 업무 영역)은 한 번 만들면 고칠 길이 없다.** 이것이 빈칸이다.

## 2. 바로잡기 원칙 (사용자 · 역할 관리와 같은 규칙)
1. **이름 · 설명 · 담당 같은 정보 값은 언제든 고친다.** 결재 없이 고치고, 감사 로그에 남긴다. 다른 곳에 보이는 이름(참조 · 결재 문서 제목 · 산출물)은 새 이름으로 보인다. 이미 만든 결재 문서와 확정본에는 당시 이름이 남는다.
2. **모델 내용과 구조는 상태에 따라 고친다.**
   | 상태 | 고치는 법 |
   |---|---|
   | 작업 중 · 확정본 없음 | 바로 고침 · 지움 |
   | 검토 중(결재 진행) | 먼저 **회수** → 작업 중으로 돌아와 고침 |
   | 확정본 있음 | 확정본은 그대로 두고 **새 작업 버전**에서 고침 → 다시 확정 결재 |
3. **이력이 있으면 지우지 않고 ‘사용 중지(보관)’한다.** 확정본 · 결재 문서 · 다른 영역의 참조가 하나라도 있으면 삭제는 막고 보관만 된다(계정 삭제와 같은 규칙). 보관한 것은 목록에서 숨고 조회 전용, 언제든 다시 쓸 수 있다.
4. **DBMS는 시스템의 정체성이라 바꾸지 않는다.** 등록 창에서 “등록 뒤 바꿀 수 없습니다”를 확인받는다. **시스템 이동처럼 물리 설계에 영향이 큰 일은 하기 전에 영향을 보여 준다.** 바뀌는 컬럼 수 · 테이블 수 · 업무 영역 · 진행 중 결재를 보여 주고 확인 뒤 저장한다(설정의 ‘영향이 큰 변경’ 확인 창과 같은 꼴).
5. **확정본은 바꾸지 않는다.** 이미 확정한 버전의 DDL · 산출물은 확정할 때의 값(DBMS · 이름 규칙)으로 남는다. 새 값은 작업 버전과 다음 확정부터 적용된다.

## 3. 경우별 수정 방안
### 3-1. 업무 영역 이름 · 설명 · 담당이 틀림
- **어디서**: 시스템 홈 업무 영역 표의 행 메뉴 ⋯ › **[영역 정보 수정]**, 모델 트리 영역 메뉴 › 같은 항목.
- **누가**: 그 영역 담당 모델러 · 관리자.
- **무엇을**: 이름(같은 시스템 안에서 중복 금지) · 설명 · 담당 모델러.
- **결과**: 바로 적용 · 감사 로그 ‘업무 영역 정보 수정(이전 → 이후)’. 다른 영역의 참조 이름과 결재함 표시도 새 이름으로 바뀐다. 이미 만든 결재 문서 본문과 확정본은 당시 이름 그대로다.

### 3-2. 업무 영역을 잘못 만듦(오타 · 중복 · 필요 없음)
- **[삭제]**: 확정본 · 결재 문서 · 다른 영역의 참조가 **하나도 없을 때만**. 확인 창에 엔터티 수를 보여 주고, 되돌릴 수 없다고 알린다.
- **[사용 중지(보관)]**: 이력이 있을 때. 트리 · 시스템 홈에서 숨김(‘보관함 보기’로 열기), 조회 전용, 진행 중 결재가 있으면 먼저 회수하라고 막는다. 다른 영역이 참조 중이면 그 영역 목록을 보여 주고, 참조는 ‘원본 보관됨’으로 표시한다.
- **중복으로 만든 경우**: [다른 영역으로 옮기기](3-4)로 엔터티를 맞는 영역으로 옮긴 뒤 빈 영역을 삭제한다.

### 3-3. 업무 영역을 다른 시스템에 만듦
- **확정본 · 결재 이력이 없을 때**: 영역 메뉴 › **[다른 시스템으로 옮기기]**(관리자). 대상 시스템의 DBMS · 명명 템플릿 · 타입 매핑으로 물리 모델을 다시 만든다는 영향을 보여 준 뒤 옮긴다. 다른 영역에서 참조하던 관계는 끊김 목록으로 보여 준다.
- **확정본이 있을 때**: 옮기지 않는다. **[다른 시스템으로 복제]**로 대상 시스템에 새 영역(v1 작업 중)을 만들고, 원본은 3-2 규칙으로 보관한다. 원본 이력은 그대로 남는다.

### 3-4. 엔터티를 다른 업무 영역에 만듦
- **어디서**: 엔터티 메뉴 › **[다른 영역으로 옮기기…]** → 같은 시스템의 영역 고르기.
- **조건**: 두 영역 모두 **작업 중**이고 편집 권한이 있어야 한다. 검토 중이면 회수부터.
- **결과**: 원래 영역에서 빠지고 대상 영역에 추가된다(속성 · 자기 참조 관계 포함). 원래 영역에 남는 엔터티와의 관계는 **끊긴다** — 옮기기 전에 목록을 보여 주고, 대상 영역이 확정된 뒤 참조로 다시 잇는다. Ctrl+Z로 되돌리지 않고, 되돌리려면 다시 옮긴다. 두 영역의 다음 확정 결재에 ‘이동(→ ○○ 영역)’ · ‘이동(← ○○ 영역)’으로 보인다(버전 비교 · 결재 변경 내역).
- 엔터티가 원래 영역 **확정본에 이미 있으면** 확정본은 그대로이고, 다음 확정 때 ‘삭제(이동)’로 결재받는다.

### 3-5. 시스템 DBMS가 틀림 — 바꾸지 않고 옮긴다
- **DBMS는 바꿀 수 없다.** 시스템 정보 창에서 DBMS는 조회 전용이다. 시스템 등록 창에서 DBMS를 고를 때 “등록 뒤 바꿀 수 없습니다 — 다른 DBMS가 필요하면 시스템을 새로 등록합니다”를 확인받는다.
- **잘못 넣은 경우 바로잡는 순서**
  1. 설정 › 시스템 › **[시스템 등록]**: 올바른 DBMS로 새 시스템을 만든다.
  2. 원래 시스템의 업무 영역마다 **[다른 시스템으로 옮기기]**(확정본 없음) 또는 **[다른 시스템으로 복제]**(확정본 있음)를 한다. 대상 시스템의 타입 매핑 · 명명 템플릿으로 물리 모델을 다시 만든다는 영향을 미리 본다.
  3. 원래 시스템은 업무 영역이 남지 않으면 **[삭제]**, 남으면 **[사용 중지(보관)]**한다.
- **버전 · 기본 스키마**는 같은 DBMS 안의 정보라 [시스템 정보]에서 고친다(관리자 · 감사 로그). 확정본과 이미 만든 DDL은 당시 값으로 남는다.

### 3-6. 명명 템플릿 · 타입 매핑이 틀림 (지금도 됨 — 보강)
- 지금: 설정 › 시스템에서 저장 → 다음 DDL · 물리 반영부터 적용.
- **보강**: 모델 › 물리 보기에 **[이름 · 타입 규칙 다시 적용]**을 둔다. 작업 버전의 테이블 · 컬럼 · 제약조건 이름과 타입을 새 규칙으로 다시 만든다. 바뀌는 항목을 미리 보여 주고 고른 것만 적용한다. 직접 고친 물리명은 ‘직접 지정’이라 건너뛴다.

### 3-7. 시스템 자체가 틀림(이름 · 중복 · 필요 없음)
- **어디서**: 설정 › 시스템 탭 시스템 고르기 옆 **[시스템 등록]** · **[시스템 정보]**.
- 이름 · 설명은 3-1처럼 바로 고친다. 삭제는 업무 영역이 하나도 없을 때만 하고, 있으면 보관한다(3-2).

## 5. 결정 (2026-11-24)
1. 업무 영역 이름 변경 — **결재 없이 바로**, 감사 로그에 이전 → 이후.
2. 엔터티 영역 이동 — **모델러가 직접**(두 영역 모두 편집 권한). 다음 확정 결재의 변경 내역에 ‘이동’으로 보이고 DA가 확인.
3. DBMS 변경 — **허용하지 않음.** 새 시스템 등록 → 업무 영역 옮기기/복제 → 원래 시스템 보관 · 삭제.

## 6. 목업 반영 (2026-11-24)
- **시스템 홈**: 업무 영역 행 끝 ⋯ — [영역 정보 수정](이름 · 설명 · 담당, 같은 시스템 안 이름 중복 금지) · [다른 시스템으로 옮기기 · 복제](확정본 · 결재 이력이 없으면 옮기기, 있으면 복제 · 영향 목록) · [사용 중지 · 삭제](이력 없으면 삭제, 있으면 사유 받고 보관, 결재 중이면 막음). 표 아래 ‘보관함’ + [다시 사용]. 트리 영역 메뉴의 같은 세 항목은 시스템 홈의 이 창을 연다(`?area=…&act=edit|move|off`).
- **설정 › 시스템**: [시스템 등록](이름 · 코드 · 설명 · DBMS · 버전 · 스키마, “DBMS는 바꿀 수 없음” 확인 필수) · [시스템 정보](DBMS 조회 전용 + 바로잡는 순서 안내, 이름 · 설명 · 버전 · 스키마 수정, 남은 영역이 없으면 삭제 · 보관된 영역만 있으면 사용 중지 · 다시 사용). 사용 중지한 시스템은 상단 시스템 목록에서 빠진다.
- **모델**: 엔터티 메뉴 [다른 영역으로 옮기기…] — 같은 시스템의 편집 가능한 영역만 고를 수 있고(결재 중 · 확정본 · 권한 없음은 이유와 함께 막음), 끊기는 관계를 미리 보여 준다. 두 영역 버전 비교에 ‘이동(→ / ←)’.
- 다른 시스템으로 **복제**할 때 원래 시스템의 다른 영역을 가리키던 참조는 빼고 복제한다(참조는 시스템을 넘지 않음).
- 사용 중지한 업무 영역은 모델 화면 · 트리에서 열리지 않는다 — 보관함에서 [다시 사용]하면 다시 열린다.
- 감사 로그 항목: 업무 영역 정보 수정 · 시스템 이동 · 다른 시스템으로 복제 · 사용 중지 · 다시 사용 · 삭제, 엔터티 영역 이동, 시스템 등록 · 정보 수정 · 사용 중지 · 다시 사용 · 삭제.

## 7. 리뷰 반영 (2026-11-24) — [resolution-correction-flows](review/resolution-correction-flows.md) X-01 ~ X-15
- **엔터티 이동**
  - 실행 직전에 다시 검사한다. 원래 영역을 먼저 저장하고(실패하면 옮기지 않음), 그다음 대상을 저장한다(실패하면 원래 영역을 되돌림). 이동이 끝나면 Ctrl+Z 기록을 비운다.
  - 끊기는 관계의 FK 속성은 일반 속성으로 바꾼다. 개수와 목록은 창에 보여 준다.
  - 대상 영역에 있던 이 엔터티의 참조는 실체로 바꾸고, 관계는 그대로 이어 둔다. 다른 작업 중 영역의 참조는 새 원본을 가리키게 하고, 잠긴 영역은 다음 버전에서 갱신한다고 알린다.
  - 자기 참조 관계는 FK 그룹 이름이 겹치면 새 이름을 붙인다.
- **업무 영역 작업**
  - 모든 작업을 실행 직전에 다시 검사한다: 권한, 결재 중 여부. 막히면 결재함 링크를 단다.
  - 삭제 창의 첫 포커스는 [취소]이고, 삭제한 영역은 기록해 되살아나지 않는다. 없어지거나 보관된 영역에는 모델 저장을 거절한다.
  - 참조 판정에 보관 영역도 넣는다. 이름 중복은 보관함까지 포함해 검사하고, 옮기기 · 복제 · 다시 사용 · 정보 수정 모두에 적용한다.
  - 보관 영역은 보관함 · 결재 링크로 열면 조회 전용으로 열린다.
- **DBMS 바로잡기**
  - 옮기거나 복제할 때 컬럼 타입을 대상 DBMS에 맞게 바꾼다. 예: Oracle → PostgreSQL에서 VARCHAR2 → VARCHAR · NUMBER → NUMERIC · DATE → TIMESTAMP. 바뀌는 건수는 창에 미리 보인다.
  - 대상 기본값은 최근 등록한 시스템이다. 영역이 참조하던 원래 시스템 영역은 영향에 보이고, 먼저 복제한 영역에 대한 참조는 복제본끼리 다시 잇는다.
  - 복제가 끝나면 원래 시스템 홈에 머물고, 원본 [사용 중지] 창이 열린다. 복제본 링크가 함께 보이고 사유는 미리 채워진다. 사용 중지하면 보관함이 펼쳐진다.
  - 시스템을 등록하면 토스트에 [원래 시스템 홈] 링크가 붙는다.
  - 확정 신청 사본에는 당시 DBMS · 스키마(`sysAt`)를 남기고, DDL은 사본을 열 때 그 스키마를 쓴다.
- **설정**
  - 시스템 목록은 저장 직전에 최신 목록을 읽고, 해당 시스템만 바꾼다(탭 간 덮어쓰기 방지).
  - 등록 · 정보 창의 오류는 칸에 표시하고 첫 오류 칸에 포커스를 준다.
  - 사용 중지 · 삭제는 창 안에서 두 번 눌러 확인한다.
  - ‘DBMS를 바꾸면’ 문구를 정리했다.
- **트리**: 시연용 ‘영역 복제’를 없앴다. 권한이 없는 사람의 영역 메뉴는 막히고 이유가 보인다.
- 남겨 두었던 네 가지는 §8에서 목업에 반영했다.

## 8. 남은 네 가지 반영 (2026-11-24)
- **이동 기록을 작업본 · 결재 사본에 고정**
  - 엔터티를 옮기면 원래 영역 작업본의 `moves`에 {엔터티 · 대상 영역 · 당시 이름 · 시각 · 누가}를 남기고, 대상 쪽에는 {출발 영역}을 남긴다.
  - 확정 신청 사본(`doc.model.moves`)에도 함께 저장한다.
  - 버전 비교는 사본의 이동 목록을 먼저 쓴다. 전역 기록은 예전 데이터를 읽을 때만 쓰고, 영역 이름이 나중에 바뀌어도 당시 이름으로 보인다.
- **시스템별 데이터타입 매핑**
  - 설정 › 시스템의 매핑 표는 고른 시스템의 것을 보여 주고, 머리에 그 시스템의 DBMS를 적는다. 저장은 `dbm-typemap-<코드>`.
  - 고친 칸은 저장 막대 ‘시스템’ 건수와 [변경 보기]에 들어가고, [되돌리기] · [이 DBMS 기본값으로]도 된다.
  - 새 시스템은 등록할 때 그 DBMS의 기본 매핑으로 시작한다. 기본값: Oracle · Tibero / PostgreSQL / MySQL.
  - 다른 시스템으로 옮기거나 복제할 때 **두 시스템의 매핑 표를 행끼리 맞춰** 컬럼 타입을 바꾼다. 길이 · 정밀도 인자는 유지하고, 표에 없는 타입은 기본 변환표를 쓴다.
- **시스템 전체 한 번에 옮기기**
  - 시스템 홈 머리에 [모든 영역 옮기기 · 복제](관리자)를 둔다.
  - 대상 시스템을 고르면 영역마다 처리 · 타입 변환 수 · 참조 수를 미리 보여 준다. 처리는 옮기기 / 복제 / 건너뜀(결재 중 · 이름 겹침 이유).
  - 참조되는 영역부터 처리한다. 서로 참조하는 영역(예: 회계 ↔ 영업)은 끝난 뒤 복제본끼리 다시 잇는다.
  - 복제한 원본은 선택에 따라 사용 중지한다(사유 자동).
  - 끝나면 결과 목록과 [원래 시스템 사용 중지] · [새 시스템 홈] 링크를 보여 준다. 감사 로그에는 ‘시스템 전체 업무 영역 옮기기’로 남긴다.
  - 옮긴 영역의 참조도 대상 시스템에 있는 복제본으로 다시 잇는다.
- **담당 시스템을 코드로**
  - 사용자의 담당 시스템은 시스템 코드로 저장한다. 이름으로 저장된 계정은 처음 읽을 때 한 번 바꾼다.
  - 권한 판정(`inScope`)은 코드로 비교하므로 시스템 이름을 바꿔도 담당 범위는 그대로다.
  - 화면에는 이름을 보여 준다(`sysNames`): 설정 사용자 목록 · 계정 패널, 마이페이지, 모델 조회 전용 안내, 홈, 역할 미리 보기.
  - 역할 변경 요청의 ‘담당 시스템 추가’도 코드로 저장한다.
