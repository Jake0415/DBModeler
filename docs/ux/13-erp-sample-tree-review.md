# 통합ERP 예시 데이터와 모델 트리 재검토

> 2026-11-19 · 상태: **적용 완료(목업)**
> 사용자 요청: 트리를 봐도 업무가 낯설어 이해가 안 된다. 회사 업무 ERP에 맞춘 가상 데이터를 최대한 많이 넣어 예시를 정확히 만들고, 그 예시로 메뉴 트리 구조를 다시 검토한다. 사용자가 보자마자 이해할 수 있어야 한다.

## 1. 무엇을 넣었나
기존 예시(요구사항관리)는 그대로 두고, 시스템을 하나 더 만들었다. 왼쪽 트리 맨 위의 **시스템 바꾸기**에서 고른다(주소 `?system=ERP`).

| 시스템 | DBMS · 스키마 | 업무 영역 | 엔터티 | 속성 | 관계 |
|---|---|---|---|---|---|
| 요구사항관리 (기존) | Oracle 19c · RQMS | 2 | 9 | 약 40 | 7 |
| **통합ERP (신규)** | Oracle 19c · ERP | **6** | **63** (+참조 7) | **394** | **79** |

### 1.1 통합ERP 업무 영역
| 영역 | 버전 | 담당 | 주요 엔터티 (분류) | 흐름 다이어그램 |
|---|---|---|---|---|
| 영업관리 | v3 | 정영업 | 기준: 고객기본 · 판매가격기본 / 거래: 고객담당자 · 견적(상세) · 주문(상세) · 출하(상세) · 매출 · 반품 / 이력: 주문상태이력 / 참조: 품목 · 창고(재고) · 사원(인사) | 주문 → 출하 → 매출, 고객 · 견적 |
| 구매관리 | v2 | 한구매 | 기준: 공급사 · 공급사단가 / 거래: 구매요청(상세) · 발주(상세) · 입고검사 · 매입 / 이력: 발주변경이력 / 참조: 품목 · 창고 | 요청 → 발주 → 입고 |
| 재고관리 | v6 | 김모델 | 코드: 품목분류 / 기준: 품목 · 창고 · 저장위치 · 로트 / 거래: 재고 · 입고 · 출고 · 재고이동 · 재고실사 / 이력: 재고수불이력 | 재고 수불 |
| 생산관리 | v1 | 오생산 | 기준: 제품구성(BOM) · 공정 · 설비 / 거래: 생산계획 · 작업지시 · 작업실적 · 자재투입 · 품질검사 / 이력: 설비가동이력 / 참조: 품목 · 창고 | 계획 → 작업지시 → 실적 |
| 회계관리 | v4 | 최회계 | 기준: 계정 · 원가센터 · 거래처 · 은행계좌 / 거래: 전표(상세) · 세금계산서 · 채권 · 채무 · 예산 / 이력: 월마감이력 | 전표, 채권 · 채무 |
| 인사관리 | v5 | 박설계 | 코드: 직급 / 기준: 부서 · 사원 / 거래: 근태 · 휴가신청 · 급여(상세) · 가족 · 교육이수 · 자격증 / 이력: 발령이력 | 급여, 근태 · 휴가 |

### 1.2 데이터를 만드는 규칙 (정확한 예시가 되도록)
- **단어 사전에서 물리명을 만든다**: 고객 CUST · 주문 ORD · 번호 NO · 일자 YMD처럼 단어 약 240개를 정했다. 속성 이름을 단어로 나누어 `주문일자 → ORD_YMD`, `여신한도금액 → CRLMT_AMT`를 만든다. 엔터티는 `기본 → _M`, `내역 → _D`, `이력 → _H`, `상세 → _DTL`을 붙인다(`주문상세내역 → ORD_DTL_D`).
- **마지막 단어(분류어)가 타입과 도메인을 정한다**:

  | 분류어 | 타입 | 도메인 |
  |---|---|---|
  | 번호 | VARCHAR2(20) | 번호V20 |
  | 코드 | VARCHAR2(10) | 코드V10 |
  | 명 | VARCHAR2(100) | 명V100 |
  | 일자 | CHAR(8) | 연월일C8 |
  | 일시 | DATE | 일시T |
  | 금액 · 단가 | NUMBER(18,2) | 금액N18 |
  | 수량 | NUMBER(15,3) | 수량N15 |
  | 율 | NUMBER(5,2) | 율N5 |
  | 여부 | CHAR(1) | 여부C1 |
- **FK는 관계에서 만든다**: 부모의 PK를 자식에 FK로 넣는다. 식별 관계면 자식 PK에도 들어간다. 예: 주문상세내역의 PK는 주문번호 + 주문순번이고, 품목코드가 FK다. 그래서 트리 · DDL · 오른쪽 패널의 FK가 늘 같다.
- **개인정보는 자동으로 표시한다**: 전화번호 · 이메일 · 주소 · 생년월일 · 계좌번호 · 가족명 · 사원명.
- **표준 상태도 실제처럼 섞었다**:

  | 상태 | 예시 |
  |---|---|
  | 미등록 단어 | 견적메모, 배송요청사항, 구매단가, 지시일자, 휴가신청번호 |
  | 조합 가능 | 변경상태코드, 거래상태코드, 손실율 |
  | 예외 | 거래처 사업자등록번호 → 외부 연계 컬럼명 BIZ_NO 유지 |
  | FK 제외 | 재고수불이력 → 대량 적재라 FK 미사용 |
  | FK 누락 | 품목분류 · 부서의 상위 분류/부서 재귀 관계 → 역할명 컬럼 지정 필요 |
- **참조**: 영업 · 구매 · 생산은 품목 · 창고(재고관리)를 참조하고, 영업은 사원(인사관리)도 참조한다. 참조는 읽기 전용이고, 준수율과 개수에 넣지 않는다.

## 2. 예시로 다시 본 트리 — 무엇이 어려웠나
ERP 영업관리(엔터티 12개)를 넣어 보니, 지금 트리에는 다음 문제가 있었다.

| # | 문제 | 왜 어렵나 |
|---|---|---|
| 1 | 엔터티 12개가 한 목록에 섞여 있다 | 고객 · 주문 · 이력이 같은 줄에 있어, 무엇이 기준 정보이고 무엇이 거래인지 한눈에 안 보인다 |
| 2 | 참조 엔터티(품목 · 창고 · 사원)가 내 엔터티 사이에 섞여 있다 | 내가 고칠 수 있는 것과 없는 것이 구분되지 않는다 |
| 3 | 엔터티 줄에 논리명만 있다 | DB 담당자는 `ORD_M`처럼 테이블명으로 찾는데, 마우스를 올려야 보였다 |
| 4 | "보기" · "사용한 표준" · "후보" | 무엇인지 말에서 바로 드러나지 않는다 |
| 5 | 표준 폴더의 "64 · 15" | 숫자가 무엇을 세는지 알 수 없다 |
| 6 | 업무 영역 줄이 이름뿐이다 | 영역이 어떤 업무를 다루는지 처음 보는 사람은 모른다 |
| 7 | 홈 · 시스템 홈의 트리가 240px 고정 | 4단계(영역 › 엔터티 › 분류 › 엔터티)가 되면 이름이 잘린다 |

## 3. 바꾼 트리 구조
```
통합ERP · Oracle 19c · ERP                       ▾  ← 시스템 바꾸기
[ 엔터티·속성·테이블·용어 찾기 ]          [거르기]
업무 영역                                       ＋
▾ 영업관리                                     v3   ← 마우스를 올리면 "고객 · 견적 · 주문 · 출하 · 매출 · 반품 · 엔터티 12"
    모델 · 표준 맞추기 3 · DDL · 산출물               ← 바로가기
  ▸ 다이어그램 3                                     ← 전체 · 주문 → 출하 → 매출 · 고객 · 견적
  ▾ 엔터티 12
    ▾ 기준 정보 2                                    ← 오래 쓰는 정보
        ● 고객기본                       CUST_M
        ● 판매가격기본                   SALE_PRC_M
    ▾ 거래 9                                         ← 업무가 일어날 때마다 쌓이는 정보
        ● 고객담당자내역                 CUST_PIC_D
        ◐ 견적기본                       1          ← 미준수 1
        ● 주문기본 ▸ (펼치면 속성: 주문번호 PK · 주문일자 · 고객번호 FK …)
        …
    ▾ 이력 1
        ◐ 주문상태이력                   1
  ▸ 다른 영역에서 참조 3                             ← 품목기본(재고관리) · 창고기본(재고관리) · 사원기본(인사관리)
  ▸ 관계 16
  ▸ 표준 용어 · 도메인   용어 64 · 도메인 15 · 미등록 2
▸ 구매관리 v2 · 재고관리 v6 · 생산관리 v1 · 회계관리 v4 · 인사관리 v5
```
물리 모드에서는 테이블도 같은 분류(기준 정보 · 거래 · 이력 · 코드)로 묶는다.

| # | 바꾼 것 | 해결한 문제 |
|---|---|---|
| A | **엔터티를 분류로 묶는다**: 기준 정보(M) · 거래(A) · 이력(H) · 코드 · 분류(K). 영역에 엔터티가 7개 이상일 때만 묶는다. 묶음 줄에 마우스를 올리면 뜻이 보인다 | 1 |
| B | **참조를 따로 모은다**: "다른 영역에서 참조" 폴더. 줄에 원본 영역 이름(재고관리 · 인사관리)을 보인다 | 2 |
| C | **엔터티 줄 오른쪽에 물리명을 회색으로 보인다**. 미준수가 있으면 그 자리에 미준수 수를 보인다(물리명은 툴팁) | 3 |
| D | 쉬운 이름으로 바꿨다: 보기 → **다이어그램**, 사용한 표준 → **표준 용어 · 도메인**, 후보 → **미등록** | 4 |
| E | 숫자에 이름을 붙인다: "용어 64 · 도메인 15 · 미등록 2" | 5 |
| F | 업무 영역 줄에 설명(다루는 업무)과 엔터티 수를 툴팁·낭독기 이름으로 붙인다 | 6 |
| G | 홈 · 시스템 홈도 내용에 맞춰 넓어진다(최대 400px) | 7 |
| H | 시스템 바꾸기가 실제로 동작한다. 시스템을 바꾸면 트리 · 시스템 홈 · 홈 · 모델 · DDL(스키마 `ERP.`) · 산출물 제목이 함께 바뀐다. 다른 시스템의 영역 주소로 들어오면 시스템도 자동으로 바뀐다 | — |

## 4. 더 검토할 것 (다음 단계 후보)
- **업무 영역이 많아질 때(10개 이상)**: 업무 영역도 "업무 그룹"(예: 물류 = 구매 · 재고 · 생산, 경영 = 회계 · 인사)으로 묶을지 정해야 한다. 지금 6개는 묶지 않아도 읽힌다.
- **엔터티 분류 기준**: 지금은 이름 끝말(기본 · 내역 · 이력)과 기준 정보 목록으로 정한다. 실제 제품에서는 엔터티의 분류 속성(K · M · A · H)을 모델러가 직접 정한다.
- **영역 사이 관계 보기**: 시스템 전체 ERD에서 영업 → 재고(품목 · 창고) 같은 영역 간 참조가 굵기로 보이는지 ERP 데이터로 다시 본다.
- **T2 메뉴 · T3 배치·참조**는 이 예시 데이터로 진행한다.
