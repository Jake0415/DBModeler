## 0. 한 줄 요약

**IE(Information Engineering, 까마귀발) 표기법**을 바탕으로, 국내 DA 도구(DA# · ERwin · eXERD) 사용자가 익숙한 관례(PK `#`, 논리명 + 물리명 한 상자)를 더하고, 이 제품의 목적인 **표준 준수 상태**를 엔터티 안에 바로 보이게 덧붙였다. 관계명은 2026-11-24부터 **명사형**이다.

## 2. 다른 표현 방식과 비교

### 2.1 관계 표기법 — 7가지

| 표기법 | 다수 / 하나 | 선택성 | 식별 · 비식별 | 속성 표시 | 장점 | 단점 | 주로 쓰는 곳 |
|---|---|---|---|---|---|---|---|
| **IE · 까마귀발** (James Martin) — **지금** | 까마귀발 / 막대 | 원 | 실선 / 점선 | 상자 안 목록 | 한눈에 읽힘, 상자에 속성이 같이 있어 **물리 설계까지 한 그림**, 국내 도구 기본값 | 다항 관계(3개 이상) 표현이 어색함 | DA# · ERwin · eXERD · 대부분의 현업 |
| **Chen** (1976) | 선 옆 숫자 1 · N · M | 이중선(전체 참여) | 이중 마름모 · 이중 사각(약한 엔터티) | 타원(속성마다) | 개념 설계 교육에 좋음, 관계 자체가 마름모 도형이라 관계 속성 표현이 쉬움 | **공간을 매우 많이 씀**, 속성 수십 개면 읽을 수 없음, 물리 설계로 이어지지 않음 | 대학 교재 · 개념 모델 |
| **Barker** (Oracle CASE) | 까마귀발 / 없음 | **선 절반이 점선**(그쪽은 선택) | 선 위 가로 막대(UID 바) | 둥근 상자 안 `#` 키 · `*` 필수 · `o` 선택 | 관계를 양방향 문장으로 읽게 함, `# * o` 기호가 간결 | 선 절반 점선이 익숙하지 않음, 식별 표시가 작음 | Oracle Designer · 일부 국내 공공 산출물 |
| **IDEF1X** (미 연방 표준) | 자식 쪽 **점(●)** · 문자(P · Z · n) | 다이아몬드 · 문자 | 실선 / 점선 + **종속 엔터티는 둥근 모서리** | 상자 위(키) / 아래(일반) 두 칸 | 키 전파 규칙이 엄격 · 정밀, 공공 · 국방 표준 | 기호를 외워야 읽힘(●, P, Z), 처음 보는 사람에게 어려움 | ERwin(선택 가능) · 미국 공공 |
| **UML 클래스 다이어그램** | 선 끝 숫자 `0..*` `1` | 숫자 하한 0 | 표기 없음(합성 ◆ 정도) | 클래스 3칸(이름 · 속성 · 연산) | 개발자에게 익숙, 객체 모델과 같은 그림 | **DB 키(PK · FK) · 식별 관계 개념이 없음**, 연산 칸이 DB에는 필요 없음 | 응용 설계 · 객체 모델 |
| **Bachman** | 화살표 | — | — | 상자 | 최초의 데이터 구조도 | 사실상 쓰지 않음 | 역사적 |
| **Min-Max (ISO)** | `(0,n)` 숫자 쌍 | 숫자 하한 | — | Chen과 비슷 | 수치가 정확 | 읽는 방향이 다른 표기와 반대라 혼동 | 학술 |

**판단:** 관계 표기는 **IE 유지**.
- 사용자(모델러 · DA · 기관 담당자)가 이미 DA# · ERwin · eXERD에서 IE로 일한다 — 새 표기를 배우게 하지 않는다.
- 제품의 결과물이 **DDL · 테이블 정의서**라서, 속성과 키가 상자 안에 있는 IE · IDEF1X 계열이어야 그림에서 바로 물리로 이어진다(Chen · UML은 탈락).
- IDEF1X는 정밀하지만 기호(●, P, Z, 둥근 모서리)를 외워야 하고 기관 담당자가 읽기 어렵다. 다만 IDEF1X의 **'키 구역을 가로줄로 나누기'**는 IE 상자에 이미 가져와 쓰고 있다(E4).

### 2.2 엔터티(표) 표현

| 방식 | 모양 | 키 표시 | 지금과 비교 |
|---|---|---|---|
| **IE 상자 + 키 구역** — **지금** | 사각, 위 키 구역 · 아래 일반 속성 | `#` + 구역 구분선 | 기본 |
| Chen 타원 | 사각 엔터티 + 속성 타원 | 밑줄 | 속성이 많은 업무 모델에 맞지 않음 |
| IDEF1X 상자 | 독립 = 직각, **종속 = 둥근 모서리**, 두 칸 | 키 칸 | 종속 여부는 우리는 **선(실선)** 으로 보여 줌 — 상자 모양까지 바꾸면 모든 카드가 둥근 지금 디자인과 충돌 |
| Barker 상자 | 둥근 모서리 | `#` 키 · `*` 필수 · `o` 선택 | `#`는 가져옴. 필수(`*`)는 상자 안에 쓰지 않고 패널 · 물리 캔버스의 NN으로 |
| UML 3칸 클래스 | 이름 · 속성 · 연산 | `«PK»` 스테레오타입 | 연산 칸이 불필요 |
| DA# · ERwin 관례 | 논리명 + 물리명 한 상자, 논리 / 물리 보기 전환 | 열쇠 아이콘 · PK/FK 글자 | **논리명 + 물리명 한 줄**(E2 · E6), **논리 / 물리 별도 캔버스**(C2)를 가져옴 |

### 2.3 키 표시

| 방식 | 장점 | 단점 | 채택 |
|---|---|---|---|
| **`#` 접두** (Barker · DA#) | 한 글자, 고정폭 글꼴과 잘 맞음, 국내 산출물에 흔함 | IE 원래 표기에는 없음(IE는 구역 구분만) | **PK에 사용** |
| PK · FK 글자 | 뜻이 바로 읽힘 | 줄마다 글자가 늘어 폭을 먹음 | FK에 "(FK)"만 사용 |
| 열쇠 아이콘 | 시각적 | 작은 배율에서 뭉개짐, 아이콘이 상태 점과 경쟁 | 트리에서만 사용 |
| 밑줄 (Chen · 교재) | 교재 관례 | 링크로 오해, 대비 약함 | 사용 안 함 |
| 구역 구분선 (IDEF1X) | 키 묶음이 한눈에 | — | **함께 사용** |
| FK 강조(이탤릭 · 색) | 키 전파 경로를 따라가기 쉬움 | 색만 쓰면 색약 사용자 불편 | **이탤릭 + 파랑 + "(FK)" 글자** 세 겹 |

### 2.4 관계명

| 방식 | 예 | 장점 | 단점 | 채택 |
|---|---|---|---|---|
| 동사구(서술형) — Chen · Barker | "부서가 사원을 가진다" | 문장으로 읽힘(업무 확인용) | 길어서 선 위가 복잡, 방향마다 문장이 따로 필요, 표준 용어로 관리하기 어려움 | 2026-11-24 **폐기** |
| **명사형 관계명** | 소속 · 담당 · 포함 | 짧아 선 위가 깔끔, 표준 단어로 관리 가능 | 관계 방향의 뜻은 끝 기호로 읽어야 함 | **채택** |
| 역할명(role name) — IDEF1X · UML | 출발 · 도착, 상위 | **FK 이름(출발창고ID)** 과 그대로 이어짐 | 일반 관계에는 과함 | 같은 두 엔터티 사이 여러 관계 · 재귀에서 채택 |

### 2.5 선 그리기

| 항목 | 선택지 | 채택 · 이유 |
|---|---|---|
| 경로 | 직선 · **직각** · 곡선 | **직각** — 표 그림이 정돈돼 보이고 DA# · ERwin과 같음. 직선은 엔터티를 가로지르기 쉬움, 곡선은 끝 기호 방향이 흐려짐 |
| 붙는 곳 | **엔터티 가장자리** · **FK 행** | 설계는 FK 행(어느 컬럼이 FK인지 선으로 보임, SWS 장점), 목업은 아직 가장자리 → §4 과제 1 |
| 선이 겹칠 때 | 그대로 · 피해 가기 · 묶기 | 설계 원칙 3(엔터티를 피해 직각, 라벨 겹침 방지) — 목업은 가운데 꺾임만 → 구현 단계 자동 배선 |

| 더한 것 | 이유 | 다른 도구 |
|---|---|---|
| 속성 줄 **표준 상태 점 + 글자 배지**(E7) | 제품 목적이 표준 준수 — 미준수가 **편집창 안이 아니라 캔버스에서** 보여야 한다(03 원칙 7, DA# 문제 F-14 · U-07) | DA# · ERwin은 별도 검사 보고서 |
| 머리 **'미준수 n'** · 미니맵 호박색 | 수십 개 엔터티 중 고칠 곳을 바로 찾기 | 없음 |
| **분류 배지 M · A · H · K** | 기준 정보 · 거래 · 이력 · 코드 성격이 배치 · 명명 규칙(…기본 · …내역 · …이력)과 연결 | DA#은 색으로만 구분 |
| **자물쇠**(보안 속성) | 개인정보 속성을 설계 단계에서 보이게 | 별도 문서 |
| **참조 엔터티 점선 상자** | 다른 영역에서 빌려온 것은 여기서 고칠 수 없다는 표시 | ERwin 서브젝트 영역 공유와 비슷 |
| **공동 편집 테두리 · 이름표** | 여러 명이 같은 영역을 동시에 편집 | 데스크톱 도구에는 없음 |
| **글자 크기 기준 상세도** | 수백 개 엔터티에서도 읽을 수 있는 크기만 보이기 | ERwin · DA#은 수동 표시 수준 |

원칙: **색만으로 뜻을 전하지 않는다** — 상태는 점 + 글자, FK는 색 + 이탤릭 + "(FK)", 식별은 선 모양(실선 · 점선) + 패널 글자.

## 4. 검토 결과 · 남은 과제

| # | 내용 | 권고 | 시점 |
|---|---|---|---|
| 1 | **선이 붙는 곳** — 설계(FK 행에 붙임)와 목업(엔터티 가장자리)이 다르다 | 구현 단계에서 FK 행 끝점 + LOD에서 가장자리로 돌아가기 | 구현 |
| 2 | **범례에 선 · 끝 기호 설명이 없다** — 지금 범례는 상태 점 · 미니맵 색만 | 범례 [ⓘ]에 "실선 식별 · 점선 비식별 · ⋔ 다수 · ｜ 하나 · ○ 없을 수 있음 · 고리 재귀 · 보라 호 배타" 한 줄 추가 | 목업에서 바로 가능 |
| 3 | 첨부 화면처럼 **브라우저에 저장된 이전 데이터의 관계명이 동사형** | 저장 데이터를 불러올 때 '…한다 · …된다'를 명사형으로 바꾸거나, 표준 맞추기 · 모델 검토에 "관계명 서술형" 점검 항목 추가 | 목업 / 구현 |
| 4 | **표기법 바꾸기(IDEF1X 등) 옵션** 요구가 나올 수 있음 | 편집 캔버스는 IE 하나로 고정(학습 · 지원 비용). 필요하면 **이미지 · 산출물 내보내기에서만** IDEF1X 선택을 검토 | 요구 시 |
| 5 | 1:1 관계가 항상 실선 | 1:1 비식별(점선)도 있을 수 있음 — 관계 패널의 식별 여부를 그대로 따르게 | 구현 |
| 6 | 다항(3개 이상) 관계 | IE 관례대로 **교차 엔터티**로 표현(M:N 해소와 같은 흐름) — 별도 기호 만들지 않음 | 유지 |
