## 2. 부딪히는 점
1. 최소 검증 ↔ 26:101(참조 오류 막기). 정합성 최소선 제안: 필수 열 · 빈 물리명 · 빈 타입 · 같은 테이블 안 물리명 중복 · 대소문자만 다른 테이블명. 나머지 경고.
2. 엔티티 추가 금지 ↔ 병합 기본. ‘삭제 후 추가’는 id 연속성 · ALTER DDL · 결재 비교 · 관계/예외 사유를 깨뜨림 → 운영 DB에 잘못된 DDL 위험(높음).
3. 관계 중복 팝업 ↔ 18 §0 ‘연결은 묻지 않는다’. 엑셀로 컬럼을 먼저 올리는 고객 흐름에서는 자식에 `DEPT_CD`가 이미 있는 게 보통 → 기본 선택은 ‘덮어쓰기’가 맞음. LG-R07 W2/P5 → 우선순위 변경(사람 확인).
4. PK 추가 팝업 ↔ 공동 편집 저장: 팝업 대기 중의 반쯤 만든 관계 · FK를 Yjs에 미리 쓰면 남에게 보이고 되돌리기가 꼬임 → **계획은 클라이언트에서, 확정 뒤 한 Y 트랜잭션으로 적용**을 18 §5 · T-P2-402/403 계약에.
5. PK 삭제 ‘FK만 끊기’ ↔ 두 선택 + 관계 삭제와의 자식 PK 처리 불일치.
6. 표준화 순서: 표준화 전에 관계를 그리면 `DEPT_CD`(표준) ↔ `DEPT_CODE`(원본)를 못 잡아 FK 컬럼이 둘이 됨. 표준 맞추기 일괄 적용(T-P2-503)에도 ‘PK 변경 → FK 전파’ 필요(T-P2-501 계약).
7. 차단 항목을 늘리면 신청 시점 검수 기준 버전을 스냅샷하고 승인 재검사도 같은 기준으로(arch:281).
8. 스냅샷 · 승인 DDL은 설계와 맞음. 목업 두 곳(작업본 DDL 내려받기, 결재 중 산출물 링크 snap 없음)만 다름.
9. 우선순위: 관련 REQ 일부가 W2/P5(LG-R07 · LG-R05 · DG-R02 · RV-R03). ‘중복 컬럼 → FK’는 W3 제외 확정된 RV-R04(관계 후보 미리보기)와 겹치므로 ‘사용자가 선을 그었을 때 같은 이름 하나만’으로 한정.

## 4. 개선 제안
1. 모델 불변식(엔터티 안 물리명 유일 · 시스템 안 테이블명 유일 · 엔터티명 유일)을 `packages/rules` 한 곳에 두고 엑셀 · collab 쓰기 검증 · 게이트 B · 신청에서 공용.
2. 관계 그릴 때 같은 물리명/용어 컬럼이 있으면 기본값 ‘이 컬럼을 FK로’(사용자가 선을 그은 경우만 — RV-R04와 구분).
3. 엔터티 정의 입력 · 표시, 하드코딩 검사 제거, DDL `COMMENT ON TABLE`에 정의 사용(추측).
4. 캔버스 밀도 설정 + 상세도 임계값 문서(75%) · 목업(92%) 일치.
5. ALTER DDL · 결재 비교 짝짓기를 안정 속성 id + 물리명 보조로, ‘재추가’ 경고.
