## 사람 확인이 필요한 질문

1. **등록을 막는 최소 조건은 어디까지인가요?** 권장안은 읽을 수 없는 파일, 처리 상한 초과, 테이블·컬럼 식별 불가, 이름 중복을 차단하는 것입니다. 타입·설명·참조 문제는 원본과 위치를 보존해 등록 후 모델 검증으로 넘깁니다.
2. **기존 자식 속성을 ‘덮어쓴다’는 것은 어떤 값을 바꾸는 뜻인가요?** 권장안은 기존 속성 ID와 설명을 보존하고, FK 연결에 필요한 타입·도메인·키 변경을 확인 후 적용하는 것입니다. 다른 관계에 이미 쓰이는 속성에는 새 이름을 제안합니다.
3. **부모 PK 삭제 시 복합 키와 마지막 PK를 어떻게 처리할까요?** 권장안은 자식 컬럼을 보존하고 남은 키 조합으로 유효한 FK를 구성할 수 있으면 갱신하는 것입니다. 구성할 수 없으면 FK 제약을 해제하고 관계선에 미해결 상태를 표시합니다. 식별 관계에서 자식 PK와 하위 관계에 미치는 영향도 적용 전에 보여 줍니다.
4. **최초 표준 맞추기는 반드시 완료해야 하나요?** 권장안은 업로드 후 먼저 안내하고, 사전 결재를 기다리는 동안 모델 편집을 허용하는 것입니다. 확정 신청에서 합의한 차단 조건을 적용합니다.
5. **설명의 ‘제대로 입력’과 표준 검증의 통과 기준은 무엇인가요?** 권장안은 W1에서 엔터티명과 양쪽 설명의 빈값·공백을 검사하고, 내용의 적절성은 승인자가 확인하도록 하는 것입니다. 사유가 있는 표준 예외와 비대상은 기존 정책대로 표시하고, 연결 용어의 결재 상태도 함께 보여 줍니다.
6. **승인본 DDL은 언제 만들까요?** 권장안은 결재 완료 문서에 [DDL]을 제공하고 권한 있는 사용자가 열 때 생성하는 것입니다. 확정본과 생성에 쓰인 기준 버전을 고정하고, 같은 기준으로 다시 생성할 수 있게 합니다.
7. **엔터티 중복의 범위와 파일 처리 단위는 무엇인가요?** 권장안은 대상 작업 영역의 엔터티 논리명·테이블 물리명을 기준으로 중복과 그에 의존하는 행을 표시하는 것입니다. 미리보기에서 독립적으로 적용 가능한 항목만 사용자가 선택하고, 중복은 기존 엔터티 정보와 삭제 영향 확인 경로를 제공합니다.

## 개선 제안

- **승인본에서 DDL 점검 위치로 이동할 때 버전을 유지합니다.** DDL의 현재 [모델에서 열기] 링크는 `snap`을 전달하지 않습니다. 확정본의 점검 행을 누르면 같은 확정본의 해당 엔터티를 여는 편이 검토 맥락을 보존합니다. [DDL 점검 링크](/D:/project/DBModeler/docs/ux/mockups/ddl.html:157)
- **공식 DDL의 감사 기록에 결재 문서 ID와 스냅숏 해시를 남깁니다.** 현재 목업 로그에는 파일명·시스템·줄 수가 남습니다. 두 식별자가 있으면 같은 버전 이름의 산출물도 어느 승인본에서 생성했는지 확인할 수 있습니다. [DDL 내려받기 감사](/D:/project/DBModeler/docs/ux/mockups/ddl.html:171) · [스냅숏 소유와 참조](/D:/project/DBModeler/docs/arch/01-backend-architecture-v1.md:284)
- **한 모델을 W1 인수 시나리오 끝까지 사용합니다.** 중복과 미해결 참조가 있는 엑셀부터 표준 적용, 검증 실패와 수정, 승인까지 이어서 확인합니다. 이후 새 작업 버전을 편집하고 이전 승인본의 DDL을 다시 생성해 승인 기준이 유지되는지 확인합니다. [W1 수직 완주 기준](/D:/project/DBModeler/docs/arch/01-backend-architecture-v1.md:306)
