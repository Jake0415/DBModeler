# RBAC 2차 목업 구현 리뷰

[협의 결과](resolution-rbac-r2.md)의 최종 결정을 우선 적용했다. 최종 표가 변경하지 않은 항목은 초안의 요구를 기준으로 삼았다. 지정된 목업 diff와 새 검수 기준 화면을 읽고, 로그인 및 신청처럼 판정의 결과를 소비하는 연결 경로도 확인했다. 아래 실행 결과는 코드 경로를 따라 판단했다.

## 권한과 결재

### CI-01 · 높음 · 위임으로 대리인의 결재 자격을 건너뛴다 (R-05, R-08)

근거 `assets/app.js:109–135`, `mypage.html:259–271`. 대리인 선택은 내부 소속과 중지·만료 여부만 본다. 실행 시에도 원 담당자에게만 단계 권한을 검사하므로 조회만 계정이나 임시 비밀번호 상태의 계정도 대리 처리 후보가 된다. 유효 범위가 다른 대리인과 잠긴 계정도 걸러지지 않는다. `actingFor`는 후보 선정과 다른 조건으로 원 담당자를 고른다.

수정 방법은 단계별 역할과 정규화한 담당 범위를 등록 시 검증하고, 실행 시 양쪽의 최신 계정 상태·기간·직접 권한으로 다시 판정하는 것이다. 재위임 없이 동일 판정에서 실제 처리자와 원 담당자를 반환해 대기함·알림·처리·이력에 사용한다.

### CI-02 · 높음 · DA 승인과 최종 승인의 독립성이 대리 이력에 반영되지 않는다 (R-02, R-08)

근거 `assets/app.js:128–140`, `approvals.html:776–784`. DA 이력에는 `forId`를 남기지만 최종 후보 판정은 `whoId`만 읽는다. DA 단계의 원 담당자가 최종 단계의 원 담당자 또는 실제 처리자가 되는 경로가 남는다. 최종 후보에서 신청자와 DA 처리자를 비교할 때도 위임 쌍을 일관되게 비교하지 않는다.

수정 방법은 각 단계의 실제 처리자와 원 담당자를 이력에서 복원하고, 최종 단계 양쪽 신원을 신청자 및 DA 단계 양쪽 신원과 비교하는 것이다. 자기 신청의 승인 판단도 이 규칙을 사용한다.

### CI-03 · 높음 · 자기 승인과 결재선 공백을 신청 전에 거르지 못한다 (R-02, R-06)

근거 `assets/app.js:129,138–140,177–193`, `model.html:1018–1020`, `approvals.html:773–780`, `dictionary.html:691`. 자기 승인 기본값은 합의대로 허용이지만, 독립 최종 후보가 없는 자기 신청도 대기함에 잡힌다. `lineGaps`는 단계별 인원만 따로 세어 같은 겸임자 한 명으로 양쪽을 채울 수 있다고 보고, 최종 생략 결재선에서 자기 승인으로 붙는 최종 단계는 검사하지 않는다. 사전 신청 경로의 공통 생성 함수에도 공백 검사가 없다. 실행 검사는 항목 반려와 승인 이력의 인메모리 변경 뒤에 실행된다.

수정 방법은 DA 후보마다 실제 가능한 최종 처리 조합을 계산하고, 자기 승인 후보는 자동 부착 단계까지 검사하는 것이다. 문서 생성·대기함·알림·승인에서 같은 판정을 사용하고, 승인 이력과 항목 상태 변경 전에 최종 검사한다.

### CI-04 · 높음 · 사용 기한 만료 계정이 로그인할 수 있다 (R-05, R-09)

근거 `login.html:62–69,81–104`, `assets/app.js:106–119,1432`. 로컬·SSO·최초 비밀번호 변경 후 로그인에 사용 기한 판정이 없다. `canUser`는 잠김 계정을 허용하고, `expiredUser`는 고정된 2026-11-19를 사용해 시간이 지나도 데모에서 만료되지 않는다. 임시 비밀번호 차단 목록에는 결재 문서 전체 보기와 감리 감사 조회가 포함되지 않는다.

수정 방법은 의도한 기준일을 로그인·권한·목록에서 공유하고, 로그인 완료 직전에 중지·잠김·만료를 재검사하는 것이다. 최초 변경 전에는 해당 역할에서 얻는 권한 자체를 보류해 다른 역할로 허용된 기능만 남긴다.

### CI-05 · 높음 · 감리 문서와 집계에 조회 범위가 적용되지 않는다 (R-07, R-11, R-12)

근거 `assets/app.js:92,118–119,1209–1212`, `approvals.html:173–183,244`, `audit.html:51–63`. 끝난 문서의 `appr.viewall` 호출에 문서가 빠져 제한 계정도 전체 범위로 판단된다. 참조함은 `cc`만 검사해 상세가 차단하는 진행 중 문서의 목록·검색 메타데이터를 보여 준다. 감리 계정도 `appr.viewall` 때문에 집계 탭을 얻는다. 감사는 범위가 잘못 적용된 문서 판정을 재사용하고 `done`만 남겨 반려·회수 이력을 제외한다.

수정 방법은 문서의 유형과 당시 시스템을 넘겨 범위를 판정하고, 신청·참조·결재선 예외에도 계정 상태와 감리의 종료 문서 조건을 적용하는 것이다. 목록·상세·검색·집계·감사에서 해당 판정을 공통 적용하고 집계 권한을 명시한다.

### CI-06 · 높음 · 대리인에게 대기함은 열리지만 문서 열람이 거절될 수 있다 (R-07, R-08)

근거 `assets/app.js:133–138,1209–1212`, `approvals.html:172–183,567`. 대기함은 위임을 인정하는 `canUserAct`를 사용하고 상세의 `onLine`은 직접 권한과 과거 이력만 본다. 후보로 인정된 대리인이 상세를 못 열 수 있다.

수정 방법은 진행 문서의 결재선 열람에 검증된 위임 관계를 반영하고, 대기함 목록도 동일한 문서 열람 판정을 통과시키는 것이다.

## 관리 변경 확인

### CI-07 · 높음 · 이전 계정 정보로 확인을 적용하거나 최신 계정 변경을 덮을 수 있다 (R-01, R-03)

근거 `assets/app.js:43–47,1085–1088,1122–1129,2496–2502`, `approvals.html:222–229,749–757`. 확인 버튼은 요청 목록은 다시 읽지만 확인자와 대상은 로드 당시 `USERS`에서 읽는다. 확인자 권한·상태가 다른 탭에서 바뀌어도 결정에 반영되지 않을 수 있고, `saveUsers`는 그 탭의 전체 계정 복사본을 저장한다. 일반 승인과 달리 확인 요청의 결정은 현재 선택 계정 변경도 검사하지 않는다.

수정 방법은 클릭 시 저장된 계정으로 행위자·대상·요청 상태를 다시 조회하고, 최신 계정 목록에 검증된 대상의 변경만 합치는 것이다. 확인·거절에는 신청자·대상 제외를, 철회에는 신청자 일치를 실행 시 공통 적용한다.

### CI-08 · 높음 · 역할 확인의 재검사가 담당 시스템 변경을 놓친다 (R-03, R-16)

근거 `settings.html:478–480`, `assets/app.js:1128–1129`, `approvals.html:226–229`. 요청은 담당 시스템의 이전 값을 저장하지만 `arStale`은 역할만 비교한다. 역할을 유지한 채 담당을 축소해도 이전 요청 확인이 그 축소를 되돌릴 수 있다. 적용 로그에는 실제 역할·시스템 코드 전후가 빠진다.

수정 방법은 정규화한 역할 및 담당 시스템 전후와 대상 자격을 검증하고, 확인한 차이만 적용하는 것이다. 만료·중지·담당 변경 시 재신청 안내를 남기고 실제 적용된 차이를 감사에 기록한다.

### CI-09 · 높음 · 높은 역할에 대한 담당 확대 확인에 공백이 있다 (R-03)

근거 `settings.html:450–458,588–602,614–619`. `HIGH_ROLES`로 추가 역할을 찾지만 담당 확대 검사는 DA·기관 담당자·감리만 포함해 Admin의 담당 확대는 즉시 저장된다. 신규 계정의 확인자 사전 검사에는 실제 대상 ID 대신 `_new`가 들어간다.

수정 방법은 추가·확대에 같은 높은 역할 집합과 코드 집합 비교를 사용하고, 등록·수정 모두 실제 요청 대상 ID로 확인 가능자를 계산하는 것이다.

### CI-10 · 높음 · 모델 정책 한 번의 저장으로 만든 확인 요청이 즉시 무효가 될 수 있다 (R-01)

근거 `settings.html:407–435`, `assets/app.js:1107,1128–1129`. 모델 최종 승인 OFF 요청의 기준과 적용값은 저장 전의 `finalModel` 전체다. 같은 저장에서 다른 영역을 ON으로 강화하거나 기본 ON인 영역 키를 채우면, 저장 직후의 전체 객체가 달라져 방금 만든 요청도 stale이 된다. 단순히 전체 객체 덮어쓰기를 허용하면 다른 영역의 변경이 소실된다. 또한 완화가 보류되거나 사유 입력이 취소돼도 자기 승인 변경을 적용한 것처럼 기록하고, 강화 변경에 기관 담당자 알림이 없다. 자기 승인 설정은 실행 중 문서의 판정에도 사용되므로 모든 영향이 다음 신청에 국한된다는 요청 문구도 부정확하다.

수정 방법은 영역별 기본값을 정규화해 실제 변경 키만 비교·적용하고, 즉시 반영한 값에서 요청의 기준을 잡는 것이다. 실제 반영 전후로 감사·저장 메시지·강화 알림을 만들고 자기 승인 정책의 진행 문서 영향을 따로 표시한다.

### CI-11 · 중간 · 첫 기관 담당자 지정과 사용자 영향 미리보기가 불완전하다 (N-01, R-16)

근거 `settings.html:457,461–475,605–611,619–628`, `assets/app.js:1121`. 신규 첫 기관 담당자 지정은 사유 입력과 알림이 없고 기존 계정 지정에는 신규 전용 감사 이벤트도 없다. `previewHtml`은 이전 상태에도 새 담당 시스템을 넣고 임시 비밀번호·기한·상태를 지운 뒤 문맥 없이 권한을 비교한다. 그 결과 시스템별 권한 증감과 앞으로 비게 될 결재 단계를 빠뜨리고, 즉시 반영과 확인 후 반영이 구분되지 않는다.

수정 방법은 첫 지정 사유·감사·알림을 등록과 수정이 공유하게 하고, 실제 이전 계정과 두 반영 시점의 계정 상태를 범위 및 결재선별로 비교하는 것이다.

### CI-12 · 중간 · 확인 결과 알림의 도착 화면에서 수신자가 요청을 볼 수 없다 (R-03)

근거 `approvals.html:191–209,220–231,233–235`, `settings.html:711–713`. 역할 대상자에게 결과 링크를 보내지만, 탭 진입과 목록 판정이 대상자에게 자기 요청을 열어주지 않는다. 예를 들어 감리만 받는 대상자는 확인 결과 링크에서 내 신청으로 이동한다. 철회는 양쪽 화면 모두 버튼 표시 조건에 의존한다.

수정 방법은 본인이 대상인 요청의 상태와 관련 상세를 읽을 수 있게 하고, 확인·거절 자격과 철회 자격은 별도로 실행 시 검사하는 것이다.

## 사업 종료와 조회·내보내기

### CI-13 · 높음 · 사업 종료가 중지 보호 및 유효한 인계를 보장하지 않는다 (R-10)

근거 `settings.html:640–642,681–708`. 사업 소속 내부 직원도 기본 선택되어 마지막 Admin 또는 현재 계정을 일괄 중지할 수 있다. 인수자는 내부 DA·모델러 여부만 확인하므로 대상 시스템의 편집 권한이 없거나 잠긴 사람에게도 영역이 넘어간다. 대상 체크를 바꿔도 인계 목록과 영역·엑셀의 인수자 필수 판정은 초기 집합을 사용한다. 열린 뒤 새로 생긴 신청은 최신 목록에서 처리하면서 인수자 필수 검사는 초기 목록을 사용해, 인수자가 없으면 `USERS[to].name`에서 예외가 날 수 있다.

수정 방법은 현재 고른 계정에 대해서만 인계 계획을 계산하고, 실행 직전에 최신 상태로 보호 대상·인수자 권한·필수 인계를 검사한 뒤 저장하는 것이다.

### CI-14 · 높음 · 사업 종료의 대리 회수와 결재선 처리가 빠졌다 (R-02, R-06, R-10)

근거 `settings.html:686–708`, `approvals.html:758–759`. 'DA 대리 회수'를 누르면 설정을 연 Admin이 그대로 문서를 회수한다. 인계는 신청자 ID만 바꾸므로 인수자가 현재 승인자 또는 기존 DA 승인자일 때의 독립성, 중지 대상이 빠진 결재선의 공백을 검사하지 않는다. 정상 회수와 달리 문서별 후속 처리의 공통 경로도 없다.

수정 방법은 자격 있는 DA에게 대리 회수를 맡기고, 원신청자와 인수자 이력을 유지하며 인계 이후 전체 결재선의 유효한 조합을 미리 확인하는 것이다.

### CI-15 · 중간 · 사업 기본값·종료 상태·후보 인계·만료 예고가 일부 빠졌다 (R-09, R-10, N-03, N-04)

근거 `settings.html:503,527–529,543–547,588–591,671–708`, `home.html:106–111`. 사업 선택 시 종료일만 복사하고 시스템은 사업 기본값으로 설정하지 않는다. 종료 실행 뒤 사업 상태를 저장하지 않아 날짜가 남은 사업은 여전히 선택할 수 있다. 후보는 안내 문구만 있고 대상의 실제 후보를 표시·인계하지 않는다. 만료 예고는 진행 중 신청만 세며, 사용자 설정의 '7일 안 만료' 필터에는 이미 만료되거나 중지된 계정도 든다.

수정 방법은 사업 선택 시 기한·시스템을 기본값으로 채우고, 대상·인계 항목·인수자·중지 단계를 진행하면서 후보를 포함한 실제 처리 대상을 표시하는 것이다. 사업 종료 상태를 저장하고 만료 예고에 영역·엑셀·후보 등 남은 일을 합친다.

### CI-16 · 높음 · 모델러 내보내기 범위와 ERD 내보내기 통제가 일치하지 않는다 (R-11, R-14)

근거 `assets/app.js:110,118–119`, `model.html:1675–1681,1712`, `ddl.html:168–173`, `outputs.html:145–152`. 담당 시스템 제한은 역할 배열이 모델러 하나일 때만 적용돼, 내려받기 권한이 없는 추가 역할도 범위를 넓힌다. 모델 화면의 ERD 이미지 내보내기에는 `out.export` 검사와 다운로드 감사가 없다. DDL의 감사에는 별도 버전·보안 컬럼 수가 없고 개인정보 산출물의 감사는 사유가 있으면 시스템·버전 문맥을 사유로 대체한다.

수정 방법은 역할별로 다운로드 허용과 범위를 계산한 후 허용 범위를 합치는 것이다. 모델 화면과 산출물에서 ERD 내보내기 판정을 공유하고, 파일·시스템·버전·컬럼 수·필요한 사유를 감사에 남긴다.

### CI-17 · 중간 · 조회 범위 제한에 필요한 시스템이 없는 경우를 허용하거나 다른 화면으로 바꿔 버린다 (R-11)

근거 `assets/app.js:118–124,209–220,1739–1749`, `model.html:278`, `ddl.html:79–80`, `outputs.html:87–88`. 시스템을 확인할 수 없는 범위 제한 요청은 `!sk`로 허용된다. 반대로 URL의 영역을 검사하기 전에 현재 시스템의 영역 목록에서 찾고 없으면 기본 영역으로 바꿔, 링크로 지정한 영역에 대한 허용 여부를 직접 판단하지 않는다. 접근 가능한 시스템이 하나도 없을 때는 `curSys`가 원래 시스템을 반환하므로 모델 페이지의 검사와 영역 목록·트리가 동일한 경계를 공유하지 않는다.

수정 방법은 명시된 영역·시스템의 원본 코드를 확인하고 대상별로 판정하며, 시스템이 필요한 동작은 코드가 없으면 차단하는 것이다. 대상 없음과 범위 밖을 표시하고 트리·시스템 영역 목록도 같은 판정으로 거른다.

### CI-18 · 중간 · 감리 감사에서 업무 이벤트까지 사라진다 (R-12, R-14, R-15)

근거 `audit.html:51–63`, `dict-history.html:56`, `ddl.html:173`, `outputs.html:151`. 감리만 있는 계정에 `getAudit()` 이벤트 전체를 제거해 업무 다운로드도 보이지 않는다. 반면 삭제 로그는 전체 컬렉션을 그대로 그리며 사전 이력 화면에서는 수행 역할을 'DA·Admin'이라고 고정 표시한다.

수정 방법은 감사 이벤트에 관리·업무 유형과 시스템 범위를 넣고, 감리에게 허용된 업무 이벤트만 범위 내에서 제공하는 것이다. 삭제 기록에는 저장한 실제 수행자를 표시한다.

## 화면별 잔여 항목

### CI-19 · 중간 · 검수 기준 편집 경로가 설정에도 남아 있다 (R-19)

근거 `settings.html:53,161–201,240–249,324–335,401–405,432–433`, `rules.html:76–95`. 새 화면으로 연결되지만 설정에도 동일 편집 폼·저장 경로가 남고, 기존 검수 기준 해시는 새 화면으로 이동하지 않는다. 이전 설정 탭이 열린 채 새 화면에서 기준을 변경하면, 설정의 다른 항목을 저장하는 과정에서 숨은 이전 입력값으로 정책을 다시 저장할 수 있다.

수정 방법은 설정 저장 대상에서 검수 기준 폼·입력 검증·저장을 제거하고, 기존 검수 기준 해시를 새 경로로 연결하는 것이다.

### CI-20 · 중간 · 담당 시스템 기본 영역과 엑셀 취소 시점 권한 확인이 끝까지 연결되지 않았다 (R-18, R-26)

근거 `assets/app.js:213–220,1085–1088`, `standardize.html:88`, `import.html:82,127–129`, `import-excel.html:292–297,426`. `defArea`는 이미 선택된 시스템의 영역 안에서만 편집 가능한 곳을 고른다. 기관 전체 열람 모델러가 담당 밖 시스템에서 기본 진입하면 담당 시스템으로 옮겨 주지 않는다. 엑셀 취소는 현재 잠금을 확인하지만 `can`이 열린 탭의 계정 복사본을 사용하므로 다른 탭의 역할·담당 회수는 놓친다.

수정 방법은 명시적 영역이 없는 작업 진입에서 편집 가능한 담당 시스템과 영역을 함께 정하고, 엑셀 취소에는 기존 `liveCanEdit`처럼 저장된 최신 계정의 권한을 쓰는 것이다.

### CI-21 · 낮음 · 타입 요청 숨김과 잠금 사유가 권한 상태와 어긋난다 (R-04, R-17, R-24)

근거 `datatypes.html:190,206–207,445`, `assets/app.js:86–88,1510`, `model.html:278–281,1881–1884`. 타입 요청 탭 숨김은 문맥 없는 역할 판정이고, 초기화가 요청 버튼을 다시 노출하면서 DA 전용 등록을 'DA · Admin'으로 안내한다. 모델 편집 도구의 ARIA와 툴팁은 `viewOnly` 분기에서만 붙으므로 담당 모델러의 결재 중·확정 상태에 동일하게 붙지 않는다. 담당 밖과 비활성 영역을 한 사유로 다룬다.

수정 방법은 타입 탭·버튼·안내에 실제 요청 가능 시스템 및 DA의 처리 권한을 적용하고, 모델 편집 도구는 잠금 원인별 판정으로 표시·비활성화·접근성 설명을 맞추는 것이다.
