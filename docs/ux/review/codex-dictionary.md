# 표준 사전 교차 검증 및 UX 검토

## ① 요약

검토 기준은 `835357a`와 `b3e65ec`를 포함한 HEAD `b3e65ec` 및 작업 트리다. 검토 시작 시 작업 트리는 깨끗했다. [30 v1.3 §3.6](../../spec/da-feature-spec/30-metadata-design.md), [20 §4](../20-dictionary-modeler-comparison.md), [19 요구 대비 점검](../19-standard-dictionary-gap.md)을 현재 목업과 대조했다. DA#·SWS 비교는 저장소의 비교 문서에 근거했다.

폼·표·모델·엑셀 예시가 계정별 바구니로 합류하고, 결재와 버전 이력으로 이어지는 구조는 있다. 초기 구축의 핵심인 **신규 단어·분류·도메인·용어의 한 품의**는 현재 결재 재검사에서 막힌다. 변경 경로에서는 반대로 신규 등록에서 막히는 잘못된 약어가 반영될 수 있다. 이 두 검사 불일치와 모델의 부분 반려 추적을 먼저 고쳐야 한다.

**시험 범위.** 미리보기 사전 경로에서 HTTP 200을 확인했다. 별도 Edge 프로필의 디버깅 포트에 연결되지 않았고 브라우저 접근 호스트도 새 탭을 열 수 없었다. 따라서 UI 클릭·렌더링·키보드 실측은 코드 추적으로 대체했다. 공유 브라우저 저장소를 읽거나 변경하지 않아 백업·복원 대상은 없었다. Node 26에서 원본 `app.js`를 최소 DOM 스텁과 메모리 저장소로 실행해 검사·반영·역할 함수 일부를 확인했다. 실제 파일 처리, 결재 버튼 조작, 레이아웃은 함수 시험 범위 밖이다.

## ③ UX 기능 검토

### 찾기, 작성, 검토 내역

통합 검색의 종류·출처·상태와 상세 이력은 DA가 중복과 기존 표준을 먼저 확인하기에 좋다. 표 진입점이 사전 메뉴와 목록 작업에 모두 있고 선택한 항목의 ID를 표로 넘겨 재검색을 줄인다. 원본이 다른 업무의 진입점 7개가 같은 높이로 나열돼 초기 구축 순서를 드러내기 어렵다. 사전 상단은 **검색·상세 / 화면 작성 / 그룹·분류 / 후보 검토**를 중심으로 두고, 업로드 이력은 엑셀 단계 안, 변경 내역은 사전 또는 결재 완료 후 상황에 맞게 연결하는 편이 찾기 쉽다. 그룹과 분류는 한 곳에 유지하고 그룹 행에는 ‘DA 직접 관리’, 분류 행에는 ‘품의 필요’를 표시한다. 형식단어가 먼저 필요한 경우 분류 선택 자리에서 단어 소형 폼으로 열고 담은 뒤 같은 화면으로 돌아온다.

표의 키보드 이동·붙여넣기·행 복제·정상 행만 담기는 직접 작성의 주 경로에 맞는다. 기존 항목을 골라 같은 값을 바꾸는 작업은 목록 액션을 유지하고, 개별 값이 서로 다른 작업은 표에서 고치기로 연결한다. 20건의 서로 다른 값을 넣을 때 목록의 [변경 담기]를 선택하면 빈 변경 행을 각각 다시 열어야 한다. 다중 선택의 기본 변경 액션을 표로 연결하고, 그 안에서 다음 오류 행과 미반영 행으로 이동할 수 있게 한다. 코드·코드값은 행 수가 늘기 쉬우므로 코드 그룹을 한 행으로 두고 코드값 하위 표를 편집하는 흐름이 맞다.

### 바구니, 초안, 품의

사용자는 단추 이름만으로 현재 작업을 이어 쓸 수 있는지, 결재자에게 넘어갔는지 구분해야 한다. 폼의 [목록에 추가]를 [바구니에 담기], 제출을 [품의 올리기]로 통일한다. 바구니는 ‘현재 작업 · 자동 저장’, 이름 있는 초안은 ‘작업 묶음 보관’, 제출 문서는 ‘품의번호 · 결재 상태’로 표시한다. 표의 미전송 행 수와 바구니 건수를 함께 보여 주고, 담은 뒤에는 원본 행으로 돌아갈 수 있어야 한다. 재편집 시 바구니 원본을 유지하고 저장 성공 시 교체한다. 반려·후보·엑셀에서 온 항목에는 출처와 사유가 행에 남아야 한다. 최종 승인 뒤에만 붙는 V1·버전 증분과 별도 공표 차수도 결과 화면에서 구분한다.

### 검증과 결재 부담

SWS 비교 문서에서 기대하는 입력 시점 검증, 원본 행 가이드, 부분 제출 기준을 폼·표·엑셀·결재에서 동일하게 적용해야 한다. 오류는 입력란과 바구니 행에서 같은 이름으로 보여 주고 제출 전 차단한다. 경고는 확인 사유와 판정 시점으로 결재 문서에 남긴다. 결재 화면에서 검사 결과를 눌렀을 때 해당 행의 전후 값과 의존 행을 바로 볼 수 있어야 한다. 대기함은 오류·경고·변경·반려 예정만 좁혀 볼 수 있게 하고, 부분 반려 시 함께 검토할 의존 행을 표시한다. 집계는 문서 처리 수와 승인·반려 항목 수를 구분해 50건 중 2건 반려된 품의가 통째로 성공으로 묻히는 일을 줄인다. 신청자에게는 반려 행, 사유, 재신청 번호를 하나의 흐름으로 연결한다.

### ERD 연계와 기존 도구 기대

DA# 사용자는 분석과 동기화에서 현재값·후보·최종 적용 상태를 구분하고, 논리명/물리명 기준·분해 대안을 활용하는 데 익숙하다는 것이 비교 문서의 관찰이다. NeoDB의 5단계 마법사는 이를 담는다. 마법사와 표준 맞추기는 각각 **미등록 이름을 분석해 사전으로 보내기**, **모델과 승인 사전의 차이를 검토·적용하기**로 진입점의 목적을 명시하고 같은 후보·점수·타입 출처를 써야 한다. 바구니를 기본으로 두고 바로 신청은 단일 작업의 보조 액션으로 둔다. 후보 큐는 약어나 도메인을 결정할 수 없는 항목에 집중한다. SWS와 비교한 여러 종류의 혼합 품의는 유지할 가치가 있으며, 승인 뒤 사용 모델의 재검토까지 연결돼야 체감 가치가 생긴다. 엑셀은 보조 진입점, 분석 세부 옵션과 저장 검색·집계는 각 작업 화면의 보조 영역에 두면 초기 작성의 우선순위가 선명해진다.

## ⑤ 권장 최종 흐름

1. **표준화 담당자**는 통합 검색에서 공통·기관 기준과 유사 항목을 확인한다. DA가 필요 그룹을 준비하고 담당자는 형식단어와 분류를 연결해 도메인·용어·엔터티 용어·코드값까지 작성한다. 소량은 폼, 여러 행은 표, 기존 파일은 엑셀로 같은 작업 묶음에 담는다.
2. **품의 전**에 바구니에서 차단·경고·의존 순서를 확인한다. 오류 행에서 곧바로 원래 폼·표·엑셀 행으로 이동한다. 작업을 나눠야 할 때는 이름 있는 초안으로 보관한다. 준비된 행은 품의 사유 한 번으로 제출한다.
3. **DA와 기관 담당자**는 전후 값과 영향 범위를 보고 결재한다. 기관 설정에 따라 DA 단계에서 끝나거나 최종 승인자가 이어받는다. 부분 반려는 의존 행까지 확인하고 신청자가 사유와 이전 값을 보며 수정한다. 승인 항목은 버전과 변경 이력, 반려 항목은 보완 및 재신청 번호로 추적한다.
4. **모델러**는 ERD에서 승인 사전을 우선 검색·자동완성한다. 다수의 미등록 이름은 자동분석에서 대안·근거를 검토하고, 단어와 도메인을 정할 수 있으면 바구니에 담는다. 판단이 필요한 항목은 발생 위치와 함께 후보 큐로 보낸다.
5. **모델 적용**은 현재·제안 비교 후 선택한다. 신청 중인 참조는 품의의 해당 항목을 따라가고, 반려되면 보완 또는 후보로 돌아간다. 승인 사전 변경으로 영향받은 모델은 표준 맞추기에서 재검토하고 변경분을 확인한 뒤 적용한다.
