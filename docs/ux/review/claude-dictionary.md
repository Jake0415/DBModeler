## ① 요약

- **화면에서 빠르게 만드는 기능은 크게 좋아졌습니다.**
  - 화면 일괄 작성(dict-grid)의 키보드 · 붙여넣기
  - 목록 다중 선택과 같은 값 일괄 변경
  - orderItems 의존 순서 정렬
  - 항목별 부분 반려 → 신청자 바구니로 되돌리기
  - 종류별 진입점의 권한 처리(엑셀 · 모델 패널)

  DX 필수 8건은 대부분 목업에 들어 있습니다.
- **그러나 핵심 시나리오 S1이 막힙니다.** 한 품의 안에서 새 도메인과 그 도메인을 쓰는 용어를 함께 신청하면, 신청 검사와 DA 승인 재검사가 모두 "도메인이 사전에 없음"으로 실패합니다(app.js:646). "사전을 먼저 한 번에 만든다"는 이번 흐름의 출발점이 막힙니다.
- **변경 경로의 검증과 전파가 약합니다.**
  - 도메인명을 바꿔도 용어의 도메인 참조가 갱신되지 않습니다.
  - 영문약어명 변경은 폼 · 신청 · 승인 어디에서도 검사되지 않고, 화면 일괄 작성에서만 검사됩니다.
  - 신청 화면은 차단 오류도 "두 번 누르면 신청"됩니다. 이렇게 낸 품의는 DA 승인에서 반드시 실패합니다.
- **권한 문제가 있습니다.** dictionary.html의 [신청]에 dict.request 검사가 없습니다(조회 전용도 신청 가능). 용어 자동분석의 [바로 신청]은 dict.request 대신 model.edit로 판정하고, 사전 검사도 하지 않습니다.
- **정보 구조가 복잡합니다.** 사전 탭이 7개로 늘었고, 같은 일을 하는 경로가 여러 개입니다(폼 / 표 / 엑셀 / 마법사). "바구니 · 초안 · 품의 · 신청"이라는 말이 섞여 있어 처음 쓰는 표준화 담당자에게 단계가 잘 보이지 않습니다.

## ③ UX 기능 검토 (화면 · 흐름별)

### 1. 정보 구조 · 진입점
- 탭 7개(통합 검색 · 화면 일괄 작성 · 도메인 그룹/분류 · 엑셀 가져오기 · 업로드 이력 · 후보 큐 · 변경 내역)는 서로 성격이 다른 일이 한 줄에 있습니다. 표준화 담당자 기준으로 세 무리로 묶을 것을 권합니다.
  - **찾기 · 고치기**: 통합 검색, 화면 일괄 작성
  - **가져오기**: 엑셀, 업로드 이력
  - **흐름 · 이력**: 후보 큐, 변경 내역

  도메인그룹/분류는 기준정보이므로 설정 성격의 보조 메뉴로 옮길 것을 권합니다.
- 작성 경로가 네 가지입니다(폼 · 표 · 엑셀 · 마법사). 이 자체는 DA# · SWS 사용자에게 자연스럽습니다. 다만 경로마다 검증 깊이가 다릅니다(폼은 약어 변경을 검사하지 않고 표는 검사함). 사용자 눈에는 "같은 사전인데 결과가 다른" 혼동이 생깁니다. 검증은 checkItem 하나로 통일하세요.

### 2. 바구니 · 초안 · 품의 개념
- 화면에 바구니, 신청 바구니, 등록 신청, 초안, 품의, 신청이 섞여 있습니다. 다음 세 단계로 고정할 것을 권합니다.
  - **바구니(담기)**: 작업 중
  - **초안(보관)**: 이름을 붙여 저장
  - **품의(올리기)**: 결재 중

  상태 칩도 같은 말을 쓰세요.
- 바구니는 사전 화면의 오른쪽 패널에서만 보입니다. 모델 · 마법사 · 엑셀에서 담은 뒤 "몇 건이 담겼는지 · 어디서 품의하는지"를 알 수 없습니다. 공통 상단 바에 바구니 배지(n건)를 두고, 누르면 사전 바구니 패널로 가게 하세요.
- 많은 건수에서의 속도:
  - 좋은 점: 표 편집의 Tab · Enter · Ctrl+Enter · 붙여넣기, 같은 값 일괄 변경, 저장한 검색.
  - 아쉬운 점 1: 바구니 안에서 한 행씩 [고치기]를 눌러야 합니다. 바구니 자체를 표로 편집하는 모드(dict-grid를 바구니 위에 여는 것)가 있으면 클릭 수가 크게 줄어듭니다.
  - 아쉬운 점 2: 같은 항목을 두 번 [변경으로 담기]하면 건너뜁니다. 기존 행에 병합하는 것이 기대 동작입니다.

### 3. 검증 피드백 (즉시 · 신청 · 승인)
- 세 시점의 규칙이 서로 다릅니다.
  - 즉시(checkItem): 같은 바구니의 도메인을 허용합니다.
  - 신청 · 승인(checkDictDoc): 허용하지 않습니다.
  - 약어 검사: 즉시에서만 합니다(표 경로).

  사용자는 "담을 때는 통과했는데 결재에서 실패"를 겪게 됩니다. 원칙은 **신청 검사 = 승인 재검사 = 즉시 검사의 합집합**, 그리고 차단 오류는 신청 불가입니다.
- 오류에서 고치는 길: 신청 시 problems 목록에 항목 링크(해당 바구니 행으로 스크롤 · 강조)를 주세요. 승인 "재검사 실패"는 DA에게 원인 항목을 골라 바로 부분 반려하는 버튼을 주세요. 지금은 DA가 멈춘 뒤 할 수 있는 일이 없습니다.

### 4. DA 결재 부담 · 신청자 추적
- 좋은 점: 항목별 부분 반려(사유 포함)와 집계 통계(approvals 175~188)는 DA 부담을 크게 줄입니다.
- 보완할 점:
  - 반려한 단어 · 도메인에 의존하는 같은 문서의 항목을 "함께 반려할까요?"로 묶어 제안하세요.
  - 문서 전체 반려도 바구니로 돌려주세요(부분 반려와 같게).
  - 신청자에게는 바구니 행에 "반려됨 · 사유" 표식이 이미 있습니다. 결재함의 "내 신청" 목록에서도 항목별 상태(반영 n · 반려 m)를 보여 주면 추적이 끝까지 이어집니다.

### 5. DA# · SWS 사용자 기대와 차이
- 기대와 맞는 부분: 단어 → 도메인 → 용어 순 의존, 형식단어, 도메인명 규칙(분류+타입+길이), 과거 이름 유지.
- 기대와 다른 부분: 도메인 변경 시 용어 · 모델 컬럼으로 영향 전파 및 영향도 목록. DA#은 변경 영향 분석이 기본입니다. "사용처 n곳"을 숫자로만 보여 주지 말고, 품의 문서에 영향 목록을 첨부하세요.
- 빠진 기능: 코드값 표 입력, 바구니 표 편집, 품의 문서에서의 영향도 요약.
- 줄일 기능: 업로드 이력과 변경 내역의 중복 표시는 변경 내역 하나에 출처 필터(엑셀 · 화면 · 마법사)로 합칠 수 있습니다.

## ⑤ 권장 최종 흐름 (표준화 담당자 → 모델러)

1. **기준정보 준비(DA)**: 도메인그룹 직접 관리 → 도메인분류는 바구니에 담습니다.
2. **사전 일괄 작성(표준화 담당자)**: [화면 일괄 작성]에서 종류 탭(분류 · 단어 · 도메인 · 용어 · 엔터티 · 코드)을 오가며 표로 입력하거나 붙여넣습니다. 행마다 즉시 검사(checkItem 공통)가 돌고, 같은 바구니 안의 의존(새 도메인 ↔ 용어)은 허용합니다. 행정 공통표준이나 기존 엑셀은 [엑셀 가져오기]로 같은 바구니에 합칩니다.
3. **바구니 정리**: 상단 배지에서 바구니를 엽니다. 정렬은 orderItems(단어 → 분류 → 도메인 → 용어 → 코드)를 따릅니다. 필요하면 [표로 편집]으로 일괄 수정하거나, 이름을 붙여 초안으로 보관합니다.
4. **품의 올리기**: 신청 검사 = 승인 재검사 기준입니다. 차단이 있으면 버튼을 막고 해당 행으로 이동시킵니다. 경고만 확인 후 올립니다. 결재선은 기관 설정(DA → 최종)을 미리 보여 주고, 품의 문서에 영향 목록(사용처 · 연쇄 갱신 예정)을 붙입니다.
5. **DA 결재**: 집계로 전체를 파악하고 항목별로 반려합니다(의존 항목 함께 반려 제안). 반려 항목은 신청자 바구니로, 나머지는 최종 승인으로 넘어갑니다. 재검사가 실패하면 원인 항목을 골라 바로 반려합니다.
6. **최종 승인 → 반영**: 버전을 올리고 과거 이름을 남깁니다. 이름 변경은 의존 용어 · 모델 컬럼에 연쇄 갱신하거나 재검토 표식을 붙입니다. 변경 내역에 출처(화면 · 엑셀 · 마법사)를 기록합니다.
7. **보완 재신청(신청자)**: 바구니의 "반려됨 · 사유" 행을 고쳐 다시 올립니다. 전체 반려도 같은 길을 씁니다.
8. **ERD 모델링(모델러)**: 사전 패널 · 자동완성 · 표준 맞추기로 반영된 용어를 씁니다. 없는 용어는 [바구니에 담기] 또는 용어 자동분석 → 바구니에 담습니다(바로 신청도 같은 검사 · dict.request 권한). 이렇게 담은 항목은 다시 3~6단계를 거칩니다.
