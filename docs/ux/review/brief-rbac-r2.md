# 리뷰 요청 — RBAC 2차 검토(설정 화면 · 서비스 시나리오)

## 사용자 요청
"settings.html 의 권한 관련 검토를 다시 하고, RBAC를 지금대로 적용해도 무방한지 리뷰하고, 서비스 시나리오에 맞도록 더 고민해서 개선이 필요한지 검토해 달라."

## 대상
- 기준 문서: `docs/ux/15-rbac.md`(권한표 · 규칙 · 1차 교차 검토 반영 · 결재 중 열람 범위). 1차 리뷰는 `docs/ux/review/codex-r1rbac.md` · `claude-r1rbac.md`.
- 정의 한 곳: `docs/ux/mockups/assets/app.js`의 `PERMS`, `canUser` · `can()` · `canActOn()` · `canUserAct`, 사용자 `USERS`(역할 · 담당 시스템).
- 화면: `docs/ux/mockups/settings.html`(탭: 기관 · 시스템 · 사용자 · 역할 · 권한표 · 검수 기준) — http://localhost:5178/settings.html?as=lee
- 그 뒤에 들어온 기능도 권한이 맞는지 본다.
  - 바로잡기(25): 업무 영역 이름 변경(결재 없이 감사 로그), 엔터티 영역 이동(모델러 직접 · 다음 확정에서 DA 확인), DBMS 변경 금지.
  - 엑셀로 ERD 시작하기(26, `import-excel.html`), 데이터 타입 · 축약명(27, `datatypes.html`, `type.*` 권한), 통합 보기(28, `model.html`).
- 서비스 흐름: `docs/ux/02-flows.md`, 입력 원칙 `docs/ux/00-inputs.md`(있으면).

## 검토 요청
1. **지금대로 적용해도 되는가**: 역할 5개(모델러 · DA · 기관 담당자 · Admin · 조회만) × 할 수 있는 일 × 범위(전체 · 담당 시스템)가 실제 서비스 시나리오(기관 1곳 · 여러 시스템 · 외주 모델러 · 감리/조회)에 맞는가. 빠진 역할 · 권한, 너무 넓은 권한, 서로 어긋나는 권한.
2. **직무 분리**: 신청자 · 1단계 승인 · 최종 승인 분리, 자기 승인, Admin이 표준 · 결재에 개입하는 범위, 권한 상승 경로(Admin이 자기 역할 추가 등).
3. **화면과 정의의 일치**: `PERMS`와 화면 검사(`can()`)가 다른 곳, 권한표에 없는 버튼 검사(`ME.has` 등 하드코딩), 담당 시스템 범위가 새지 않는가.
4. **설정 화면 사용성**: 권한표 읽기 쉬움(줄 · 칸 정렬, 묶음, 범위 배지), 사용자 · 역할 패널에서 역할을 바꿀 때 영향 보이기, 감사 로그.
5. 결과는 한국어로, 번호를 붙여(심각도 높음 · 중간 · 낮음 · 근거 파일:줄 · 고칠 방법) 쓴다. 파일은 고치지 않는다.
