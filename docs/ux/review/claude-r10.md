### 6.3 마무리 판단 — v7로 목업 반복을 끝내도 되는가

**된다고 판단합니다.** 조건은 v7을 "넓히기"가 아니라 "끝 고리 잇기"로 한정하는 것입니다.

- **수확 체감**: v4→v5→v6에서 닫힘 수는 엄격 기준으로 계속 0~1/10이지만, 남은 결함의 성격이 바뀌었습니다. v4·v5의 결함은 화면 흐름(어디로 가는지·무엇이 보이는지)이었고, v6의 상위 결함 대부분은 **실행 시점 최신성·동시성·원자성·불변성**입니다. 이는 localStorage 목업으로는 흉내만 낼 수 있고 닫을 수 없습니다(로드 때의 `ME`, 탭별 전체 덮어쓰기, 분 단위 ID).
- **목업으로 닫을 수 있는 것은 이제 6개 묶음뿐**입니다((a) 1~6). 모두 기존 화면의 연결 수정이고, 새 화면이 필요 없습니다.
- **구현 설계의 입력이 이미 충분합니다**: 합의 원인 S1~S6과 (b) 6개가 API 계약(제출 스냅숏·멱등 키·기대 상태·트랜잭션·기준본 ID)으로 바로 옮겨집니다. 더 다듬으면 목업에서 서버 규칙을 클라이언트로 재구현하는 비용만 늘어납니다.
- **권장 진행**: v7 반영 → 두 검토자가 (a)의 6개 시나리오만 클릭 확인(전면 재검증 없음, 새 발견은 '상'만 보고) → 06에 목업 동결 기록 → 구현 설계(서버 판정·API) 시작. v7 확인에서 '상'이 남으면 그 항목만 설계 문서의 수용 기준으로 옮깁니다.
