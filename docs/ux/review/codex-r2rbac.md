# RBAC 2차 검토

1차 리뷰 두 건과 기준 문서, 설정 화면 및 25~28번 기능의 목업 소스를 대조했다. 아래 판정은 정적 검토 기준이며 브라우저 동작은 확인하지 않았다.

### RB-01 · 높음 · 결재 중 사전 품의의 열람 제한이 상세에서 풀린다

- **근거** `docs/ux/15-rbac.md:93–102`, `docs/ux/mockups/approvals.html:174–180,537–545`, `docs/ux/mockups/assets/app.js:1161–1164`
- 권한표와 목록은 품의자와 결재 담당자만 볼 수 있다는 규칙을 전제로 한다. 상세는 `roView`를 통해 사전 조회 권한만 있어도 진행 중인 사전 품의를 읽을 수 있게 한다. 사전 조회 권한은 조회 전용 계정에도 주어진다.
- **고칠 방법** 목록·검색·상세·첨부에 동일한 문서 열람 판정을 적용한다. 사전 검토 의견을 공개할 업무가 있다면 공개할 항목과 대상을 별도로 승인하고 품의 본문과 분리한다.

### RB-02 · 높음 · 자기 승인 정책과 결재 가능 인원 계산이 어긋난다

- **근거** `docs/ux/00-inputs.md:24,56–63`, `docs/ux/15-rbac.md:36–47,78–80`, `docs/ux/mockups/assets/app.js:112–118`, `docs/ux/mockups/approvals.html:553–556,708–721,740–746`, `docs/ux/mockups/settings.html:577–578`
- 자기 승인 비허용은 승인 버튼과 승인 실행에 반영되지만 결재 후보 계산에는 반영되지 않는다. 신청자가 유일한 DA여도 1단계 인원 조건을 통과할 수 있다. 또 신청 시점에는 실제 1단계 처리자가 정해지지 않아, DA와 기관 담당자를 겸한 동일인이 양쪽 단계의 유일한 후보라면 신청 때는 통과해도 1단계 처리 후 최종 승인자가 사라진다. 설정의 경고는 시스템당 첫 영역과 가상 신청자만 검사한다.
- **고칠 방법** 승인·반려·열람의 자격과 현재 단계의 담당자를 명시하고, 자기 승인 정책을 후보 산정·버튼·알림·실행에 일관되게 적용한다. 신청할 때 단계별 인원과 함께 서로 다른 담당자 조합의 존재를 확인한다. 역할·담당 변경 전에는 실제 진행 문서와 남은 단계를 검사해 대체 담당자를 지정하거나 변경을 보류할 수 있게 한다. 겸임 동선을 유지하되, 독립 검토가 필요한 시스템은 최종 승인 필수로 운영한다.

### RB-03 · 높음 · Admin이 계정 관리와 결재 통제 및 표준 변경을 겸한다

- **근거** `docs/ux/mockups/settings.html:391–414,532–554,559–563`, `docs/ux/mockups/assets/app.js:76–91`, `docs/ux/mockups/datatypes.html:306–322`
- 자기 계정 역할 변경은 막지만 동일 Admin이 다른 계정의 승인 역할 부여와 로컬 인증 초기화를 모두 맡을 수 있다. Admin 단독으로 자기 승인 정책과 최종 승인 사용 여부를 바꿀 수 있고, 영구 삭제·도메인그룹 직접 관리·타입 정책 변경도 가능하다. Admin 단독의 승인 버튼 제한만으로는 업무 결정의 독립성을 보장하기 어렵다.
- **고칠 방법** 계정 운영, 고위험 역할 부여, 결재 정책 변경, 표준 유지보수 권한을 구분한다. DA·기관 담당자·Admin 부여와 독립 검토 요건 완화에는 별도 승인자를 두고, 결재 권한 계정의 인증 복구에도 독립된 확인을 둔다. 표준 변경과 영구 삭제는 해당 업무 권한을 별도로 받은 사용자에게 부여한다.

### RB-04 · 높음 · 외주 모델러와 감리의 조회 범위를 제한할 수 없다

- **근거** `docs/ux/15-rbac.md:13–27,38–39,66–69,93–108`, `docs/ux/mockups/assets/app.js:69–91,97–108,1162–1167`
- 시스템 담당 지정은 모델러의 쓰기와 모델 결재에 적용된다. 모델·DDL·산출물의 기본 권한은 모든 역할에서 기관 전체이고, DA와 기관 담당자는 완료된 다른 시스템 결재도 조회할 수 있다. 조회만 계정에는 시스템별 열람 제한이나 완료 결재·감사 증적의 지정 열람을 부여할 방법이 없다. 외주 프로젝트의 범위 제한과 감리 증적 제공을 동시에 만족시키기 어렵다.
- **고칠 방법** 기관 공통 사전 조회와 시스템 자산 조회를 구분하고, 모델·DDL·산출물·검색 및 완료 결재의 시스템 범위를 지정할 수 있게 한다. 외주는 계약 시스템과 만료일을 지정하고, 감리는 맡은 시스템의 확정본·완료 문서·지정 증적에 한정한 읽기 권한으로 운영한다. 기관 전체 조회가 필요한 내부 사용자에게는 그 범위를 명시적으로 부여한다. 역할 겸임 시 서로 다른 시스템의 역할을 독립적으로 지정할 필요가 있다면 역할별로 범위를 저장한다.

### RB-05 · 높음 · 엑셀 ERD 가져오기 취소에 권한과 결재 잠금 검사가 빠졌다

- **근거** `docs/ux/26-erd-excel-import.md:35–36`, `docs/ux/mockups/import-excel.html:293,402–414,425–432`, `docs/ux/mockups/assets/app.js:1059–1062`
- 적용에는 모델 편집 권한과 기존 영역 잠금 검사가 있다. 취소는 버전과 편집 리비전만 비교한 뒤 영역을 삭제하거나 이전 모델을 저장한다. 결재 상태만 바뀌었거나 담당 권한이 회수된 경우를 취소 시점에 판별하지 않는다. 새 영역을 통째로 삭제하는 분기에는 결재·참조 이력 확인도 없다.
- **고칠 방법** 적용과 취소 모두 최신 계정으로 대상 시스템·영역 권한과 작업 상태를 다시 검사한다. 가져오기가 만든 영역을 삭제할 때는 후속 결재·참조·편집이 생겼는지 함께 확인한다. 제품에서는 검사와 변경을 한 트랜잭션으로 처리한다.

### RB-06 · 중간 · 타입 권한의 시스템 범위와 실제 변경 영향이 다르다

- **근거** `docs/ux/27-datatype-abbreviation.md:28–35`, `docs/ux/mockups/assets/app.js:82–85`, `docs/ux/mockups/datatypes.html:190–191,306–322,375–396,403–428`
- DA의 시스템별 매핑 탭 수정은 담당 시스템 범위지만, 타입 편집 저장은 공통·표준 타입을 쓰는 시스템들의 기본 매핑도 갱신한다. 추가 타입 권한은 다른 시스템 전용 타입 등록과 요청 처리까지 포함한다. 사용자 패널은 이를 개별 권한으로 보여 주고도 겸임 사용자가 직접 등록할 수 있으면 요청 버튼을 숨긴다는 점은 설명하지 않는다.
- **고칠 방법** 기관 공통 표준 변경에 따른 기본 매핑 전파와 시스템 전용 타입·매핑·요청 처리를 구분해 권한표에 표시한다. 시스템 전용 작업은 대상 코드로 제한하고, 기관 공통 전파는 별도 권한과 영향 확인을 거친다. 등록·반려·매핑 저장 시 최신 권한을 확인하고 직접 등록과 요청 버튼의 우선순위를 명시한다.

### RB-07 · 중간 · 바로잡기 작업의 권한이 설정·모델 편집에 묶여 있다

- **근거** `docs/ux/25-correction-flows.md:35–57,83–91`, `docs/ux/mockups/assets/app.js:218–234,2013`, `docs/ux/mockups/model.html:2279–2286,2307–2309,2331–2332`, `docs/ux/mockups/settings.html:99`
- 영역 이름·설명·담당 변경은 담당 모델러 또는 Admin에게 열리고 감사 로그에 남는다. 영역의 시스템 이동·복제·중지·삭제는 `settings`로 판단하지만 권한표의 설명에서 빠져 있다. 엔터티 이동은 같은 시스템에서 양쪽의 편집 가능 여부를 확인한다. 다만 참조 영향 미리보기는 다른 영역의 작업본을 직접 읽어 참조 사실을 계산하므로 결재 중인 원본의 열람 제한과 맞지 않을 수 있다. 시스템 DBMS는 설정 화면에서 변경 불가로 표시된다.
- **고칠 방법** 영역 정보 수정, 시스템 이동·복제, 보관·삭제 권한을 권한표에 명시한다. 엔터티 이동은 양쪽 편집 권한과 다음 확정에서 DA 검토를 유지하고, 참조 영향의 사용자 표시에는 열람 가능한 버전만 사용한다. DBMS 불변 조건은 시스템 저장 시에도 검증한다.

### RB-08 · 중간 · 권한표, 사용자 패널, 결재 화면의 의미가 어긋난다

- **근거** `docs/ux/15-rbac.md:19–41,83,93–99`, `docs/ux/mockups/assets/app.js:69–91,99–108,2229–2240`, `docs/ux/mockups/approvals.html:177,188–202,550–556`, `docs/ux/mockups/settings.html:232,513,578,595–598`
- `dict.group`과 `dict.common`은 코드와 화면에 있고 기준 문서 표에는 없다. `model.submit`의 표 문구는 회수를 포함하지만 문서는 신청자에게 별도 회수 권리를 둔다. ‘모든 결재 문서 보기’도 진행 중에는 제한된다. 결재함의 일부 탭·안내와 상단 관리 메뉴는 역할 이름을 쓰고, 설정의 중지 확인에 표시하는 대기 건수도 담당 범위와 최종 승인 제외 조건을 반영하지 않는다.
- **고칠 방법** 권한 정의에 회수의 신청자 조건, 완료 결재 조회, 엑셀 ERD 가져오기 및 관리 행위를 명시하고 기준 문서와 화면이 같은 뜻을 쓰게 한다. 메뉴 진입은 해당 권한으로, 문서 안내와 대기 건수는 실제 문서 판정으로 표시한다. 역할 이름은 역할 소개와 배지에 사용한다.

### RB-09 · 중간 · 역할 변경 전에 영향이 보이지 않고 감사 기록도 범위 차이를 충분히 남기지 않는다

- **근거** `docs/ux/mockups/settings.html:513,525–554,557,568,577–578`, `docs/ux/mockups/assets/app.js:1088`
- 사용자 패널의 ‘할 수 있는 일’은 저장된 사용자 기준이고 역할 체크 변경은 선택 상태만 바꾼다. 결재 공백 경고는 저장 뒤에 나온다. 역할과 담당을 동시에 바꿔도 같은 감사 항목에는 역할 전후만 남고, 담당만 바꾸면 어느 시스템이 추가·제거됐는지 기록되지 않는다.
- **고칠 방법** 저장 전에 권한과 담당 범위의 추가·제거, 영향을 받는 진행 결재, 세션 종료 여부를 보여 준다. 변경 감사에는 행위자·대상 ID·역할과 시스템 코드의 전후·변경 사유를 함께 남기고 설정에서 해당 감사 기록을 바로 열 수 있게 한다.

### RB-10 · 낮음 · 권한표에서 행과 범위 예외를 따라가기 어렵다

- **근거** `docs/ux/mockups/settings.html:12–16,145–151,595–598`, `docs/ux/15-rbac.md:13–17,34–38`
- 영역별 묶음, 역할 열 가운데 정렬과 범위 배지는 이미 있다. 다만 고정 너비의 작업 열과 역할 다섯 열 뒤쪽에 참고가 있어, 좁은 화면에서는 결재의 범위 예외를 셀과 함께 읽기 어렵다. ‘담당 시스템’ 배지만 보면 기관 전체 사전 결재 범위가 드러나지 않는다.
- **고칠 방법** 결재 셀에 ‘사전: 기관 전체 / 모델: 담당 시스템’을 직접 표시하고 열 제목과 첫 열을 가로·세로 스크롤 중에도 따라갈 수 있게 한다. 작업명을 먼저 읽도록 권한 ID의 공간을 줄이고, 조회만은 역할 열에서 설명한다.

### RB-11 · 낮음 · 통합 보기에서 조회와 편집의 경계를 안내할 필요가 있다

- **근거** `docs/ux/28-erd-integrated-view.md:92–98,111–115`, `docs/ux/mockups/model.html:264–279,296–305`
- 모델의 논리·물리 통합은 업무 영역 안의 보기 방식이므로 기존 `model.edit` 및 버전 잠금을 그대로 쓰는 것이 맞다. 시스템 전체 ERD는 별도로 조회 전용이다. 여러 시스템과 감리 시나리오에서는 두 화면의 범위가 비슷한 용어로 보일 수 있다.
- **고칠 방법** 권한표에서 업무 영역의 통합 보기와 시스템 전체 ERD를 구분해 설명한다. 통합 보기에서도 해당 모델 버전의 열람이 허용될 때만 논리·물리 정보를 함께 보여 주고, 잠금이나 담당 범위로 편집이 제한되면 기존 모델 안내를 재사용한다.

## 지금대로 적용해도 되는가

운영 서비스에는 지금대로 적용하기 어렵다. 한 기관 안에서 역할을 겸하는 내부 사용자의 기본 흐름에는 현재 다섯 가지 구분을 유지할 수 있다. 여러 시스템에 외주와 감리 계정까지 들어오는 운영에서는 결재 중 열람, 시스템별 조회, 자기 승인과 결재 공백, Admin의 권한 부여와 결재 정책 변경, 엑셀 가져오기 취소를 먼저 보완해야 한다. 그 뒤 권한표와 사용자 변경 화면에 실제 적용 범위를 표시하고, 서버에서 열람·변경 요청마다 같은 규칙을 집행하는 조건으로 적용하는 것이 적절하다.
