# 검토 요청: ERD 관계 연결 · 삭제 시나리오 (UX 전문가 관점)

NeoDB(데이터 표준 · 모델링 웹 도구, 사용자는 DA#에 익숙한 데이터 모델러 · DA)의 ERD에서 **테이블 사이 관계를 연결 · 설정 · 삭제하는 시나리오**를 검토해 주세요. 지금은 FE 목업 단계입니다(`docs/ux/mockups/model.html`, 미리보기 http://localhost:5178/model.html?system=ERP&area=e_tr&as=kim).

## 사용자 요구

1. 테이블을 선택하고 테이블끼리 연결하면 **PK · FK가 자동으로 할당**되고, **관계를 설정**할 수 있어야 한다.
2. 관계를 삭제할 때도 **연결 조건에 따라 삭제하는 방법을 사용자가 정할 수 있어야** 한다.

## 지금 설계와 구현

설계 문서는 `docs/ux/03-erd-editor.md` §4이고, 구현은 `model.html`입니다. 관련 함수:
- 캔버스 click의 `tool === 'rel'` 분기
- 관계 패널(`eg` click)
- `rel-ident` · `rel-del`
- `askDelete`
- 속성 그리드 `agDel` · `agPkOff` · `pkSpread` · `pkReach` · `makeFk`
- `app.js`의 `fkOf`

**연결 흐름**
1. [관계] 도구(R)에서 유형을 고른다(1:N 비식별 · 1:N 식별 · 1:1 · M:N · 배타 묶기).
2. 부모를 클릭하면 강조 · 미리보기 선이 그려진다.
3. 자식을 클릭하면 관계가 생기고 FK가 자동으로 붙는다.
   - 부모 PK가 자식 FK가 되고, 짝(`fkp`)을 기억한다.
   - 식별 관계면 자식 PK + NOT NULL도 된다.
   - 이름이 겹치면 `원○○`(`ORG_`)으로 자동 명명하고 토스트로 알린다.
   - 같은 테이블이면 재귀 확인 후 `상위○○`(`UPR_`)을 만든다.
   - M:N은 FK 없이 만들고 [M:N 해소]로 처리한다.
4. 관계 패널에서 식별 ↔ 비식별 전환을 하면 손자 FK까지 바뀐다. 실행 취소가 있다.

**삭제 흐름**
- 관계: "FK 일반 속성으로 유지" / "FK 속성도 삭제"
- FK 속성: "속성만(관계는 FK 누락)" / "관계까지"
- 부모 PK: "자식 FK도 삭제" / "자식 FK는 일반 속성으로"
- 테이블: 영향 확인 후 FK 처리를 고른다.

**빈 곳(확인함)**
- 관계명 · 선택성 · 유형 · FK 짝 편집이 없다. 선택성은 "부모 필수 · 자식 선택"으로 고정 표시된다.
- 부모 PK가 없으면 FK 없이 관계만 생기고 안내가 없다.
- 이름이 겹칠 때 설계는 역할명 입력 팝업인데, 구현은 자동 명명이다.
- 부모 PK를 끌어다 놓아 관계를 만드는 방식(설계 채택)이 없다. 1:1의 UK도 없다.
- 식별 관계를 삭제할 때:
  - "유지"를 고르면 자식에 PK 표시가 남는다.
  - "삭제"를 고르면 손자 FK가 정리되지 않는다.
  - 재귀 · 역할명 · 같은 자식으로 가는 두 번째 관계도 선택지가 같다.
- DB 삭제 규칙(ON DELETE RESTRICT · CASCADE · SET NULL)이 설계에 없다(DDL · 정의서에도 없음).

## 지금 검토 중인 보완안 (초안)

- 관계 패널을 편집 가능하게 만든다:
  - 관계명
  - 유형
  - 선택성 — 비식별은 FK 필수 여부와 연결
  - FK 짝(자식 컬럼 ↔ 부모 PK, 역할명)
  - 삭제 규칙(RESTRICT · CASCADE · SET NULL — SET NULL은 선택 관계일 때만)
- 연결할 때:
  - 부모 PK가 없으면 "식별자를 먼저 정하세요"를 묻는다.
  - 이름이 겹치면 역할명 입력 팝업을 띄운다.
  - 1:1이면 FK에 UK를 붙인다.
- 관계 삭제를 조건별로 다르게 묻는다:
  - 비식별: 남기기 / FK 삭제
  - 식별: 자식 PK에서 빼고 남기기 / 손자까지 함께 삭제
  - 재귀 · 역할명: 그 역할 컬럼만 정리
  - 영향(자식 · 손자 컬럼, DDL 변화)을 미리 보여 준다.
- 삭제 규칙을 DDL의 `ON DELETE`, 정의서의 "삭제 규칙" 열에 반영한다.

## 부탁하는 것 (UX 전문가 관점)

1. 위 시나리오와 보완안의 **문제점과 수정안**.
   - 사용자가 헷갈릴 개념(**관계 삭제 = 모델 구조 정리** vs **ON DELETE = DB 행 삭제 규칙**을 한 화면에서 섞는 위험)
   - 용어 · 기본값 · 확인을 묻는 횟수
2. 연결 순간의 **최소 마찰 흐름**:
   - 묻지 않고 자동으로 할 것
   - 꼭 물어야 할 것
   - 나중에 고치게 둘 것
3. 삭제 선택지의 **구조**:
   - 조건 표(관계 유형 × FK 상태 × 하위 영향)
   - 기본 선택
   - 되돌리기
   - 미리보기 형태
4. 관계 설정 패널의 **항목 순서와 표현**(DA# · ERwin 사용자 기준). 선택성 · 카디널리티 · 삭제 규칙을 어떻게 보이게 할지.
5. 키보드 · 접근성 · 실수 방지.
6. 빠진 경우: 복합 PK, 부모 PK 변경 뒤 기존 관계, 참조 엔터티(다른 영역)와의 관계, 결재 중 · 조회 전용.
