# RBAC(r1) 검토

커밋 `0d4ce24`의 목업과 [15 역할·권한](../15-rbac.md), [14 사용자 계정·인증](../14-user-account-auth.md)을 정적으로 대조했다. 아래 코드 경로는 `docs/ux/mockups/`를 기준으로 한다.

### 1. 높음 — 담당 결재자가 없어도 신청과 단계 전환이 진행된다

- 위치 `assets/app.js:97,132–149,575–579`, `approvals.html:334–338`, `settings.html:374–381,393–395`, `docs/ux/14-user-account-auth.md:108`
- 문제. 담당 시스템에 유효 DA가 없어도 신청이 저장되어 모델이 잠긴다. DA는 승인할 수 있어도 해당 시스템의 최종 승인자가 없으면 다음 단계에서 멈춘다. 최초 및 최종 알림은 역할로만 수신자를 고르므로 담당 밖 사용자나 중지 계정에도 향하고, 대기함에는 범위를 통과한 문서만 표시된다. 담당 변경·역할 회수·계정 중지로 이미 진행 중인 문서에도 같은 공백이 생긴다.
- 수정. 실제 결재 자격과 알림 수신자에 같은 판정을 쓰고, 신청 시 활성 결재선 전 단계를 확인한다. 다음 단계로 넘길 때와 계정·담당 변경 시에도 처리 가능 인원을 다시 확인한다. 공백이 생기면 14 §8의 인계 규칙에 따라 유효 담당자에게 배정하거나, 인계 완료 전 전환을 보류하고 담당자 지정 방법을 안내한다.

### 2. 높음 — 알 수 없는 대상과 문서 유형에서 시스템 제한이 풀린다

- 위치 `assets/app.js:81–97,409–416`, `model.html:708`
- 문제. 범위 인자가 없거나 시스템을 해석하지 못하면 `canUser()`가 역할만으로 허용한다. `doc.type`이 `model` 이외의 모든 값이면 기관 전체로 처리한다. 특히 모델 문서의 영역이 삭제되었거나 조회되지 않으면 화면의 현재 시스템으로 대체되어 같은 문서의 결재 자격이 화면 문맥에 따라 달라질 수 있다. 결재선과 모델 내용은 제출 시 보존하지만 시스템 식별자는 별도 필드에 고정하지 않는다.
- 수정. 권한 목록을 표시할 때 쓰는 역할 자격 조회를 실제 실행 판정에서 분리한다. 실행은 지원하는 문서 유형과 대상 식별자를 명시적으로 확인하고, 복수의 대상 정보가 일치하는지도 검증한다. 제출 시 검증된 시스템 ID를 문서에 보존하고, 과거 문서는 원래 소속을 확인해 보정한다. 소속을 확인할 수 없으면 결재를 보류하고 인계 또는 복구 대상으로 표시한다.

### 3. 높음 — 최종 승인 단계가 독립 검토자를 보장하지 않는다

- 위치 `docs/ux/15-rbac.md:38`, `assets/app.js:73–75,97`, `approvals.html:249–254,284,318,334–338`
- 문제. 신청자에게 DA와 기관 담당자 역할이 모두 있으면 두 단계 모두 같은 사람이 자기 승인할 수 있다. 신청자가 아닌 겸임 결재자도 두 단계를 연속 처리할 수 있다. 최종 승인을 끈 결재선에서는 자기 승인 한 번으로 확정·반영된다. 자기 승인 사유와 이력은 남지만 문서가 약속한 독립 검토를 보장하지 못한다.
- 수정. 다단계 결재의 최종 승인자에서 신청자와 직전 승인자를 제외하고, 직전 승인자의 계정 ID를 이력에 보존한다. 단일 단계에서 자기 승인을 허용할지 명시하고, 허용하는 경우에도 적용 범위와 사유 요건을 정한다. 독립 검토 조건을 결재함, 제출 전 담당자 확인, 실행 판정에 함께 적용한다.

### 4. 높음 — 조회 전용 계정에도 사전 신청과 엑셀 쓰기 경로가 열린다

- 위치 `assets/app.js:69–70,132–149`, `dictionary.html:47,397`, `excel-import.html:243,260–261,455–460`, `docs/ux/14-user-account-auth.md:35`
- 문제. `dict.request`는 모델러와 DA에게만 주지만 사전 신청 저장은 해당 권한을 검사하지 않는다. 엑셀 화면도 예시·잠금·묶음 소유 여부로만 쓰기를 제한한다. 조회 전용, 기관 담당자 단독, Admin 단독 계정이 사전 신청이나 새 엑셀 묶음 저장·제출을 할 수 있다.
- 수정. 사전 신청과 엑셀 저장·제출 입구 및 실행 시 `dict.request`를 확인한다. 기존 묶음의 열람 자격과 수정 자격은 별도로 처리하고, 공용 문서 생성에서도 문서 유형에 맞는 신청 권한을 확인한다.

### 5. 중간 — 결재 문서와 제출 사본에 서로 다른 열람 정책이 적용된다

- 위치 `assets/app.js:65,75,638`, `approvals.html:176,248,265`, `model.html:348–350,1187–1193,1322`, `ddl.html:76`, `outputs.html:86–100`
- 문제. 결재 상세는 신청자·참조자·전체 열람 권한자를 검사하지만 모델 및 DDL의 제출 사본 선택에는 그 판정이 없다. 권한표는 모든 시스템의 모델·DDL·산출물 읽기를 허용하며, 검토 중 제출 사본과 확정본에 같은 공개 범위를 적용할지는 명시하지 않았다. 결재 문서를 열지 못하는 사람도 제출 모델을 읽을 수 있는 현재 결과가 정책에 맞는지 결정해야 한다. 결재 상세의 산출물 링크도 검토 중에는 제출 사본 ID를 전달하지 않아 작업본 계열을 열 수 있다.
- 수정. 검토 중인 제출 사본, 공개 확정본, 결재 본문의 열람 범위를 명시한다. 해당 정책에 따라 모델·DDL·산출물에서 동일한 사본 대상과 열람 판정을 쓰고, 결재 자료의 산출물 링크가 가리키는 버전을 명시한다. 결재 문서의 참조자 지정이 편집·승인 범위에 영향을 주지 않도록 유지한다.

### 6. 중간 — Admin의 공표·영구 삭제 권한이 한 항목에 묶였다

- 위치 `docs/ux/15-rbac.md:29`, `assets/app.js:72,87`, `dictionary.html:253,294–296`, `dict-history.html:44–45`, `settings.html:343,421`
- 문제. Admin 단독도 `can('dict.publish')`를 통과하고 사용자 패널에는 공표를 포함한 항목이 표시된다. 실제 공표 버튼과 변경 내역에서 들어오는 공표 경로는 `ME.has('da')`로 다시 나뉜다. 영구 삭제 로그 역시 DA·Admin 역할을 직접 검사해 권한표만으로 버튼의 노출 여부를 설명할 수 없다.
- 수정. 공표와 영구 삭제 권한을 분리해 Admin에는 영구 삭제만 부여한다. 삭제 로그 열람 범위도 명시하고 버튼, 직접 진입, 실행, 사용자별 안내에서 각 권한을 사용한다.

### 7. 중간 — 모델 확정 신청·회수가 권한표의 모델 제출 권한을 사용하지 않는다

- 위치 `assets/app.js:66–68`, `model.html:436–441,700–718`, `approvals.html:313–319`
- 문제. 확정 신청은 편집 가능 여부를 재사용하고, 모델·결재 화면의 회수는 신청자와 진행 상태를 검사한다. 담당 시스템이 바뀌거나 모델러 역할을 잃은 신청자가 자기 문서를 회수할 수 있어 `model.submit`의 담당 시스템 범위와 어긋난다. 반대로 신청자의 회수까지 막으면 담당 변경 후 잠긴 모델을 풀 수 있는 경로가 필요하다.
- 수정. 확정 신청에 `model.submit`을 적용한다. 회수를 신청자 권리로 유지할지, 현 담당 범위로 제한하고 인계·관리 회수를 둘지 결정한 뒤 두 화면의 노출·실행 조건과 권한표를 일치시킨다.

### 8. 중간 — 모델에서 시작하는 사전 작업에 출처와 변경 대상 구분이 없다

- 위치 `model.html:197,328–333,467`, `standardize.html:102,237–250`, `assets/app.js:70,91,628–634`, `excel-import.html:455`
- 문제. 같은 기관 사전 업무에서 모델 후보 등록은 모델 편집 범위에 막히고, 엑셀 링크는 영역 문맥을 넘기지 않는다. 표준 맞추기는 영역 편집이 가능한 경우에만 용어 신청과 모델 연결을 함께 실행한다. 사전 결재가 기관 전체인 것은 문서와 일치하지만, 현재 경로는 기관 사전에만 제출하는 작업과 모델에 신청 번호를 붙이는 작업을 구분하지 않는다. 모델 후보는 선택한 참조 엔터티도 발생 위치로 기록할 수 있어 공통 원본과 사용 위치가 혼동된다.
- 수정. 기관 사전 신청·엑셀·후보 등록에는 사전 권한을, 모델에 신청을 연결하거나 모델 데이터를 변경할 때는 해당 영역의 편집 권한과 잠금 검사를 적용한다. 출처 영역을 저장하되 사전 결재 범위는 기관 전체로 유지한다. 참조 엔터티는 사용 위치와 공통 원본을 구별해 기록하고 제출 사본에서 시작한 경우 버전도 표시한다.

### 9. 중간 — 열린 화면에서 담당 시스템 변경과 권한 회수가 즉시 반영되지 않는다

- 위치 `assets/app.js:39–42,58–61,95,560,1406–1413`, `settings.html:377–381`, `import.html:67,113–114`, `system.html:55,60`, `docs/ux/14-user-account-auth.md:85,100`
- 문제. `can()`이 보는 사용자 목록은 화면 로드 시 읽은 값이다. 사용자 선택 변경 감지는 같은 ID의 담당·역할·상태 변경을 감지하지 않는다. 담당 시스템만 줄이면 역할 회수와 달리 세션 폐기 표시가 생기지 않는다. 가져오기 실행은 화면을 열 때의 결과를 재사용하고, 업무 영역 생성 실행은 사용자 전환 여부만 확인한다.
- 수정. 실행 시 현재 계정·담당과 세션 유효성을 확인하고, 담당 범위가 줄어드는 변경도 권한 회수에 포함한다. 가져오기·영역 생성에서 검증한 대상 시스템을 쓰기까지 일관되게 사용한다.

### 10. 중간 — 설정·홈·결재함 일부가 역할 이름을 권한으로 사용한다

- 위치 `settings.html:191,270,312,324,344,374–377,407,412`, `assets/app.js:639,1214`, `home.html:83–93,105–106,142,158`, `approvals.html:104–115,222`
- 문제. 설정 진입은 `settings`로 검사하지만 인증·사용자 관리 작업은 `users` 대신 Admin 역할을 직접 검사한다. 현재 두 권한은 Admin에 묶여 있어 결과가 같지만 권한표에서 분리하면 실제 화면과 관리 작업이 따라오지 않는다. 결재함 ‘전체’ 필터는 `canSeeDoc()`을 다시 구현하며, 홈의 ‘내 후보’는 후보 등록을 할 수 있는 DA 단독 사용자를 제외한다. 업로드 묶음 열람의 ‘본인 또는 DA’도 권한표에서 확인할 수 없다.
- 수정. 실제 기능 노출과 목록 범위는 해당 권한 또는 공용 열람 판정을 사용한다. 묶음 열람 정책은 본인과 기관 전체 권한을 명시한다. 역할 이름은 화면 제목과 역할 배지처럼 표시 목적에 사용한다.

### 11. 중간 — 결재 안내가 담당 범위와 실제 대기함을 설명하지 못한다

- 위치 `approvals.html:115,256,318,410–411`, `model.html:709`, `excel-import.html:400`
- 문제. 담당 밖 결재자에게는 해당 단계의 역할 이름만 보이고 처리할 수 없는 이유가 나오지 않는다. 신규 신청 안내와 기본 탭은 실제 문서의 처리 자격 대신 DA 여부를 사용한다. 모델 제출 완료 문구는 유효 수신자 존재 여부와 관계없이 DA에게 보냈다고 알린다.
- 수정. 해당 단계의 권한 판정 결과를 토대로 역할 부족, 담당 범위 밖, 결재자 미지정, 자기 승인 가능 여부를 안내한다. “내 대기함에 추가됨”은 실제로 추가된 경우에만 쓰고, 그 밖의 신청자는 ‘내 신청’에서 문서를 확인하게 한다.

### 12. 낮음 — 조회 전용과 적용 실패의 사유가 화면마다 다르다

- 위치 `docs/ux/15-rbac.md:46–48`, `import.html:67–68`, `standardize.html:164–165,237`, `system.html:55`, `settings.html:343,420–421`
- 문제. 담당 밖 모델러에게 DDL 가져오기는 “모델러 역할만”이라고 안내하고, 표준 맞추기 적용 실패는 권한 조건도 작업 버전 변경으로 표시할 수 있다. 사용자 패널에는 결재 범위가 담당 시스템으로만 표시되어 사전 결재가 기관 전체임을 알기 어렵다. “요구사항관리은(는)”처럼 조사를 그대로 노출하는 예도 있다.
- 수정. 역할 부족, 담당 범위 밖, 결재 잠금, 버전 변경에 맞는 문구를 모델·가져오기·표준 맞추기·업무 영역 생성에서 일관되게 적용한다. “담당 시스템에 ‘요구사항관리’가 포함되어 있지 않습니다”처럼 자연스럽게 표시하고, 사용자 패널의 결재 범위에는 “사전 신청은 기관 전체, 모델 확정은 담당 시스템”을 각각 표시한다.
