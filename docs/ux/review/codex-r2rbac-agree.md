# RBAC 2차 합의안 협의 의견

합의안의 역할·권한 구조는 유지하는 데 동의한다. 운영 적용 전에는 기관 담당자 확인의 독립성, 자기 승인 후 최종 결재 가능 여부, 감리 증적의 조회 범위를 명시해야 한다. 아래는 목업 소스의 정적 검토이며, 화면 재현 근거는 역할별 화면 목록을 인용했다. [합의안 초안](resolution-rbac-r2.md) · [Codex 리뷰](codex-r2rbac.md) · [UX 리뷰](claude-r2rbac.md) · [역할별 화면 목록](rbac-role-inventory.md)

| R-17 | 동의 | 역할 부족일 때도 띠와 변경 요청 경로가 필요하다. 현재 편집 가능 판정을 도구 표시에 재사용해 읽기 동작과 편집 동작을 구분한다. (화면 목록, RB-11) |
| R-18 | 동의 | 담당이자 해당 작업을 할 수 있는 영역을 기본으로 열면 첫 진입에서 막히는 사례가 해소된다. 적합한 영역이 없으면 선택 안내를 표시한다. (화면 목록) |

| R-26 | 수정 제안 | 중간 이상 우선순위로 올린다. 취소 직전에 최신 권한·잠금·리비전을 검사하고, 새 영역 삭제는 이후 결재·참조·편집이 없을 때만 허용한다. (RB-05) |

## 목업 반영 제안

### R-01 · R-03 기관 담당자 확인

- `assets/app.js`의 `PERMS`에 Admin의 정책 변경 요청 권한(예: `policy.approval`)과 기관 담당자의 관리 변경 확인 권한(예: `adminChange.confirm`)을 기관 범위로 둔다. 계정 변경 요청은 `users`를 쓴다. 공용 확인 판정에서 현재 활성 계정·확인 권한·대기 상태를 검사한 뒤 요청자와 역할 변경 대상자를 제외한다. 일반 사전·모델의 `appr.final`과 `canUserAct`는 해당 업무 문서에 계속 사용한다.
- `settings.html`의 `saveAll()`에서 `finalDict`, 영역별 `finalModel`, `selfAppr`의 변경분은 `getOrg()`가 읽는 유효 설정에 바로 쓰지 않고 공용 대기 기록에 저장한다. 일반 기관 설정은 기존 방식대로 저장한다. 사용자 패널의 등록·수정도 고위험 역할 추가와 해당 역할의 범위 확대에 같은 기록을 사용한다. 대기 기록에는 요청 ID, 변경 종류, 요청자·대상 ID, 변경 전후 값, 사유, 상태, 처리자를 저장한다. 대기 중인 새 계정의 고위험 역할은 확인 전까지 발효시키지 않는다. 권한 축소는 즉시 반영하고 혼합 변경에서는 확대분만 대기로 보여 준다.
- `approvals.html`의 대기함에 ‘관리 변경 확인’을 넣어 현재 확인할 수 있는 건과 전후 값·사유를 보여 준다. 기존 결재 문서의 승인·반려·사전 반영 흐름과 별도의 [확인]·[거절] 동작으로 연결한다. 확인 직전에 최신 계정·대기 상태·유효 값·결재 공백을 재검사한다. 요청 후 바뀐 값이나 회수된 권한을 발견하면 적용을 막고 재요청 안내를 표시한다. 확인 시에만 승인된 변경분을 적용하고, 확인·거절 각각에 감사와 요청자 알림을 남긴다. 설정 띠에는 적용 중인 값과 대기 제안을 함께 보여 준다. 독립 확인자가 없는 초기 기관은 최초 기관 담당자 확보 절차를 별도로 정해야 한다.

### R-02 · R-06 자기 승인과 결재 후보

- `app.js`에 유효 설정의 `selfAppr === true`를 쓰는 공통 판정을 두고, `settings.html` 라디오와 `approvals.html`의 `selfOK` 기본값을 맞춘다. 기존 목업의 기본 허용 시드나 저장값을 자동으로 승인된 예외로 승격하지 않는다. 허용값은 R-01 확인을 거친 경우에 적용하며 기존 완료 이력은 보존한다.
- `canUserAct`는 DA 단계에서 비허용이면 신청자를 제외하고, 최종 단계에서는 항상 신청자와 실제 DA 승인자를 제외한다. `approversFor`, 대기함, 홈, 알림, 실행은 이 결과를 사용한다. 신청 점검(`lineGaps`)은 실제 신청자와 저장할 결재선 기준으로 DA별로 이어질 최종 후보가 있는지 검사한다. 정규 최종 단계가 없어도 자기 승인 분기에는 최종 후보가 필요하다. 독립 조합이 하나라도 있으면 신청을 허용하되, 독립 최종 후보가 없는 DA의 승인 경로는 차단한다. 신청자 본인의 반려 대신 회수 동선을 제공한다.
- `approvals.html`의 `act()`에서 최신 문서·계정으로 실제 자기 승인 여부와 예상 최종 결재선을 다시 계산한다. 유효 후보를 확인한 다음 문서의 `line`에 `final`을 한 번만 추가하고 `step`을 `final`로 저장한다. 연결 용어 검사의 ‘이 승인으로 확정되는가’ 판단에도 같은 결재선을 써야 한다. 최종 승인 전에는 사전 반영·모델 확정을 실행하지 않는다. 기존 문서의 저장 결재선을 보존하고, 정책 변경으로 다음 단계의 처리가 막히는 문서는 확인 전에 표시한다.

### R-11 조회 범위

- `users`로 편집하는 계정에 소속과 조회 범위(기관 전체/담당 시스템)를 저장하고, `PERMS`의 `model.view`는 전 역할에 부여하되 계정의 조회 범위를 타도록 표시한다. `canUser`에서 시스템 코드로 판정하고 `dict.view`는 기관 범위를 유지한다. 기존 계정에 필드가 없으면 확인된 내부 계정에만 기관 전체 기본값을 준다. 소속을 알 수 없는 외부 이관 데이터는 담당 범위로 제한하고 설정에서 확인한다. 담당이 없는 계정은 담당 시스템 조회 결과가 비어야 한다.
- 대상 없는 `can('model.view')`는 메뉴 노출에만 사용한다. 모델·DDL·산출물·전체 ERD의 목록, 검색, 대상 선택, 직접 URL과 스냅샷 데이터 로딩에는 `{system}` 또는 `{area}`를 전달한다. 영역·시스템 확인이 실패하면 내용을 읽기 전에 차단한다. `areaView` 등 공통 데이터 경로에도 같은 검사를 적용해 전체 ERD 집계, 표준 용어 사용처, 참조 정보가 범위 밖 모델을 드러내지 않게 한다. 내려받기는 `model.view`와 `out.export` 및 버전 열람 가능 여부를 실행 시 함께 확인한다.
- `canUserSeeDoc`에서 유효 계정과 모델 시스템 범위를 확인한 뒤 신청자·참조·결재 참여·완료 조회 규칙을 적용한다. 완료 문서는 저장된 `sysAt.code`를 우선해 영역 이동으로 과거 증적의 범위가 바뀌지 않게 한다. `canUser`의 현재 사전 문서 예외는 사전 결재 권한에 한정한다. 감사 로그는 대상 시스템과 기관 공통 증적의 구분을 저장하고, 범위를 판정할 수 없는 로그는 감리에게 기본 공개하지 않는다.

### R-17 모델 조회 전용

- `model.html`은 우선 `can('model.view', {area: AREA})`로 진입을 확인한다. 조회가 가능하면 현재 `viewOnly`·`outOfScope`·`canEdit()`·`guard()`를 활용한다. 현재 `ban-view`는 `outOfScope`일 때만 표시된다. 모델러 역할이 없으면 역할 부족 안내와 `mypage.html?req=modeler&what=모델%20편집` 링크를 표시하고, 역할은 있고 편집 담당 밖이면 기존 담당 시스템 추가 요청 링크를 표시한다. 결재 중·확정본·영역 중지·전체 ERD에는 해당 원인 안내를 우선한다.
- 렌더링에서 `canEdit()`가 거짓이면 엔터티·관계·메모 생성, 자동 배치, 되돌리기와 메모 삭제·편집성 메뉴를 숨기고 편집 도구가 선택돼 있으면 선택 모드로 복귀시킨다. 선택·이동 탐색·확대·논리/물리/통합 보기는 제공한다. 키보드·드래그·메모 수정과 저장 직전에도 기존 최신 권한·잠금 검사를 적용한다. 확정 신청은 `model.submit`과 문서·버전 상태로 별도 판단한다. 업무 영역의 통합 보기와 시스템 전체 ERD의 조회 전용 상태를 권한표에도 구분해 적는다.
