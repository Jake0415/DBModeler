## 1. 일괄 옮기기 — 미리 보기 → 실행 → 결과 → 다음 행동

### UQ-01 옮긴 뒤 그 시스템을 편집 · 결재할 사람이 없다 — 심각도: 높음
- 근거
  - 관찰: ERP → ERPPG 일괄 실행 뒤 `canUser(u,'model.edit',{system:'ERPPG'})`가 kim · park · choi 모두 false였다. 이들의 담당은 `ERP`다.
  - 담당 범위를 코드로 비교(`app.js:93 inScope`)하므로, 영역이 새 코드로 가면 기존 담당자는 모두 범위 밖이 된다.
    - 모델러 편집, DA 1단계 승인, 기관 담당자 최종 승인이 모두 막힌다.
  - 결과 창(`system.html:215-216`)은 [원래 시스템 사용 중지] · [새 시스템 홈]만 안내한다. 담당자 이야기는 없다.
  - 시스템 홈의 영역 생성에는 ‘맡은 모델러가 없다’는 경고가 있다(`system.html:96`). 일괄 옮기기에는 같은 경고가 없다.
- 제안
  - 미리 보기에 ‘원래 시스템 담당자 N명(이름)은 대상 시스템 담당이 아닙니다’를 적는다.
  - [담당 시스템도 함께 옮기기] 체크(기본 켬)를 둔다. 켜면 원래 코드를 가진 사용자에게 대상 코드를 더한다. 감사 로그 · 알림도 남긴다.
  - 체크를 끄고 실행했다면 결과 창 다음 행동에 ‘설정 › 사용자 · 역할에서 담당 지정’ 링크를 둔다.

### UQ-02 DBMS를 바로잡은 시스템은 원래 이름 · 코드로 돌아갈 길이 없다 — 심각도: 높음
- 근거
  - 이름 중복 검사가 사용 중지한 시스템까지 포함한다(`settings.html:294`). 코드도 다시 쓸 수 없다(`settings.html:295`).
  - 그래서 관리자 A는 ‘통합ERP(PG) · ERPPG’ 같은 임시 이름으로 새 시스템을 만들 수밖에 없다.
    - 옮긴 뒤에도 코드 `ERPPG`는 영구히 남는다.
    - 이름은 원래 시스템을 먼저 다른 이름으로 바꾸고 새 시스템 이름을 바꾸는, 숨은 두 단계로만 되찾을 수 있다.
  - 결과 창과 등록 창 어디에도 이 순서를 알려 주지 않는다.
  - 등록 직후 토스트(`settings.html:304`)는 영역 하나씩 옮기는 길(⋯ › 다른 시스템으로 옮기기)만 안내한다. 이번에 만든 [모든 영역 옮기기 · 복제]는 말하지 않는다.
- 제안
  - 시스템 등록 창에 ‘DBMS를 바로잡으려는 경우’ 안내를 둔다.
    - 코드는 나중에 바꿀 수 없으니 최종 코드를 쓰라고 알린다.
    - 원래 시스템 코드가 필요하면 원래 시스템을 먼저 다른 코드로 정리해야 한다는 방침을 정해 적는다.
  - 일괄 옮기기 결과 창의 다음 행동을 순서 목록으로 바꾼다.
    - ① 원래 시스템 사용 중지 ② 원래 시스템 이름 바꾸기(예: ‘통합ERP(구)’) ③ 새 시스템 이름을 ‘통합ERP’로 ④ 담당자 확인(UQ-01)
  - 등록 토스트의 동작 버튼은 [원래 시스템에서 모든 영역 옮기기]로 바꾼다. 이동 화면은 `system.html?system=<원래>&act=bulk`로 열리게 한다.
  - 장기적으로는 정리(사용 중지)된 시스템 이름을 다시 쓸 수 있게 할지 정할 것에 올린다.

### UQ-03 홈 화면은 시스템을 옛 이름 필드로 판단해 담당 영역과 DBMS가 틀리게 나온다 — 심각도: 높음
- 근거
  - `home.html:85`가 `sys: m.sys || '요구사항관리'`, `dbms: m.dbms || 'Oracle'`을 쓴다.
    - `m.sys`는 시드에만 있는 옛 이름 필드다(`app.js:542`, ERP 영역은 `'통합ERP'`).
  - 그래서 다음처럼 된다.
    - 옮긴 영역은 `m.system`만 바뀌고 `m.sys`는 그대로라, 홈에 여전히 ‘통합ERP · Oracle’로 보인다.
    - 복제본과 새로 만든 영역은 `sys`가 없어 ‘요구사항관리 · Oracle’로 보인다.
    - 담당 판정 `inScope(ME, a.sys)`(`home.html:89`)도 이 값으로 해서, 홈 ‘내 담당 영역’이 모델 · 시스템 홈과 다르게 나온다.
- 제안
  - 홈도 `sysOfArea(id)`와 시스템의 `db`(코드 → `SYSLIST`)로 바꾼다.
  - `m.sys` · `m.dbms`는 읽지 않는다. 시드를 읽을 때 지운다.

### UQ-04 결재 문서의 담당 판정이 제출 때의 시스템 ‘이름’으로 이뤄진다 — 심각도: 높음
- 근거
  - `createDoc`이 `sys: sysOfArea(o.area)`, 곧 그때의 시스템 이름을 저장한다(`app.js:163`).
  - `canUser`는 이 값을 먼저 쓴다(`app.js:103` `d.sys || sysOfArea(d.area)`).
  - 시스템 이름을 바꾸면 `sysCodeOf(옛 이름)`이 코드를 찾지 못한다. 그러면 검토 중 문서의 DA · 최종 승인자가 범위 밖이 된다.
  - §8 ‘이름을 바꿔도 담당 범위는 그대로’와 어긋난다. 결재함과 모델 화면의 판정도 달라진다.
- 제안
  - 문서에는 시스템 코드를 저장한다. 모델 확정 문서에는 `sysAt.code`가 이미 있다(`model.html:986`).
  - 판정 순서는 `d.sysAt?.code || sysCodeOf(d.sys) || 영역의 system`으로 한다. 화면에는 `sysNameOf`로 이름을 보여 준다.

### UQ-05 ‘모두 처리’가 확인 없이 바로 실행되고, 결과 창의 초점 · 상태가 정리되지 않는다 — 심각도: 중간
- 근거(`system.html:203-217`)
  - 실행 버튼을 한 번 누르면 영역 7개 복제 · 이동과 원본 사용 중지가 한꺼번에 일어난다.
    - 버튼 이름은 ‘모두 처리’라 무엇을 몇 개 하는지 드러나지 않는다.
    - ‘원본 사용 중지’ 체크(`:51`)는 기본으로 켜져 있다.
  - 실행 뒤 상태
    - `bk-go`가 숨겨지는데 초점을 옮기지 않는다. 마우스로 누른 사용자는 초점이 사라진다.
    - 결과 영역에는 `role="status"`나 초점 이동이 없어 화면 읽기 프로그램이 결과를 읽지 않는다.
    - 빈 머리줄(순서 · 업무 영역 · 처리…)이 그대로 남는다(관찰).
    - 대상 시스템 선택과 체크가 계속 켜져 있어, 바꿀 수 있는 것처럼 보인다.
  - 닫기
    - [닫기]는 `location.reload()`(`:217`)를 부른다.
    - Esc는 공용 처리(`app.js:2398`)로 창만 닫는다. 그래서 배경 표와 트리에 옮긴 영역이 그대로 남는다(관찰).
- 제안
  - 실행 버튼 이름에 건수를 넣는다. 예: `복제 6 · 옮기기 1 실행`.
  - 원본 사용 중지가 켜져 있으면 버튼을 두 번 눌러 확인하게 한다. 첫 번째 누름에 ‘원본 6개를 사용 중지합니다’를 보여 준다. 시스템 정보 창의 방식(`settings.html:323`)과 같게 한다.
  - 실행 중에는 버튼을 막고 ‘처리 중…’을 보인다.
  - 끝나면 다음처럼 정리한다.
    - 표를 숨기고 선택과 체크를 막는다.
    - 결과 머리말(`<h4 tabindex="-1">처리 결과</h4>`)로 초점을 옮긴다.
    - 결과 상자에 `role="status"`를 준다.
  - Esc로 닫아도 새로 읽게 한다. 예: `mo-bulk`에 닫힘 훅을 단다.

### UQ-06 미리 보기가 ‘복제 = 결재를 다시 받는다’는 무게와 참조 손실을 보여 주지 않는다 — 심각도: 중간
- 근거
  - 관찰: ERP에서는 7개 중 6개가 ‘복제(확정본 있음)’였다. DBMS를 바로잡는 실제 상황에서는 거의 모두 복제가 된다.
  - 복제본은 v1 작업 중으로 시작해 확정 결재를 다시 받아야 한다. 영역 하나 창(`system.html:145`)은 이 점을 적지만, 일괄 창은 적지 않는다.
  - ‘참조’ 칸(`:198`)은 참조하는 영역 수(`refsTo.length`)만 보인다. 무엇이 다시 이어지고 무엇이 빠지는지는 나오지 않는다.
    - 빠지는 예: 건너뛴 영역이나 다른 시스템을 가리키는 참조.
    - 영역 하나 창은 `copyRefPlan`으로 이를 보여 준다(`:143`).
  - ‘옮기기’ 행은 다른 시스템 영역이 이 영역을 참조할 때 끊긴다는 경고(`:141`)가 일괄 창에는 없다.
  - 단위도 섞인다. 미리 보기 ‘참조 3’은 영역 수이고, 결과 ‘참조 4 이음’은 엔터티 수다(관찰, 영업관리).
- 제안
  - 표 위에 요약 한 줄을 둔다. 예: `복제 6(확정 결재 다시 필요) · 옮기기 1 · 건너뜀 0 · 컬럼 타입 421개 변환 · 원본 6개 사용 중지`.
  - ‘참조’ 칸은 `이음 n · 빠짐 n`으로 나눈다. 빠지는 행은 위험색으로 칠하고, 툴팁이나 펼침으로 대상 영역 이름을 보인다.
  - 결과도 같은 단위(참조 엔터티 수)로 쓴다.

### UQ-07 매핑이 어떻게 적용되는지 미리 보기에서 볼 수 없다 — 심각도: 중간
- 근거
  - 일괄 창에는 ‘타입 변환 53’ 같은 숫자만 있다(`system.html:198`).
  - 무엇이 무엇으로 바뀌는지, 어느 시스템의 매핑 표를 쓰는지 알 수 없다.
  - 관리자 B가 대상 시스템 매핑을 막 고쳤다면 그 값이 쓰이는지 확인할 방법이 없다.
  - 영역 하나 창의 예시 문구(`:140` ‘예: VARCHAR2 → VARCHAR’)는 고정 문구라, 사용자 매핑과 다를 수 있다.
- 제안
  - 대상 시스템을 고르면 표 위에 `원래 Oracle 19c → 대상 PostgreSQL 15` 줄과 매핑 대응 칩을 보인다.
    - 예: `VARCHAR2 → VARCHAR · NUMBER → NUMERIC · DATE → TIMESTAMP · CLOB → TEXT`
    - 칩은 `TM_ROWS` 기준 다섯 줄이다. 같은 타입은 흐리게 보인다.
  - 옆에 [대상 시스템 매핑 보기 ↗] 링크(`settings.html#sys`, 대상 시스템 미리 선택)를 둔다.
  - 영역 하나 창의 예시도 실제 대응에서 만든다.

### UQ-08 중간 실패 · 다시 실행할 때 사용자가 상황을 알기 어렵다 — 심각도: 중간
- 근거
  - 처리 반복(`system.html:206-210`)에 예외 처리가 없다.
    - 한 영역의 `modelOf`가 예외를 던지면 그때까지 처리한 영역은 이미 저장된 채 멈춘다.
    - 그러면 결과 창도, 감사 로그(`:212`)도 남지 않는다.
  - 다시 열면, 이미 복제했지만 원본 사용 중지를 끈 영역이 ‘건너뜀 — 통합ERP(PG)에 같은 이름이 있음’으로 보인다(`:195-196`).
    - 사용자는 이를 ‘충돌’로 읽는다. 실제로는 ‘이미 복제됨’이다.
  - 건너뛴 행(결재 중)에는 결재함 링크가 없다. 영역 하나 창(`:120`)에는 있다.
  - 결과 창의 ‘남은 업무 영역 n개’(`:213, :216`)에는 일부러 사용 중지를 끈 원본도 들어간다.
    - 성공해도 경고(노란) 배너가 뜬다.
    - 어떤 영역이 남았는지 이름이 없다.
- 제안
  - 영역마다 처리를 try/catch로 감싼다. 실패는 결과에 `실패 — 사유`로 남기고, 결과와 감사 로그는 항상 남긴다.
  - 건너뜀 사유를 둘로 나눈다. 원본이 `copiedFrom`인 대상 영역이 있으면 `이미 복제됨(복제본 ‘…’ ↗)`, 아니면 `이름 겹침`이다. 결재 중이면 [결재함 ↗]을 붙인다.
  - 남은 영역은 이름과 사유(결재 중 / 원본 유지 선택)로 나눠 보인다. ‘원본 유지 선택’만 남았으면 정보(파란) 배너로 보인다.

### UQ-09 보관함 영역 · 최종 승인 설정이 함께 옮겨지지 않는다 — 심각도: 낮음
- 근거
  - `live()`가 사용 중 영역만 고른다(`system.html:191`). 그래서 보관함(사용 중지) 영역은 옛 DBMS 시스템에 남는다.
    - 나중에 [다시 사용]하면 잘못된 DBMS 시스템에서 살아난다. 미리 보기에는 아무 말이 없다.
  - 복제본은 새 영역 ID라, 원본의 ‘모델 확정 최종 승인 안 함’ 설정(`getOrg().finalModel[id]`)을 잇지 않는다. 기본값이 ‘사용’이라 결재선이 말없이 바뀐다.
- 제안
  - 미리 보기 아래에 ‘보관함 영역 n개는 옮기지 않습니다 — 필요하면 다시 사용한 뒤 처리’를 적는다.
  - 복제할 때 `finalModel[nid] = finalModel[id]`로 잇는다. 결과에도 ‘최종 승인 설정 이어받음’을 적는다.

### UQ-10 [모든 영역 옮기기 · 복제] 버튼이 아예 안 보이는 경우 — 심각도: 낮음
- 근거
  - 다른 사용 중 시스템이 없으면 버튼이 숨는다(`system.html:193`).
  - 관리자 A는 새 시스템을 먼저 등록해야 한다는 것을 이 화면에서 알 수 없다.
- 제안
  - 관리자에게는 버튼을 보여 주되 막아 둔다. 툴팁 또는 누를 때 안내로 ‘옮길 대상 시스템이 없습니다 — 설정 › 시스템 › [시스템 등록]’을 띄운다.
  - 복제가 0건이면 ‘원본 사용 중지’ 체크를 숨긴다.

## 2. 시스템별 데이터타입 매핑

### UQ-11 빈 값 · 오타 매핑이 저장되고, 옮길 때 컬럼 타입을 지우거나 망가뜨린다 — 심각도: 높음
- 근거
  - 관찰(콘솔)
    - 대상 매핑 ‘문자(가변)’를 빈 값으로 두면 `convertTypeByMap('VARCHAR2(10)', …)`이 `''`를 돌려준다. 컬럼 타입이 비어 버린다.
    - 오타 `VARCHR(n)`을 넣으면 `VARCHR(10)`이 그대로 퍼진다.
  - 입력 단계에서 막지 않는다.
    - 입력은 `trim()`만 하고 검사가 없다(`settings.html:279`).
    - [변경 보기]가 ‘(빈 값)’을 정상 변경처럼 보이고(`:388`), 그대로 저장한다(`:428`).
  - 변환 쪽에도 막는 장치가 없다. `app.js:253-254`는 대상 칸이 비면 그대로 빈 타입을 쓴다.
- 제안
  - 저장 전 검사
    - 빈 값을 막는다.
    - 형식을 확인한다. `^[A-Z][A-Z0-9 ]*(\((n|p,s|p|\d+(,\d+)?)\))?$`
    - 그 DBMS가 아는 타입 목록에 없으면 경고한다. 저장은 허용한다.
    - 같은 기본형이 두 줄에 있으면 경고한다. 찾기가 첫 줄만 맞추기 때문이다.
  - 검사 결과는 숫자 칸과 같은 방식으로 보인다. `aria-invalid`를 붙이고 오류 문구를 두며, 저장 막대는 ‘저장하지 않았습니다 — 오류 n건’으로 알린다.
  - 변환 쪽도 대상 칸이 비면 기본 변환표로 넘긴다(방어).

### UQ-12 표의 ‘길이 조건 · 비고’가 Oracle 고정이라, 시스템마다 다르다는 메시지를 흐린다 — 심각도: 중간
- 근거
  - `settings.html:108-112`의 길이 조건(`1~4000`, `p 1~38`)과 비고는 정적 문구다.
    - 비고 예: `4000 초과 → CLOB`, `밀리초 필요 시 TIMESTAMP`
  - 관찰: PostgreSQL 시스템을 골라도 값은 `TIMESTAMP` · `TEXT`인데, 비고는 ‘4000 초과 → CLOB’, ‘밀리초 필요 시 TIMESTAMP’ 그대로다.
- 제안
  - 길이 조건과 비고도 DBMS별 기본값 표(`TM_DEF`)와 함께 둔다. 예: PostgreSQL은 `VARCHAR 1~10485760`, `NUMERIC p 1~1000`, `TIMESTAMP(p) 0~6`.
  - 비고는 그 DBMS에 맞는 문장으로 바꾼다.

### UQ-13 어느 시스템의 표인지, 어느 칸이 시스템별인지 한눈에 보이지 않는다 — 심각도: 중간
- 근거
  - 표 머리는 `Oracle 19c`처럼 DBMS만 적는다(`settings.html:266`). 시스템 이름은 페이지 맨 위 선택 상자에만 있다.
  - 두 시스템이 같은 DBMS면(요구사항관리 · 통합ERP 모두 Oracle 19c) 표 머리가 같다. 바꿨는지 알기 어렵다.
  - 같은 탭의 다른 칸은 시스템별이 아니다.
    - ‘명명 템플릿’ · ‘시스템 컬럼’은 `dbm-set-extra` 하나에 저장된다(`:345`). 선택한 시스템과 상관없이 같은 값이다.
    - 이 탭의 첫 줄 설명은 ‘시스템(DB)마다 다른 물리 설계 규칙’(`app.js:1381`)이라 사용자는 모두 시스템별로 믿는다.
  - 다른 시스템 매핑을 고쳐 둔 채 선택을 바꾸면 선택 상자에는 표시가 없다.
    - 관찰: ERPPG를 고친 뒤 ERP로 바꾸면, 탭 점과 저장 막대 ‘시스템 1건’만 남는다.
- 제안
  - 표 머리를 `통합ERP(PG) · PostgreSQL 15 물리 타입`으로 쓴다.
  - 행 설명에 ‘이 시스템만’ 태그를 붙인다. 설정형 화면의 ‘바로 적용’ 태그와 같은 형식이다.
  - 시스템별이 아닌 칸에는 ‘모든 시스템 공통’을 적거나, 시스템별로 저장되게 고친다. 어느 쪽인지 정할 것에 올린다.
  - 저장하지 않은 매핑이 있는 시스템은 선택 상자 옵션 끝에 ` · 저장 안 함`을 붙인다.
  - 시스템을 바꾸면 표 머리를 갱신했다고 `aria-live="polite"`로 짧게 알린다.

### UQ-14 고정 인자 매핑(예: `TIMESTAMP(3)`)의 인자가 무시된다 — 심각도: 낮음
- 근거
  - `app.js:254`는 인자를 늘 원본 컬럼에서 가져온다. 대상 매핑 `TIMESTAMP(3)`에 대해 `DATE`는 `TIMESTAMP`가 된다(코드 확인).
  - 관리자 B가 밀리초 정밀도를 넣어도 반영되지 않는다.
- 제안
  - 대상 매핑의 인자가 자리표시(`n`, `p,s`)가 아니고 숫자면 그 값을 쓴다.
  - 또는 표 아래에 ‘인자는 원래 컬럼 값을 유지합니다 — 고정 인자는 쓰지 않습니다’를 적는다.

### UQ-15 저장 막대 · [변경 보기] · [되돌리기] · [이 DBMS 기본값으로] 연결 — 유지
- 근거
  - 관찰: 고친 칸이 저장 막대 ‘시스템 1건’에 들어간다. [변경 보기]에는 `통합ERP(PG) 일시 TIMESTAMP → TIMESTAMP(3)`처럼 시스템 이름과 함께 나온다.
  - [되돌리기]는 모든 시스템 작업본을 돌린다. 감사 로그는 시스템별로 남는다(`settings.html:428`).
  - [이 DBMS 기본값으로]는 ‘저장해야 반영됩니다’를 알린다.
  - 등록할 때 기본 매핑을 바로 저장한다(`:301`).
- 판단: 설정형 화면 규칙과 맞다. 그대로 둔다.

## 3. 담당 시스템을 코드로

### UQ-16 사용 중지한 시스템을 담당한 사용자를 고치면, 담당이 말없이 빠지고 세션이 끊긴다 — 심각도: 중간
- 근거
  - 계정 패널의 체크 목록 `SYSOPT`는 사용 중 시스템만 담는다(`settings.html:442, 507`).
  - 사용 중지한 시스템 코드를 가진 사용자를 열고 연락처만 고쳐 저장해도 일이 벌어진다.
    - 그 코드가 빠진다(`:561`).
    - `prevSys`와 달라져 `revokeSessions`가 실행된다(`:562`).
    - 감사 로그는 ‘사용자 정보 수정’으로만 남는다.
  - 시스템을 삭제하면 사용자 목록에 코드가 그대로 보인다. `sysNameOf`가 코드 그대로 돌려주기 때문이다(`app.js:181`).
- 제안
  - 사용 중지 · 삭제된 시스템 코드는 체크 목록에 `통합ERP (사용 중지)`로 막아서 보이고, 저장할 때 보존한다.
  - 지우려면 따로 [빼기]를 누르게 한다.
  - 목록에서는 삭제된 코드를 `ERP(삭제된 시스템)`으로 보인다.
  - 담당 변경 감사 로그에는 `담당 통합ERP → 통합ERP, 통합ERP(PG)`처럼 이름으로 적은 차이를 남긴다.

### UQ-17 감사 로그 · 이동 링크에 코드와 이름이 섞인다 — 심각도: 낮음
- 근거
  - 사용자 등록 감사 로그는 `담당 ${systems.join(', ')}`이라 `ERP, RQMS`처럼 코드로 남는다(`settings.html:553`). 다른 화면은 이름을 보인다.
  - 모델 조회 전용 안내의 요청 링크는 이름을 넘긴다(`model.html:1832` `sys=<이름>`).
    - 받는 쪽에서 `sysCodeOf`로 바꾸니 지금은 동작한다.
    - 이름을 바꾸는 사이에 연 탭에서는 찾지 못한다.
  - 마이페이지 요청 상태는 요청 당시의 이름 문자열(`role`)을 보인다(`mypage.html:172, 176`).
- 제안
  - 감사 로그는 `sysNames(systems)`로 쓴다.
  - 링크는 코드(`sys=ERP`)를 넘긴다.
  - 요청 상태 표시는 `key`에서 `sysNameOf`로 다시 만든다.

### UQ-18 이름이 다른 시스템의 코드와 같을 수 있다 — 심각도: 낮음
- 근거
  - `sysCodeOf`는 코드를 먼저, 그다음 이름을 찾는다(`app.js:180`).
  - 등록은 이름끼리, 코드끼리만 중복을 본다(`settings.html:294-295`).
  - 그래서 이름이 ‘HR’인 시스템과 코드가 ‘HR’인 시스템이 함께 있을 수 있다.
    - 이름으로 넘기는 호출(`system.html:91` 등 `{ system: curSys().name }` 다섯 곳, `import.html:80`, `app.js:1598`)은 엉뚱한 시스템으로 판정된다.
- 제안
  - 권한 판정 호출은 모두 코드를 넘긴다. 예: `{ system: curSys().code }`.
  - 등록 · 정보 수정에서 ‘다른 시스템 코드와 같은 이름’을 막는다.

### UQ-19 이름 표시(`sysNames`) 적용 범위 — 유지
- 근거
  - 설정 사용자 목록 · 계정 패널 · 역할 미리 보기(`settings.html:472, 526`), 마이페이지(`mypage.html:130`), 첫 화면 역할 링크(`index.html:73`), 모델 조회 전용 안내에서 모두 이름으로 보인다.
  - 역할 요청 키는 `sys:<코드>`로 저장한다(`mypage.html:170`).
  - 처리 판정도 코드로 비교한다(`settings.html:568`).
- 판단: 화면 표시는 자연스럽다. UQ-03(홈)과 UQ-04(결재 문서)만 고치면 된다.

## 4. 이동 기록 · 엔터티 옮기기

### UQ-20 이동 기록이 다음 작업 버전으로 그대로 넘어가 계속 쌓인다 — 심각도: 낮음
- 근거
  - `startNextVersion`이 확정 사본 `lk.doc.model`을 그대로 다음 버전으로 복사한다(`app.js:305-306`). 사본의 `moves`도 함께 넘어간다.
  - `loadData`도 이를 그대로 읽는다(`model.html:1689`).
  - 비교는 ‘a에 없고 b에 있는’ 엔터티만 이동으로 보므로, 대부분은 드러나지 않는다.
  - 하지만 다음 경우에 문제가 된다.
    - 같은 엔터티를 다시 옮기거나 같은 ID가 다시 쓰이면, 옛 기록(`find`가 첫 항목을 집음)의 당시 이름으로 잘못 보일 수 있다.
    - 목록이 버전마다 무한히 커진다.
- 제안
  - `startNextVersion`에서 `moves: []`로 비운다. 이전 이동은 확정 사본에 남는다.

### UQ-21 일괄 실행 뒤 다시 잇기가 대상 시스템의 모든 영역 작업본을 고친다 — 심각도: 낮음
- 근거
  - `relinkRefsIn`(`app.js:282-283`)은 대상 시스템의 사용 중 영역 전부를 돈다.
  - 결재 중이거나 확정 상태인 영역도 `setModelData(k, x.ver, …)`로 고친다. 원래 그 시스템에 있던 영역이라도 마찬가지다.
  - 결과 문구는 ‘서로 참조하던 영역’이라고 하지만, 실제로는 이번 실행과 상관없는 영역도 바뀔 수 있다.
- 제안
  - 다시 잇기 대상을 이번 실행에서 만든 복제본과 옮긴 영역으로 줄인다. 잠긴 영역은 건너뛴다.
  - 결과에 ‘다음 버전에서 갱신’ 영역을 따로 적는다. 엔터티 옮기기의 `later` 처리와 같은 방식이다.

### UQ-22 엔터티 [다른 영역으로 옮기기…] 창 — 유지(작은 보완 1)
- 근거(`model.html:2224-2290`)
  - 끊기는 관계, FK가 일반 속성으로 바뀌는 것, 다른 영역 참조, Ctrl+Z 경계를 미리 보여 준다.
  - 실행 직전에 다시 계산한다.
  - 원래 영역을 먼저 저장하고, 대상 저장이 실패하면 되돌린다.
  - Esc · [취소]는 연 곳으로 초점을 돌린다. 막혔을 때 첫 초점은 [취소]다.
  - `em-why`에 `role="status"`가 있다.
  - 원래 영역 · 대상 작업본과 확정 사본의 `moves`에 당시 이름을 남긴다. 비교에서는 사본의 목록을 먼저 쓴다(`app.js:1080-1081`).
- 작은 보완(낮음)
  - 선택 상자의 `(불가)` 옵션은 고를 수 없어 이유를 들을 길이 없다.
  - 선택 상자 아래에 ‘불가 n개: 재고관리(확정본 — 새 작업 버전 먼저) …’를 한 줄 요약으로 보인다.

## 5. 접근성 요약
- 일괄 창
  - 초점 갇힘과 Esc는 공용 처리로 동작한다.

- 시스템 등록 창: 오류 요약과 첫 오류 칸 초점, `aria-invalid`가 있다. 유지.
