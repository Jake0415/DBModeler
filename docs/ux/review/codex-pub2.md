# 퍼블리싱 정합성 점검 2차

2026-11-25 · 코드 정적 검토 · 높음 5건, 중간 15건, 낮음 5건

[자동 측정 기록](pub2-auto-check.md)을 먼저 확인하고 [디자인 가이드 v2](../01-design-guide.md), [1차 점검](../17-publishing-audit.md), [설정형 가이드](../24-settings-layout-guide.md), 디자인 견본과 비교했다. 범위는 `docs/ux/mockups`의 HTML 28개, 공통 `app.css` · `app.js`, 모델 `model.css`다. HTML과 스크립트 템플릿의 제목 · 버튼 · 상태 · 토스트 · 안내 · 확인 창을 비교했다. 아래 근거의 화면·자산 경로는 `docs/ux/mockups/` 기준이다. 높음은 권한 오안내, 주요 조작의 접근성 또는 영향이 큰 변경의 보호 누락, 중간은 작업 흐름이나 부품 계약의 불일치, 낮음은 주로 편집 형식 차이다. 실제 배치·대비·낭독 및 뷰포트별 결과는 브라우저를 사용하지 않아 미검증이다.

## 지적 사항

### PC-01 · 높음 · 데이터 타입 안내가 실제 권한과 충돌한다

- **근거** `settings.html:110–111`은 DA · Admin이 등록·매핑을 저장한다고 설명한다. `assets/app.js:87–88`의 두 권한은 DA에게만 부여된다. `assets/app.js:1527` 역시 등록 권한에 Admin을 넣고, 등록할 수 없는 모든 방문자에게 요청을 안내한다. `datatypes.html:445`는 요청과 등록 권한이 모두 없으면 요청 탭과 버튼을 숨긴다. [RBAC 2차 §4](../29-rbac-r2.md)도 시스템별 매핑은 DA만으로 적고 있다.
- **고칠 방법** 설정 안내와 화면 안내에 권한표의 등록·매핑 권한을 사용한다. 요청 안내는 `type.request`가 있는 경우에 보여 주고, 매핑은 담당 시스템 범위까지 명시한다.

### PC-02 · 높음 · 검수 기준에 영향 확인 단계가 빠졌다

- **근거** [설정형 가이드 §3.4](../24-settings-layout-guide.md#34-저장--안내--정렬)는 검수 기준 저장 전 영향 요약 확인 창을 요구한다. `rules.html:89–96`은 입력 범위를 검사한 뒤 즉시 버전을 올린다. `settings.html:404–405`의 이전 확인 분기는 비활성이다. 이전 기준으로 검증한 파일의 후속 조치는 `uploads.html:72`에 나온다.
- **고칠 방법** 검수 기준의 [저장] 다음에 공통 모달로 이전 → 이후 값, 적용 시점, 기존 엑셀 묶음의 재검증 영향을 보여 준다. [취소]와 [검수 기준 저장]으로 마무리하고 취소 시 편집값을 유지한다.

### PC-03 · 높음 · 화면 안내와 단축키 창이 같은 키에 반응한다

- **근거** `assets/app.js:1622–1623`의 화면 안내와 `assets/app.js:2567–2577`의 전역 단축키가 각각 `?`를 처리한다. 화면 안내가 `preventDefault()`를 호출해도 전역 처리기는 `defaultPrevented`를 검사하지 않는다. 안내를 닫는 Esc는 안내 패널 안에서만 처리된다.
- **고칠 방법** 열린 모달, 현재 화면 안내, 전역 단축키의 키 처리 우선순위를 공통화한다. `?` 한 번으로 의도한 부품 하나만 열고, 안내를 닫을 때 [화면 안내]로 포커스를 돌린다. 버튼에서 열기, 키로 열기, 펼친 뒤 외부로 포커스가 이동한 경우를 각각 검증한다.

### PC-04 · 높음 · 사업 종료 사유에 연결된 라벨이 없다

- **근거** `settings.html:701–706`의 사업 종료 창에서 `pje-why`는 기본값과 placeholder만 갖는다. 사용자가 편집하는 동안 입력 목적을 알려 주는 영구 라벨이 없다. 결재 회수의 사유는 `approvals.html:149–153`에서 연결된 라벨로 제공한다.
- **고칠 방법** 사업 종료 창도 공통 `.field`와 `label for`를 써서 ‘종료 사유’를 표시한다. 영향 요약과 최종 버튼에서 사업명·계정 중지 범위를 읽을 수 있도록 유지한다.

### PC-05 · 높음 · 사유 입력 창을 닫으면 포커스 복귀가 누락된다

- **근거** `assets/app.js:2529–2533,2567–2573`의 공통 `data-open`은 열기 버튼을 기억한다. 동적 `askReason()`은 `assets/app.js:1140–1144`에서 창을 제거하며 호출 위치로 포커스를 돌리지 않는다. 이 경로는 확인 요청 거절과 산출물 사유 입력에 쓰인다(`approvals.html:225`, `outputs.html:149`). 전역 단축키 창도 `assets/app.js:2465`에서 열림 클래스만 설정한다.
- **고칠 방법** 공통 모달 열기·닫기에 초기 포커스, Tab 순환, Esc 취소, 실행·취소 뒤 호출 위치 복귀를 맡긴다. 호출 버튼이 목록 재렌더링으로 사라지면 선택된 행 또는 목록 제목을 복귀점으로 삼는다.

### PC-06 · 중간 · 검수 기준의 입력 오류와 저장 막대가 설정형 기준에서 벗어난다

- **근거** `rules.html:53,71,86–96`은 오류용 `pol-wd-e`를 연결해 두었지만 저장 실패 시 토스트만 띄운다. 범위 검사에 정수 조건이 없어 `step=1`과 JS의 허용 범위도 다르다. `settings.html:228,250,402`는 공통 저장 막대, 입력별 오류, 첫 오류 포커스, 실패 요약을 제공한다.
- **고칠 방법** `.setbar`와 공통 숫자 검사를 재사용한다. 정수 2~10을 검사해 ‘2~10 사이의 정수를 입력하세요.’를 칸 아래에 표시하고 `aria-invalid`를 설정한다. 입력을 고치면 오류를 지우고 효과는 확인 창에서 설명한다.

### PC-07 · 중간 · 모델용 엑셀, DDL, 사전용 엑셀의 이름이 섞인다

- **근거** `import-excel.html:6,39–41`은 탭 제목 ‘엑셀로 가져오기’, 본문 제목 ‘가져오기’, 전환 ‘엑셀 정의서’를 쓴다. `import.html:6,21–24`도 본문 제목이 ‘가져오기’다. 펼친 트리는 ‘엑셀로 가져오기’·‘DDL 가져오기’, 접힌 트리는 ‘가져오기(엑셀 · DDL)’ 링크 하나를 보여 준다(`assets/app.js:1942–1954`). 사전에는 별도 ‘엑셀 가져오기’가 있다(`excel-import.html:109`, `assets/app.js:1625`). [26 문서](../26-erd-excel-import.md)는 ‘엑셀로 ERD 시작하기’를 쓴다.
- **고칠 방법** 모델용 화면은 ‘테이블 설계 엑셀 가져오기’와 ‘DDL 가져오기’, 사전용은 ‘사전 엑셀 가져오기’로 정하고 제목 · 경로 · 검색 결과 · 링크 이름에 사용한다. 접힌 트리에서도 두 형식에 접근할 수 있게 한다.

### PC-08 · 중간 · 같은 형식 전환이 화면 이동인데 누름 버튼으로 표시된다

- **근거** `import.html:24`와 `import-excel.html:41`은 다른 HTML로 가는 형식 전환을 `.seg` 버튼과 `aria-pressed`로 노출한다. 전자는 그룹 이름도 없다. 사전의 화면 간 전환은 `assets/app.js:2334`에서 링크와 `aria-current="page"`를 쓴다. 모델의 논리 · 물리 · 통합은 한 화면 안의 보기 전환이다(`model.html:81–82,1637`).
- **고칠 방법** 가져오기 형식 전환은 링크에 현재 페이지 상태를 붙인다. 같은 화면의 보기·상자 전환에는 이름 있는 세그먼트, 목록을 좁히는 데에는 칩과 선택 상태를 사용한다.

### PC-09 · 중간 · 모델용 엑셀 단계의 업로드·이동 부품이 사전용과 다르다

- **근거** `import-excel.html:44,60–66,101,285`는 고정 인라인 여백의 단계 줄·하단, 클릭 가능한 드롭 영역, 단계 제목으로의 포커스 이동을 쓴다. `import-excel.html:31`은 그 제목의 포커스 윤곽을 제거한다. `excel-import.html:136–160,231`은 단계별 축약/일반 드롭 영역과 [파일 선택], 공통 `.btn.primary` 하단 [다음]을 제공한다. 일반 드롭 영역 안에 버튼도 들어 있다.
- **고칠 방법** 파일 고르기·드롭·오류·다음 단계 액션의 배치와 키보드 동작을 공통화한다. 선택 버튼과 드롭 영역에 각각 필요한 의미만 부여하고, 단계 이동 위치가 키보드 사용자에게 보이게 한다. 허용 확장자와 실패 뒤 안내는 각 파일 형식에 맞춘다.

### PC-10 · 중간 · 확인 창의 문장과 선택지가 경로마다 달라진다

- **근거** `datatypes.html:393`의 매핑 이탈과 `settings.html:669,671`의 사용자 전환은 ‘버리고 … 볼까요/등록할까요?’를 네이티브 확인 창에 보낸다. `model.html:1615`의 공동 자동 배치도 ‘계속할까요?’를 쓰며, 결재 회수는 `approvals.html:149–153`에서 영향 설명과 [취소]/[회수]를 제공한다.
- **고칠 방법** 공통 확인 창에 대상·결과·영향을 표시하고 최종 버튼에 ‘변경 버리기’, ‘자동 배치 적용’, ‘회수’처럼 동작을 적는다. 최초 포커스와 닫은 뒤 포커스 복귀를 같은 방식으로 제공한다.

### PC-11 · 중간 · 화면 안내 등록 범위와 복합 화면 안내가 어긋난다

- **근거** `assets/app.js:1625,2330–2338` 기준 자동 부착 대상은 사전 하위 화면과 결재함·감사 로그·설정·마이페이지다. 모델용 엑셀은 `import-excel.html:69`의 단계 안내 배너를 제공하지만 동일한 ⓘ 진입점은 없다. 결재함의 공통 안내는 문서 승인 · 반려 · 회수 중심(`assets/app.js:1535`)이며 새 ‘확인 요청’ 상자의 처리 조건은 `approvals.html:204–235` 별도 분기에 있다.
- **고칠 방법** 모델용 가져오기 화면에서 기존 배너의 절차를 공통 화면 안내와 연결한다. 결재함에서는 현재 상자에 따라 안내를 바꾸고, 확인 요청의 확인·적용과 거절·철회 권한 및 적용 시점을 표시한다.

### PC-12 · 중간 · 데이터 타입의 두 탭 줄에서 화면 안내 기준점이 다르다

- **근거** `datatypes.html:54–58`은 내부 탭 줄에 인라인 여백과 배경을 지정한다. `assets/app.js:1524–1527,2333–2335`는 사전 공통 탭 줄에 화면 안내를 달고 논리 타입 · 매핑 · 요청 · 변경 이력에 같은 내용을 쓴다. 설정·마이페이지는 내부 탭 변경을 안내에 연결한다(`assets/app.js:1541,1569,1605–1617`).
- **고칠 방법** 상위 사전 이동과 페이지 내부 탭을 서로 이름 붙이고, 페이지 내부 탭 줄의 여백과 안내 위치를 설정형 화면과 맞춘다. 매핑·요청·이력에서 현재 탭의 할 일과 권한을 표시한다.

### PC-13 · 중간 · 설정에서 편집 즉시 저장되는 결재 위임의 적용 시점이 드러나지 않는다

- **근거** `mypage.html:46,265–272`는 프로필 행에 [위임 저장]을 두고 즉시 저장·알림을 실행한다. 적용 시점 표지가 없다. [설정형 가이드 §3.4](../24-settings-layout-guide.md#34-저장--안내--정렬)와 [1차 점검의 설정형 기준](../17-publishing-audit.md#65-설정형-화면-점검-항목-2026-11-24--24-설정형-화면-레이아웃-가이드-5)은 즉시 적용 동작과 하단 저장의 구분을 요구한다.
- **고칠 방법** 위임을 독립 동작으로 드러내고 저장 버튼 옆에 ‘바로 적용’을 붙인다. 저장 즉시 예약이 등록되며 결재 위임은 입력한 시작일부터라는 점을 보조 칸에 명시한다.

### PC-14 · 중간 · 도메인 그룹의 메뉴·필드·엑셀 열 이름이 다르다

- **근거** `domain-groups.html:49,87,113,461`, `dictionary.html:76,136,298`, `dict-grid.html:284,303`, `excel-import.html:450,453`, `rules.html:37`, `settings.html:94`, `assets/app.js:83,917,1517–1520`에 ‘도메인 그룹’, ‘도메인그룹’, ‘분류(그룹)’, ‘도메인분류’가 나타난다. 엑셀 매핑은 원본 열 ‘도메인분류명’과 대상 필드를 한 줄에서 연결하므로 구별이 특히 필요하다.
- **고칠 방법** UI는 ‘도메인 그룹’과 그 하위 ‘분류’로 고정한다. 원본 헤더는 출처를 표시해 그대로 인용하고, 내부 필드 키에 매핑되는 표시 문자열만 바꾼다.

### PC-15 · 중간 · 역할·읽기 권한의 이름이 화면과 도움말마다 다르다

- **근거** `assets/app.js:40`의 ‘Admin’과 `assets/app.js:1555` 및 `settings.html:310`의 ‘관리자’, `login.html:87–91`의 ‘관리자’가 같은 역할을 가리킨다. `model.html:98`은 ‘조회 전용’, `dict-grid.html:88`과 `rules.html:27`은 ‘읽기 전용’, `excel-import.html:519,977`은 ‘열람 전용’을 쓴다. 결재 중 문서의 주체도 `approvals.html:576`에서 ‘품의자’와 ‘신청자’로 갈린다.
- **고칠 방법** 정식 역할명은 ‘시스템 관리자(Admin)’로 처음 설명한 뒤 ‘Admin’을 쓰고, 배지·권한표는 공통 역할명에서 가져온다. 수정 불가 상태는 ‘조회 전용’, 설명에는 제한과 다음 행동을 적는다. 제출한 사람은 ‘신청자’로 맞춘다.

### PC-16 · 중간 · 결재와 관리 변경의 버튼은 구별되지만 짧은 이름만으로는 대상이 모호하다

- **근거** `approvals.html:149–153,212–230,235,811–824`에는 문서 ‘회수’, 확인 요청 ‘철회’, 관리 변경 ‘확인 — 적용’, 결재 후 ‘되돌리기’가 함께 나온다. 문서 반려와 관리 변경 거절은 서로 다른 흐름이다. 모델의 확정 신청 회수는 `model.html:190`에서 이미 대상을 명시한다.
- **고칠 방법** ‘결재 문서 회수’, ‘확인 요청 철회’, ‘확인하고 적용’, ‘관리 변경 거절’로 대상과 결과를 붙인다. 기존 결재의 승인 · 반려는 그대로 쓰고, 처리 직후 되돌릴 수 있는 토스트 동작에는 공통 [실행 취소]를 쓴다.

### PC-17 · 중간 · 토스트 결과·오류·다음 행동의 문장 구조가 일정하지 않다

## 화면별 소스 비교 범위

`style=` 수는 HTML 원문의 속성 표기이며 스크립트의 HTML 템플릿을 포함한다. 실행 중 JS가 DOM 속성으로 지정하는 값은 이 숫자에 포함하지 않는다. 공통 CSS의 헤더·탭·패널·모달·상태와 비교했고, 화면 전용 레이아웃은 화면 목적이 다르면 허용했다.
