# 역할 · 권한 (RBAC)

> 2026-11-19 · 상태: **적용 완료(목업)**
> 배경: 권한 검사가 13개 화면, 40곳에 흩어져 있었다. 담당 시스템은 실제 편집을 막지 않았다(홈 표시에만 쓰임).
> 원칙: 역할을 겸할 수 있고, 겸하면 할 수 있는 일을 합친다(00-inputs 1-3). 역할별 화면을 따로 두지 않고 버튼이 늘어난다(02-flows).

## 1. 구성
**권한 = 역할 × 할 수 있는 일 × 범위.** 이 표는 `assets/app.js`의 `PERMS` 한 곳에만 정의한다. 아래가 모두 같은 데이터를 쓴다.
- 설정 → **권한표** 탭
- 사용자 패널의 "할 수 있는 일"
- 화면의 검사(`can()`)

| 범위 | 뜻 |
|---|---|
| 전체 | 기관 전체 (기관 사전 · 설정 · 감사) |
| 담당 시스템 | 사용자의 담당 시스템에서만. 담당 시스템이 "전체"면 모든 시스템 |
| 조회만 | 역할이 없는 사용자. 읽기만 한다 |

## 3. 함께 지키는 규칙
- **자기 승인**: 모델러 겸 DA가 자기 신청을 승인하면 "자기 승인"으로 기록한다. 최종 승인을 켠 결재선이면 다른 사람이 한 번 더 본다.
- **확정 잠금**: 확정 결재 중이거나 확정된 버전은 권한과 상관없이 조회만 된다.
- **계정 상태**: 사용 중지된 계정은 아무 권한이 없다. 권한을 빼면 그 사람의 열린 세션이 끝난다(14 §7).
- **자기 보호**: 자기 역할 · 상태는 스스로 바꿀 수 없고, 마지막 Admin의 Admin 역할은 뺄 수 없다(14).

## 4. 화면 적용
| 화면 | 바뀐 동작 |
|---|---|
| 모델 | 모델러라도 **담당 시스템이 아니면 조회 전용**이다. 안내 문구는 "요구사항관리은(는) 내 담당 시스템이 아닙니다 — Admin에게 담당 시스템 추가를 요청하세요 · 내 담당: 통합ERP". 확정 신청 버튼의 설명도 같다 |
| 표준 맞추기 · DDL 가져오기 | 모델 편집 권한(담당 시스템)으로 판단한다. 적용하는 순간에도 다시 확인한다 |
| 시스템 홈 · 트리의 ＋ | 업무 영역 만들기 = 담당 시스템의 모델러, 또는 Admin |
| 결재함 · 홈 "내 차례" | 그 단계의 역할 + 모델 확정 문서라면 그 영역의 시스템이 담당인지 함께 본다. 담당이 아니면 대기함에 들어오지 않고 승인 · 반려 버튼도 없다 |
| 후보 큐 · 감사 로그 · 설정 · 사전 공표 | 권한표의 같은 항목으로 판단한다 |
| 설정 → 권한표 | 위 표를 화면에서 그대로 보인다(코드와 같은 데이터) |
| 설정 → 사용자 | 패널 아래 "할 수 있는 일"에 그 사람이 지금 할 수 있는 일과 범위를 보인다 |

예: 최담당(기관 담당자 · 모델러, 담당: 통합ERP)
- 통합ERP 회계관리 모델: 편집할 수 있다.
- 요구사항관리 모델: 조회만 한다.
- 요구사항관리 모델 확정 문서의 최종 승인: 차례가 오지 않는다.
- 사전 신청의 최종 승인: 기관 전체라 차례가 온다.

## 5. 남긴 것
- **업무 영역 단위 권한**(영역 담당자만 편집): 지금은 시스템 단위다. 영역이 많아지면 "영역 담당자"를 더할 수 있다.
- **결재 위임**(부재 시 대리 결재자)과 **역할 유효 기간**(외주 인력의 기간제 역할)은 정책 항목 후보다.
- **서버 집행**: 실제 제품은 같은 권한표를 서버가 모든 요청에서 검사한다. 화면에서 버튼을 숨기는 것은 편의일 뿐이다(14 §8).
- 일부 화면(홈의 할 일 묶음, 결재함의 탭 표시)은 아직 역할 이름(`ME.has`)으로 나누어 보인다. 권한 판단이 아니라 표시 구분이라 그대로 두었다.
