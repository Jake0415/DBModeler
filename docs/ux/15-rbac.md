# 역할 · 권한 (RBAC)

> 2026-11-19 · 상태: **적용 완료(목업)** · 2026-11-24 2차 검토 반영([29](29-rbac-r2.md))
> 배경: 권한 검사가 13개 화면, 40곳에 흩어져 있었다. 담당 시스템은 실제 편집을 막지 않았다(홈 표시에만 쓰임).
> 원칙: 역할을 겸할 수 있고, 겸하면 할 수 있는 일을 합친다(00-inputs 1-3). 역할별 화면을 따로 두지 않고 버튼이 늘어난다(02-flows).

## 1. 구성
**권한 = 역할 × 할 수 있는 일 × 범위.** 이 표는 `assets/app.js`의 `PERMS` 한 곳에만 정의한다. 아래가 모두 같은 데이터를 쓴다.
- 설정 → **권한표** 탭
- 사용자 패널의 "할 수 있는 일"
- 화면의 검사(`can()`)

| 범위 | 뜻 |
|---|---|
| 전체 | 기관 전체 (기관 사전 · 설정 · 감사) |
| 담당 시스템 | 사용자의 담당 시스템에서만. 담당 시스템이 "전체"면 모든 시스템 |
| 조회만 | 역할이 없는 사용자. 읽기만 한다 |

## 3. 함께 지키는 규칙
- **자기 승인**: 기본은 허용 + **최종 승인 자동 부착**이다. 자기 승인한 문서는 최종 승인 단계가 붙고, 신청자가 아닌 최종 승인자가 없으면 자기 승인할 수 없다. 비허용이면 자기 신청은 대기함 · 알림에 뜨지 않는다.
- **두 사람 확인**: 결재 통제가 느슨해지는 변경(최종 승인 끄기 · 자기 승인 허용)과 높은 역할 부여(DA · 기관 담당자 · Admin · 감리, 그 역할의 담당 시스템 넓히기)는 결재함 › 확인 요청에서 기관 담당자가 확인한 뒤 적용된다. 기관 담당자가 0명일 때만 Admin이 첫 1명을 바로 지정한다.
- **소속 · 기한**: 계정은 내부 · 외주 · 감리 중 하나다. 외주 · 감리는 사업과 사용 기한이 필수이고, 기한이 지나면 아무 권한이 없다. 사업 종료는 인계(신청 · 영역 담당 · 엑셀 묶음) 뒤 일괄 중지한다.
- **결재 위임**: 결재 역할이 있는 사람은 마이페이지에서 기간 · 대리인을 정한다. 대리인은 자기 신청을 대리 승인할 수 없고 다시 위임할 수 없다. 이력에 ‘대리(원 담당자)’로 남는다.
- **확정 잠금**: 확정 결재 중이거나 확정된 버전은 권한과 상관없이 조회만 된다.
- **계정 상태**: 사용 중지된 계정은 아무 권한이 없다. 권한을 빼면 그 사람의 열린 세션이 끝난다(14 §7).
- **자기 보호**: 자기 역할 · 상태 · 담당 시스템은 스스로 바꿀 수 없고, 마지막 Admin의 Admin 역할은 뺄 수 없다(14).

## 4. 화면 적용
| 화면 | 바뀐 동작 |
|---|---|
| 모델 | 모델러라도 **담당 시스템이 아니면 조회 전용**이다. 안내 문구는 "요구사항관리은(는) 내 담당 시스템이 아닙니다 — Admin에게 담당 시스템 추가를 요청하세요 · 내 담당: 통합ERP". 확정 신청 버튼의 설명도 같다 |
| 표준 맞추기 · DDL 가져오기 | 모델 편집 권한(담당 시스템)으로 판단한다. 적용하는 순간에도 다시 확인한다 |
| 시스템 홈 · 트리의 ＋ | 업무 영역 만들기 = 담당 시스템의 모델러, 또는 Admin |
| 결재함 · 홈 "내 차례" | 그 단계의 역할 + 모델 확정 문서라면 그 영역의 시스템이 담당인지 함께 본다. 담당이 아니면 대기함에 들어오지 않고 승인 · 반려 버튼도 없다 |
| 후보 큐 · 감사 로그 · 설정 · 사전 공표 | 권한표의 같은 항목으로 판단한다 |
| 설정 → 권한표 | 위 표를 화면에서 그대로 보인다(코드와 같은 데이터) |
| 설정 → 사용자 | 패널 아래 "할 수 있는 일"에 그 사람이 지금 할 수 있는 일과 범위를 보인다 |

예: 최담당(기관 담당자 · 모델러, 담당: 통합ERP)
- 통합ERP 회계관리 모델: 편집할 수 있다.
- 요구사항관리 모델: 조회만 한다.
- 요구사항관리 모델 확정 문서의 최종 승인: 차례가 오지 않는다.
- 사전 신청의 최종 승인: 기관 전체라 차례가 온다.

## 5. 남긴 것
- **업무 영역 단위 권한**(영역 담당자만 편집): 지금은 시스템 단위다. 영역이 많아지면 "영역 담당자"를 더할 수 있다.
- **결재 위임**(부재 시 대리 결재자)과 **역할 유효 기간**(외주 인력의 기간제 역할)은 정책 항목 후보다.
- **서버 집행**: 실제 제품은 같은 권한표를 서버가 모든 요청에서 검사한다. 화면에서 버튼을 숨기는 것은 편의일 뿐이다(14 §8).
- 일부 화면(홈의 할 일 묶음, 결재함의 탭 표시)은 아직 역할 이름(`ME.has`)으로 나누어 보인다. 권한 판단이 아니라 표시 구분이라 그대로 두었다.

## 6. 교차 검토 반영 (codex-r1rbac 12건 · claude-r1rbac 12건)
| 지적 | 반영 |
|---|---|
| 통합ERP에서 새로 만든 영역이 요구사항관리 소속으로 판정됨 | 영역의 시스템을 저장된 시스템 코드로 판정한다. 모델 확정 문서는 신청할 때 시스템 이름을 함께 남긴다 |
| 시스템을 알 수 없으면 역할만으로 허용 | 모델 문서 · 영역의 시스템을 알 수 없으면 **아무도 처리하지 못한다**(조용히 넓어지지 않음) |
| 사전 신청 권한을 검사하는 화면이 없음 | 엑셀 가져오기의 저장 · 신청에 `dict.request`를 적용했다. 기관 담당자 · Admin 단독 · 조회만 사용자는 엑셀 묶음을 만들 수 없다 |
| 결재 담당자가 없어도 신청 · 단계 전환이 진행됨 | 확정 신청 전에 결재선의 모든 단계에 처리할 수 있는 사람(사용 중 · 담당 범위 · 신청자 제외)이 있는지 확인하고, 없으면 막는다. DA 승인 뒤 최종 담당자가 없으면 이력에 "담당 지정 필요"를 남기고 알린다. 사용자를 중지하거나 담당을 바꿔 결재 담당자가 없는 시스템이 생기면 설정 화면이 경고한다 |
| 최종 승인이 독립 검토를 보장하지 않음 | 최종 승인에서 **신청자와 1단계 승인자를 뺀다**. 결재 이력에 처리자 ID를 남겨 이름이 바뀌어도 구분한다. 최종 승인을 끈 결재선의 자기 승인 한 번은 지금처럼 허용하고 "자기 승인"으로 기록한다 |
| 알림이 처리할 수 없는 사람에게도 감 | 1단계 · 최종 알림을 **실제로 처리할 수 있는 사람**에게만 보낸다(판정과 같은 함수) |
| 새 신청 안내 · 기본 탭이 DA 여부로 정해짐 | 그 문서를 내가 처리할 수 있을 때만 "바로 대기함에 들어왔습니다"라고 안내하고 대기함을 연다. 아니면 "1단계 담당 n명에게 알렸습니다" + 내 신청 |
| 공표와 영구 삭제가 한 권한 | 둘로 나눴다. Admin은 영구 삭제만 할 수 있다. 공표 버튼과 변경 내역의 공표도 `dict.publish`로 판단한다 |
| 확정 신청이 `model.submit`을 쓰지 않음 | 확정 신청에 `model.submit`을 적용했다. 회수는 신청자 권리로 둔다(담당이 바뀌어도 자기 신청을 회수해 잠금을 풀 수 있게) |
| 담당 범위 축소에 세션이 남음 | 담당 시스템이 줄어도 그 사람의 열린 세션을 끝낸다 |
| 사용자 관리가 Admin 역할 이름으로 검사됨 | 사용자 등록 · 역할 · 담당 변경은 `users` 권한으로 판단한다. 역할 · 담당 변경 요청 알림은 `users` 권한자에게 간다 |
| 엑셀 묶음 열람이 권한표 밖 | `excel.viewall` 권한을 만들었다 |
| "담당 시스템을 요청하세요" 뒤가 막다른 길 | 모델 · 표준 맞추기 · DDL 가져오기의 조회 전용 안내에 **[담당 시스템 추가 요청]** 링크를 두었다. 마이페이지 요청 창에 "담당 시스템 추가 — 시스템 이름"이 미리 골라져 열리고, 관리자가 담당을 추가하면 요청이 닫히며 알림이 간다 |
| Admin이 만든 영역을 아무도 못 고칠 수 있음 | 그 시스템을 맡은 모델러가 없으면 영역을 만들 때 경고한다 |
| "요구사항관리은(는)" 같은 조사 | 받침에 맞춰 붙인다: "내 담당 시스템에 요구사항관리가 없습니다" |
| 사용자 패널 "할 수 있는 일" | 모두에게 주어지는 보기 권한은 빼고, 결재는 "사전 신청은 기관 전체 · 모델 확정은 담당 시스템"으로 두 범위를 함께 보인다 |

홈의 할 일 묶음과 결재함 탭 표시는 표시용이라 역할 이름으로 두었다.
## 7. 결재 중 열람 범위 (확정, 2026-11-19)
> 사용자 결정: 결재 중에는 **품의한 사람과 결재 담당자만** 볼 수 있어야 한다.

| 문서 상태 | 볼 수 있는 사람 |
|---|---|
| **결재 중** (1단계 · 최종 승인 대기) | 품의자, 그리고 그 문서 결재선의 담당자. 결재선 담당자는 1단계 처리 가능자(DA, 담당 범위)와 최종 처리 가능자(기관 담당자, 담당 범위)이고, 이미 처리한 사람도 포함한다. **참조자와 다른 DA · 기관 담당자도 볼 수 없다** |
| 결재 끝 (완료 · 반려 · 회수) | 품의자, 참조자, 결재 역할(`appr.viewall`), 결재에 참여한 사람 |

결재 중인 모델은 다음처럼 막는다.
- **결재함**: 문서를 열면 "결재 중인 문서는 품의자와 이 문서의 결재 담당자만 볼 수 있습니다"를 보인다. 전체 목록과 전체 검색에도 나오지 않는다.
- **모델 화면 · 트리 · 홈 · 시스템 홈**:
  - 결재 중인 버전(예: v2) 대신 **마지막 확정본(v1)**을 조회 전용으로 보인다. 안내는 "v2는 결재 중이라 품의자와 결재 담당자만 볼 수 있습니다".
  - 확정본이 없으면 아무것도 보이지 않는다.
  - 업무 영역이 "검토" 상태라는 사실만은 보인다.
- **제출본 주소(`?snap=`)**: 결재 중이면 열람 제한으로 비워 둔다(다른 버전으로 바꿔 보여 주지 않음).
- **DDL · 산출물**: 결재 중인 버전 대신 확정본 기준으로 만들고, "검토 중 사본" 선택지를 숨긴다.

판정은 `canSeeDoc()` · `areaView()` 두 함수로 한다. 결재함 · 모델 · 트리 · 홈 · 시스템 홈 · DDL · 산출물 · 전체 검색이 이 두 함수를 쓴다.
