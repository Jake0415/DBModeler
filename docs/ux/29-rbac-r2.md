# 29. RBAC 2차 검토 — 역할별 화면 · 서비스 시나리오 (2026-11-24)

> 요청: Admin · DA · 모델러 · 기관 담당자 각각의 화면을 자세히 보고, RBAC 관점에서 서비스 사용성까지 함께 검토해 정리한다. Codex · UX 전문가와 협의해 최종 수정과 FE(목업)까지 끝낸다.
> 상태: **반영 완료(목업)**. 권한표는 [15 §2](15-rbac.md), 합의는 [resolution-rbac-r2](review/resolution-rbac-r2.md).

## 1. 어떻게 봤나
1. **역할별 화면 수집**: 역할을 하나만 가진 시험 계정 6개로 화면 23개를 1920 화면에서 열었다. 보이는 버튼 · 꺼진 버튼(이유) · 안내 띠를 모아 역할마다 다른 점만 추렸다([rbac-role-inventory](review/rbac-role-inventory.md)).
   - 시험 계정: Admin만 · DA만 · 모델러만(외주) · 기관 담당자만 · 조회만 · 감리.
   - 처음 수집은 CSS로 끈 버튼을 ‘켜짐’으로 읽었다. 모델 화면은 직접 다시 확인해 바로잡았다.
2. **리뷰 두 건**:
   - Codex: 권한 판정 · 직무 분리 · 화면과 정의의 일치(RB-01 ~ 11).
   - UX: 사업 시작 → 표준 결재 → 모델링 → 산출물 → 사업 종료 흐름(SC-01 ~ 26).
3. **협의 두 건**: 합의안 초안(R-01 ~ 26)을 두 리뷰어에게 다시 보내 동의 · 수정 · 반대를 받았다.
   - Codex: 수정 제안 17 · 추가 2.
   - UX: 반대 0 · 수정 제안 11 · 추가 7.
   - 갈린 곳은 §4에서 정했다.

4. **구현 확인 리뷰 두 건**: Codex CI-01 ~ 21 · UX UI-01 ~ 24 → 반영([resolution 아래](review/resolution-rbac-r2.md)).
5. **검증**: 역할별 계정 11개 × 화면 25 ~ 32개를 두 번(구현 뒤 363회, 확인 리뷰 반영 뒤 다시) 열어 오류 0건, 403은 설계대로(설정 = Admin, 감사 로그 = 모델러 · 조회만 차단, 범위 밖 영역 = 외주 · 감리).

## 2. 결론 — 지금대로 써도 되나
**구조는 그대로 쓴다. 다섯 군데를 메운 뒤 적용한다(이번에 목업에 반영).** 그대로 두는 것은 세 가지다.
- 권한을 `PERMS` 한 곳에서 정한다.
- 신청자 · 1단계 · 최종 승인자를 나눈다.
- 결재 중 문서는 품의자 · 결재선만 본다.

메운 다섯 군데는 다음과 같다.
1. **직무 분리를 끄는 스위치를 Admin 혼자 쥐고 있었다**: 결재 정책 · 높은 역할 부여 → 기관 담당자 확인.
2. **결재 판정이 화면마다 달랐다**: 자기 승인 · 결재 중 열람 → 판정 하나로.
3. **외주 · 감리 계정의 범위 · 기한 · 회수 · 인계가 없었다** → 사업 · 소속 · 기한 · 조회 범위 · 사업 종료.
4. **DDL · 산출물이 권한 · 기록 없이 나갔다** → `out.export` · 감사 로그 · 개인정보 사유.
5. **역할에 따라 첫 화면 · 안내가 맞지 않았다** → 담당 시스템으로 시작, 역할별 할 일, 편집 도구 숨김.

## 3. 역할별로 본 것과 바꾼 것
### Admin (시스템 관리자)
| 본 것 | 바꾼 것 |
|---|---|
| 혼자서 최종 승인을 끄고 자기 승인을 켤 수 있었다. DA를 겸하면 자기 신청을 혼자 끝낼 수 있었다. | 느슨해지는 결재 정책은 **기관 담당자 확인 대기**(R-01). 설정에 ‘확인 대기’ 띠와 [철회]가 생긴다. |
| DA · 기관 담당자 · Admin 역할을 혼자 줄 수 있었다. | 높은 역할 부여와 그 역할의 담당 시스템 넓히기는 확인 대기(R-03). 위험한 겸임은 경고 + 사유. 기관 담당자가 0명일 때만 첫 1명을 바로 지정(N-01). |
| 타입 · 도메인그룹 · 영구 삭제로 표준 내용을 결재 없이 바꿀 수 있었다. | `type.*` · `dict.group` · `dict.purge`는 DA만(R-04). |
| 외주 계정을 한 명씩 수동으로 중지해야 했고, 빠진 사람의 신청이 영역을 잠근 채 남았다. | 설정 › 기관 › **사업** 목록과 **[사업 종료]** 창: 대상 → 인계(신청 · 영역 담당 · 엑셀 묶음) → 인수자 → 일괄 중지(R-09 · R-10). |
| 역할을 바꾸면 저장한 뒤에야 결재 공백이 보였다. | 저장 전에 늘고 주는 일 · 빠지는 결재 · 확인 대기를 보여 준다(R-16). 감사 로그에 역할 · 담당 시스템 전후를 남긴다. |
| 홈에 Admin이 할 일이 결재 기한 하나뿐이었다. | 홈 카드: 7일 안 만료 계정 · 내 확인 대기 · 결재 공백 시스템(R-23). |
| 권한표의 줄 · 칸이 들쭉날쭉했다. | 역할 칸 가운데 정렬 · 권한 코드 한 줄 정렬, 감리 열, 결재 줄은 ‘사전 전체 · 모델 담당’ 두 배지(R-22). |

### DA (데이터 관리자)
| 본 것 | 바꾼 것 |
|---|---|
| 업무 영역을 만들 수 없어 주제 영역 체계를 먼저 잡지 못했다. | `area.create`(담당 시스템)(R-19). |
| 검수 기준을 볼 수도 고칠 수도 없었다(설정 403). | 검수 기준을 **표준 사전 › 검수 기준** 화면으로 옮겼다. DA · Admin이 고치고 모두 읽는다(R-19). |
| 자기 승인 비허용인데도 자기 신청이 대기함 · 알림에 떴다. 누른 뒤에야 막혔다. | 판정 하나로: 비허용이면 대기함에 뜨지 않는다(R-06). |
| 허용이면 자기 승인으로 한 사람이 표준을 반영할 수 있었다. | 자기 승인한 문서는 최종 승인을 자동으로 거친다. 신청자가 아닌 최종 승인자가 없으면 자기 승인을 막는다(R-02). |
| 부재 중 결재가 멈췄다. | 마이페이지 › **결재 위임**: 기간 · 대리인. 이력에 ‘대리’(R-08). |
| 결재 중인 남의 사전 신청을 상세에서 볼 수 있었다. | 목록 · 상세 같은 판정(R-07). |

### 모델러 (내부 · 외주)
| 본 것 | 바꾼 것 |
|---|---|
| 외주 모델러가 다른 시스템 모델 · DDL · 산출물까지 모두 봤다. | 조회 범위를 **소속에서** 정한다. 외주는 담당 시스템만, 예외는 사유. 범위 밖 시스템은 시스템 고르기에 나오지 않고 주소로 열면 403(R-11). |
| 첫 화면이 담당 아닌 시스템으로 열려 ‘조회만’이 먼저 보였다. | 주소에 시스템이 없으면 담당 시스템 · 편집할 수 있는 첫 영역으로 연다(R-18). |
| DDL · 산출물을 어디서나 기록 없이 받았다. | 내려받기는 담당 시스템 안, 감사 로그(R-14). |
| 왜 버튼이 없는지 스스로 확인할 길이 없었다. | 마이페이지 › **권한표 보기**(읽기 전용, ‘나’ 열)와 소속 · 기한 · 조회 범위 표시(R-21). |
| 기한이 끝나 가는 줄 몰랐다. | 홈 카드 ‘내 계정 사용 기한 D-n’과 남은 일(N-04). |

### 기관 담당자 (최종 승인)
| 본 것 | 바꾼 것 |
|---|---|
| 감사 로그를 볼 수 없었다(403). | `audit.view`(R-15). |
| Admin의 정책 · 역할 변경을 알 길이 없었다. | 결재함 › **확인 요청** 탭(결재 기한 · 준수율 집계에서 뺌): 이전 → 이후 · 사유 · 영향을 한 장에, [확인 — 적용] · [거절]. 확인 직전에 값이 바뀌었으면 적용하지 않는다(R-01 · R-03). 홈에도 ‘관리 변경 확인 요청’ 카드. |
| 부재 중 결재를 맡길 방법이 없었다. | 마이페이지 › 결재 위임 — 같은 결재 역할의 내부 사용자에게 기간을 정해 맡긴다(R-08). |
| 결재 역할 계정의 비밀번호를 Admin이 초기화해도 몰랐다. | 기관 담당자에게 알림. 결재 역할은 본인이 임시 비밀번호를 바꾼 뒤에 열린다(R-05). |

### 감리 · 조회만
| 본 것 | 바꾼 것 |
|---|---|
| 감리 역할이 없어 DA나 기관 담당자를 줘야 했다(승인 권한까지 생김). | **감리** 역할: 읽기 전용 + 조회 범위의 끝난 결재 · 감사 로그(기관 관리 기록 제외) · 산출물 내려받기. 기한 필수(R-12). |
| 조회만 계정이 DDL · 개인정보 컬럼 목록을 내려받았다. | 조회만은 미리보기만. 개인정보 컬럼 목록은 DA · 기관 담당자 · 감리만, 사유(R-14). |
| 역할이 없는 사람의 모델 화면에 편집 도구가 흐리게 남았다. 화면 낭독기는 켜진 버튼으로 읽었다. | 역할상 편집할 일이 없으면 편집 도구를 **숨긴다**. 모델러가 지금만 못 하면 흐리게 + `aria-disabled` + 이유(R-17). |
| 홈에 할 일이 없었다. | 감리: 끝난 결재 문서 · 감사 로그 바로 가기. 조회만: 표준 사전 바로 가기(R-23). |

## 5. 남긴 것 (구현 단계)
- 서버 트랜잭션 · 세션 강제 종료 · 확인 요청 메일(N-07).
- 시스템 전용 타입 권한을 대상 시스템 코드로 검사(R-27). 참조 영향 미리보기는 열람 가능한 버전만(R-28).
- 역할마다 다른 담당 시스템: 계정 하나에 담당 하나로 두고, 필요하면 계정을 나눈다.
- 전체 검색(Ctrl K)의 조회 범위 적용: 시스템 고르기 · 모델 · DDL · 산출물 · 시스템 전체 ERD는 반영했고, 전체 검색 결과의 범위 거르기는 구현 단계에서 한다.
- 후보 큐 인계: 발생 기록은 신청자 이름 그대로 두고 DA가 판단한다.

- `import-excel.html`: 취소 때 다시 확인.

## 7. 변경 기록 — 목업을 권한표에 맞춤 (2026-11-25, 사람 확인: 권한표 기준)
> 요구사항 추적 점검(`docs/impl/trace/mockup-findings.md` F-26 · F-39 · F-40)에서 목업과 권한표(`packages/rules` PERMS · `docs/impl/rbac-matrix.md`)가 다른 곳을 찾았다. 사용자가 **권한표 기준**으로 정해 목업을 고쳤다. 권한표는 바꾸지 않았다.

| 항목 | 무엇 | 왜 | 화면 |
|---|---|---|---|
| F-26 | 임시 비밀번호 DA의 후보 처리: 숨김 → **[반려] · [신청으로 전환] 흐리게 + 이유**(‘임시 비밀번호를 바꾼 뒤 처리할 수 있습니다’, 마이페이지 보안 탭 링크) | 역할은 있고 지금만 못 함 = 흐리게 + 이유(rbac-matrix `cand.decide` 임시PW) | `candidates.html` |
